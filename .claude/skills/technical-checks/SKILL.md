# Технические проверки

Ты проверяешь техническое качество страницы сайта.

## Чек-лист

### 1. Консоль браузера
- [ ] Собери JS-ошибки: `playwright-cli console`.
- [ ] Зафиксируй в отчёте, только если ошибки есть.

### 2. Сетевые запросы
- [ ] Собери запросы: `playwright-cli requests`.
- [ ] Отфильтруй запросы со статусом 404.
- [ ] Для каждого битого ресурса укажи: URL, тип (картинка/скрипт/стиль/шрифт), страницу, анкор (если применимо).

### 3. HTTP-статусы страниц
- [ ] Нет внутренних 3xx-редиректов (в т.ч. из-за отсутствия/наличия завершающего слэша в URL).
- [ ] Нет 4xx на страницах, которые должны быть доступны.

### 4. Ссылки и перелинковка
- [ ] Нет пустых (`href="#"`, `href=""`) или явно битых ссылок — кроме случаев, когда клик обрабатывается через JS (проверь, что обработчик реально есть, а не просто мёртвый якорь).
- [ ] tel:-ссылки в правильном формате (`tel:+1XXXXXXXXXX`).
- [ ] Списочные/карточные секции (локации, услуги, сотрудники и т.п.) ведут на существующие страницы там, где такие страницы на сайте уже есть — не должно быть карточки без ссылки, если целевая страница существует.
- [ ] Ссылка ведёт на **правильный** соответствующий объект, а не просто на любую существующую страницу того же типа (например: карточка сотрудника ведёт на его собственную страницу, а не на страницу другого сотрудника).
- [ ] Хабовые/родительские пункты меню без прямой ссылки — только если это осознанное поведение (раскрытие подменю), а не забытая ссылка.

### 5. Атрибуты ссылок (rel, target)
- [ ] Внешние ссылки: открываются в новой вкладке (`target="_blank"`) с `rel="noopener noreferrer"`.
- [ ] Внутренние ссылки: без `target="_blank"`, кроме ссылок на скачиваемые файлы (PDF и т.п.).
- [ ] `rel="nofollow"`/`sponsored` — только там, где это оправдано типом ссылки (партнёрская, реклама, платное размещение); обычные ссылки на соцсети в футере не должны нести лишний `rel`, если это не оправдано.

### 6. Sitemap и индексация
- [ ] `sitemap.xml`/`sitemap_index.xml` существует и отдаёт 200 (если отсутствует — зафиксируй как баг, не только как повод искать страницы вручную).
- [ ] Служебные/технические страницы, не предназначенные для показа в поиске (например, страницы пагинации блога `/blog/page/2/`, пустые архивные/tag-категории вроде `uncategorized`, авто-сгенерированные коллекции) — либо не существуют, либо имеют `noindex`.

### 7. Телефонные номера — консистентность и работоспособность свопа
- [ ] **На DEV:** ожидается один и тот же (оригинальный) номер сайт-вайд в `tel:`-ссылках — хедер, футер, CTA-блоки, Schema-разметка. **Исключение — контекстно оправданные персональные номера** (например, у каждого сотрудника на его личной странице указан свой прямой номер — это нормально, не баг). Любое ДРУГОЕ расхождение, не объяснимое контекстом страницы, — баг.
- [ ] **На LIVE:** ожидается работающий своп номера для трекинга звонков (CallRail и подобные). Агент проверяет **только техническую работоспособность механизма**, а не то, какой конкретно номер «правильный» для какой страницы:
  - На странице отображается валидный по формату номер (US-формат, см. `content-checks`).
  - Если в консоли/сети виден скрипт свопа (например `callrail.com`) — он загружается и выполняется без JS-ошибок, связанный сетевой запрос не возвращает 4xx/5xx.
  - **Сверка конкретных значений номеров (какой номер должен быть на какой странице) — НЕ входит в стандартную проверку.** Это требует внешней справочной таблицы номеров, которую агент не запрашивает и не поддерживает по умолчанию. Если пользователь явно передал такую таблицу в `Сайты.txt` (`Комментарии:`) для конкретной задачи — сверяй по ней; если не передал — не проверяй соответствие конкретных цифр, только техническую работоспособность (см. выше).
  - Единственное исключение, где расхождение номера на LIVE остаётся багом и без внешней таблицы: явно переданная в `Правки:`/`Комментарии:` замена («номер X заменить на Y по всему сайту»), а старый номер X всё ещё где-то встречается.
- [ ] Если окружение в `Сайты.txt` не указано — не утверждай ни бага, ни его отсутствия по факту разных номеров: зафиксируй сам факт расхождения в «Рекомендации для ручной проверки» с пометкой, что легитимность (своп на LIVE vs ошибка на DEV) не может быть подтверждена без пометки окружения.

### 8. Мультиязычность — метод декларирования (если у сайта больше одной языковой версии)
Здесь проверяется не сам перевод (это `content-checks`), а то, ПРАВИЛЬНО ЛИ сайт объявляет поисковикам/браузеру связь между языковыми версиями:
- [ ] `<html lang="...">` соответствует фактическому языку страницы (`en`, `es` и т.п.), а не захардкожен одинаково на всех версиях.
- [ ] hreflang в `<head>`: `<link rel="alternate" hreflang="...">` — присутствуют для каждой языковой версии (и `x-default`, если используется). Связи двусторонние: каждая версия ссылается и на себя, и на альтернативы (не только одна сторона на другую). Каждый URL в hreflang должен реально существовать и отдавать 200 (не 404, не редирект, не ссылка на homepage вместо конкретной переведённой страницы).
- [ ] Sitemap: проверь `sitemap.xml`/`sitemap_index.xml` на hreflang-аннотации внутри записей (`<xhtml:link rel="alternate" hreflang="...">`) — некоторые сайты декларируют мультиязычность через sitemap вместо (или вместе с) тегов в `<head>`.
- [ ] HTTP-заголовок `Content-Language` — best-effort: если видно заголовки ответа (`playwright-cli request <id>` или аналог), проверь, используется ли он.
- **Явно укажи в отчёте, какой метод(ы) реально реализован на сайте** — hreflang в `<head>` / hreflang в sitemap / заголовок `Content-Language` / комбинация / не реализовано вовсе. Это отдельный технический факт, важный сам по себе, а не просто "мультиязычность работает/не работает".

### 9. Schema (JSON-LD) / SEO
- [ ] Разметка оформлена как JSON-LD (`<script type="application/ld+json">`), не microdata/RDFa. Извлеки все блоки через `playwright-cli eval`: `JSON.stringify([...document.querySelectorAll('script[type="application/ld+json"]')].map(s => s.textContent))` — распарси и проверь каждый.
- [ ] Тип разметки соответствует типу страницы: LocalBusiness (или LegalService для юридических сайтов) / Organization — HP и сквозная информация о компании; Product — сервисные страницы с отзывами/рейтингом; Article/BlogPosting — блоговые страницы; BreadcrumbList — все страницы кроме HP; ProfilePage — персональные страницы команды; FAQPage — страницы с видимым блоком вопрос-ответ.
- [ ] Один и тот же тип разметки не дублируется на странице (два блока `LocalBusiness` и т.п. — баг).
- [ ] **Обязательные поля по типу** (минимум, без которого Google не примет тип как валидный для rich results):
  - **LocalBusiness/LegalService:** `name`, `address` (полный `PostalAddress`: `streetAddress`, `addressLocality`, `addressRegion`, `postalCode`), `telephone`, `url`. Если бизнес мультилокационный — все локации с телефонами в одной разметке, не в нескольких раздельных блоках.
  - **Organization:** `name`, `url`, `logo`, `sameAs` (соцсети из футера).
  - **Product** (если используется для рейтинга/отзывов): `name` + минимум одно из `aggregateRating`/`review`; если есть `offers` — обязательны `price`, `priceCurrency`, `availability`.
  - **Article/BlogPosting:** `headline`, `image`, `datePublished`; желательно `dateModified`, `author.name`, `publisher.name`+`logo`.
  - **BreadcrumbList:** `itemListElement` — каждый элемент с `position`, `name`, `item` (кроме последнего/текущего уровня).
  - **ProfilePage:** компактно — базовые обязательные поля своего типа + `sameAs` (без лишнего, см. ниже).
  - **FAQPage:** `mainEntity[]`, каждый — `Question.name` + `acceptedAnswer.text`; количество вопросов в разметке должно совпадать с количеством видимых на странице (не больше и не меньше).
- [ ] Данные в разметке релевантны проекту и совпадают с тем, что реально на странице (адрес, телефон, счётчик отзывов/постов) — не хардкод из шаблона или чужого проекта.
- [ ] Разметка компактна: содержит обязательные (+ по возможности рекомендованные Google) поля своего типа, не тянет в себя лишние несвязанные данные (например, ProfilePage/Article не должны включать всё подряд).
- Готового валидатора (Google Rich Results Test) у агента нет — проверка ведётся вручную по списку выше. Если найдены системные проблемы разметки (много типов/страниц затронуто) — не пытайся починить структуру сам, зафиксируй в отчёте с рекомендацией завести отдельный таск на разметку.

### 10. ADA (базовая доступность)

Это исчерпывающий список того, что входит в «базовую проверку ADA» — выполняй все пункты на каждой проверенной странице, не сокращай список до «семантика в порядке» без остальных пунктов. Если пункт технически не удалось проверить (например, инструмент недоступен) — явно скажи об этом в отчёте, не пропускай молча.

- [ ] **Контрастность (считается, не оценивается на глаз).** Через `playwright-cli eval` возьми computed `color` и `background-color` для: основного текста параграфов, текста в CTA-кнопках, текста в навигации. Посчитай контраст по формуле WCAG (относительная яркость по каждому каналу sRGB → luminance → contrast ratio). Порог: обычный текст ≥ 4.5:1, крупный текст/элементы UI (≥18pt или ≥14pt bold) ≥ 3:1. Ниже порога — баг с указанием фактического ratio.
  ```js
  // пример: получить computed-цвета для выборки текстовых узлов
  [...document.querySelectorAll('p, button, nav a')].slice(0,20).map(el => {
    const s = getComputedStyle(el);
    return { text: el.textContent.trim().slice(0,30), color: s.color, bg: s.backgroundColor };
  })
  ```
- [ ] Семантические теги `header`, `main`, `footer`, `nav` присутствуют (проверка через snapshot/eval на наличие тегов).
- [ ] У каждого поля формы есть непустой `<label>` (связанный через `for`/`id`) либо `aria-label`/`aria-labelledby` — проверка через `eval` по всем `input`/`select`/`textarea`.
- [ ] Интерактивные элементы без видимого текста (иконки-кнопки, например бургер-меню, соцсети в футере) имеют `aria-label` — проверка через `eval` по `button`/`a` без `textContent`.
- [ ] **Клавиатурная навигация — конкретный тест:** через `playwright-cli key Tab` (повторить ~15–20 раз подряд от начала страницы) проверяй после каждого нажатия `document.activeElement` (через `eval`). Баг, если: фокус теряется (уходит на `body`/`null`), зацикливается без возможности пройти дальше по странице, либо перескакивает через видимые интерактивные элементы (пропускает пункты меню/кнопки).
- [ ] Аккордеоны, дропдауны и слайдеры открываются/переключаются с клавиатуры (Tab до элемента + Enter/Space) и не создают "клавиатурную ловушку" внутри себя (см. тест выше).
- [ ] **Focus-индикатор — конкретный тест:** для выборки интерактивных элементов (2–3 пункта меню, кнопка отправки формы, поле ввода) вызови `el.focus()` через `eval`, затем прочитай `getComputedStyle(el)` на `outlineStyle`/`outlineWidth`/`boxShadow`. Если `outline` `none`/`0px` и нет альтернативного видимого выделения (box-shadow, изменение border/background) — баг.
- [ ] На мобилке (WebKit) обычный текст, похожий на номер телефона, но не являющийся кликабельным CTA (например, часть адреса, ID, цена) — не превращается iOS в непреднамеренную `tel:`-ссылку. Если такие ложные автоссылки есть — либо должен стоять `<meta name="format-detection" content="telephone=no">` с ручной разметкой нужных номеров, либо разметка должна быть точечной.
- Усиленный ADA-аудит (полный WAVE/axe-прогон, ручное тестирование скринридером) — за пределами базовой проверки, делает человек отдельно; если он нужен — укажи это в «Рекомендации для ручной проверки», не пытайся заменить его перечисленными выше пунктами.

## Функциональный тест форм и калькуляторов (сабмит)
Полная процедура описана в CLAUDE.md, Шаг 3.1 (карта обязательности полей и поиск противоречий, граничные значения по всем полям, максимум 2–3 сабмита на шаблон, тестовые данные, рекомендация проверить админку/почту после сабмита) — используй её как есть, не дублируй логику здесь.

## Доп. информация
- В агентстве используются свопы номеров (подмена телефона для трекинга звонков) — они встречаются **только на LIVE** (и, соответственно, могут отличаться от Figma-макета). На **DEV** свопов не бывает — там ожидается один и тот же оригинальный номер клиента (кроме контекстно оправданных исключений, см. раздел 7).
- **Какой конкретно номер должен быть на какой странице — вне компетенции агента по умолчанию.** Это либо ответственность пользователя (сверка со своим справочником), либо трекинг-специалиста — агент не хранит и не запрашивает справочник номеров сам, только если он явно передан в конкретной задаче. Стандартная проверка ограничена технической работоспособностью свопа (см. раздел 7).
