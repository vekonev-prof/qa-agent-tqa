# Технические проверки

Ты проверяешь техническое качество страницы сайта.

## Чек-лист

### 1. Консоль браузера
- [ ] Собери JS-ошибки: `playwright-cli console`.
- [ ] **Не пиши в отчёт вообще (ни в «Баги», ни в «Рекомендации») ошибки от сторонней телеметрии/аналитики third-party сервисов** (например, `nitropack`, CDN-оптимизаторы, любые "beacon"/"health check"-запросы чужих плагинов и виджетов), если ошибка (а) не относится к собственным ресурсам/скриптам сайта и (б) не влияет на видимую функциональность. Особенно 403 на таких запросах — это почти всегда автоматизированный браузер (Playwright) блокируется чужой телеметрией по признакам бота, а не то, что увидит реальный пользователь. Это шум, а не находка — просто молча пропусти, не нужно даже упоминать, что заметил и отфильтровал.
- [ ] Ошибки от собственных скриптов/ресурсов сайта — зафиксируй в отчёте, только если ошибки есть.

### 2. Сетевые запросы
- [ ] Собери запросы: `playwright-cli requests`.
- [ ] Отфильтруй запросы со статусом 404.
- [ ] Для каждого битого ресурса укажи: URL, тип (картинка/скрипт/стиль/шрифт), страницу, анкор (если применимо).

### 3. HTTP-статусы страниц
- [ ] Нет внутренних 3xx-редиректов (в т.ч. из-за отсутствия/наличия завершающего слэша в URL).
- [ ] Нет 4xx на страницах, которые должны быть доступны.

### 4. Ссылки и перелинковка
- [ ] Нет пустых (`href="#"`, `href=""`) или явно битых ссылок — кроме случаев, когда клик обрабатывается через JS (проверь, что обработчик реально есть, а не просто мёртвый якорь).
- [ ] tel:-ссылки в правильном формате (`tel:+1XXXXXXXXXX`).
- [ ] Списочные/карточные секции (локации, услуги, сотрудники и т.п.) ведут на существующие страницы там, где такие страницы на сайте уже есть — не должно быть карточки без ссылки, если целевая страница существует. Сверяй по уже известному списку страниц (sitemap/навигация из Шага 1), не открывай специально каждую потенциальную целевую страницу ради этой проверки.
- [ ] Ссылка ведёт на **правильный** соответствующий объект (например: карточка сотрудника ведёт на его собственную страницу, а не на страницу другого сотрудника) — но проверяй это **дешёвой эвристикой прямо по snapshot** (сверь текст карточки/имя с текстом ссылки или её `href`, если там читается slug/имя), не открывая специально целевую страницу ради этой проверки. Если по эвристике похоже на нестыковку — вот тогда можно перейти и подтвердить; если ничего не смущает — не открывай.
- [ ] Хабовые/родительские пункты меню без прямой ссылки — только если это осознанное поведение (раскрытие подменю), а не забытая ссылка.

### 5. Атрибуты ссылок (rel, target)
- [ ] Внешние ссылки: открываются в новой вкладке (`target="_blank"`) с `rel="noopener noreferrer"`.
- [ ] Внутренние ссылки: без `target="_blank"`, кроме ссылок на скачиваемые файлы (PDF и т.п.).
- [ ] `rel="nofollow"`/`sponsored` — только на ссылках одной из трёх категорий: партнёрская, реклама, платное размещение. На всех остальных внешних ссылках (в т.ч. обычные соцсети в футере), не подпадающих ни под одну из этих трёх категорий, — лишний `rel` не нужен, это баг.

### 6. Sitemap и индексация
- [ ] `sitemap.xml`/`sitemap_index.xml` существует и отдаёт 200 (если отсутствует — зафиксируй как баг, не только как повод искать страницы вручную).
- [ ] Служебные/технические страницы, не предназначенные для показа в поиске (например, страницы пагинации блога `/blog/page/2/`, пустые архивные/tag-категории вроде `uncategorized`, авто-сгенерированные коллекции) — либо не существуют, либо имеют `noindex`.
- [ ] **PPC-лендинги** (страницы, явно перечисленные в блоке `Лендинги:` файла `Сайты.txt` — см. раздел 7 ниже, «Что считать лендингом») — должны иметь `noindex`. Они не предназначены для органического поиска; отсутствие `noindex` на такой странице — баг.

### 7. Телефонные номера — консистентность
**Это проверка только отображаемого контента.** Техническую работоспособность самого механизма свопа (скрипт/сеть/консоль) и сверку с оригинальными/конкретными номерами проверяет отдельный опциональный скилл `callrail-checks` — не дублируй эту логику здесь, она стоит дороже и не нужна по умолчанию на каждой странице.

**Что считать лендингом:** только страницы, явно перечисленные в блоке `Лендинги:` файла `Сайты.txt` (см. CLAUDE.md). Не определяй тип страницы по виду URL самостоятельно (`/ppc-...`, `utm_*` и т.п. могут просто совпасть по названию) — если страницы нет в `Лендинги:`, применяй к ней обычную логику основного сайта, даже если она похожа на рекламную. (Для телефонных номеров лендинги и основной сайт ведут себя одинаково — деление ниже нужно только для DEV vs LIVE, не для лендинг vs не-лендинг.)

- [ ] **На DEV** (любые страницы, включая лендинги): ожидается один и тот же (оригинальный) номер сайт-вайд в `tel:`-ссылках — хедер, футер, CTA-блоки, Schema-разметка. **Исключение — контекстно оправданные персональные номера** (например, у каждого сотрудника на его личной странице указан свой прямой номер — это нормально, не баг). Любое ДРУГОЕ расхождение, не объяснимое контекстом страницы, — баг.

- [ ] **На LIVE** (любые страницы, включая лендинги — агентство практикует свопы и на лендингах тоже, не только на основном сайте): ожидается динамический своп для трекинга звонков (CallRail и подобные) — на странице должен отображаться валидный по формату номер (US-формат, см. `content-checks`). Дальше не копай: техническую работоспособность самого свопа и сверку конкретных значений (какой номер закреплён за какой страницей/кампанией) — только через `callrail-checks`, если он вызван и передан справочник.

- [ ] Единственное исключение, где расхождение номера остаётся багом и без внешней таблицы (на любом типе страниц): явно переданная в `Правки:`/`Комментарии:` замена («номер X заменить на Y по всему сайту»), а старый номер X всё ещё где-то встречается.
- [ ] Если окружение в `Сайты.txt` не указано — не утверждай ни бага, ни его отсутствия по факту разных номеров: зафиксируй сам факт расхождения в «Рекомендации для ручной проверки» с пометкой, что легитимность не может быть подтверждена без пометки окружения.
- [ ] На мобилке (WebKit) обычный текст, похожий на номер телефона, но не являющийся кликабельным CTA (например, часть адреса, ID, цена) — не превращается iOS в непреднамеренную `tel:`-ссылку. Если такие ложные автоссылки есть — исправление: либо `<meta name="format-detection" content="telephone=no">` в `<head>` (отключает автоопределение сайт-вайд, реальные CTA-номера при этом должны быть явно обёрнуты в `<a href="tel:...">`, чтобы остаться кликабельными), либо (если `format-detection` не используется) сами CTA-номера должны быть явно обёрнуты в `<a href="tel:...">`, а не отображаться голым текстом, полагаясь на автоопределение браузера.

### 8. Мультиязычность — метод декларирования (если у сайта больше одной языковой версии)
Здесь проверяется не сам перевод (это `content-checks`), а то, ПРАВИЛЬНО ЛИ сайт объявляет поисковикам/браузеру связь между языковыми версиями. Проверяй только на страницах из своей обычной выборки (Шаг 1) — не обходи весь сайт ради этого, для site-wide аудита есть отдельные краулер-инструменты (Screaming Frog и подобные), агент делает точечную, а не исчерпывающую проверку.

**Проверь все три метода на каждой из проверяемых страниц, не только один — и явно укажи в отчёте, какие из них реально присутствуют, а какие отсутствуют** (не только общий вывод "мультиязычность работает"):
- [ ] `<html lang="...">` — соответствует фактическому языку страницы (`en`, `es` и т.п.), а не захардкожен одинаково на всех версиях.
- [ ] hreflang в `<head>`: `<link rel="alternate" hreflang="...">` — присутствуют для каждой языковой версии (и `x-default`, если используется). Связи двусторонние: каждая версия ссылается и на себя, и на альтернативы. Проверяй по разметке (`eval`), без дополнительных переходов. **Переходить по каждому hreflang-URL и проверять, что он отдаёт 200 — не по умолчанию**; делай это точечно только там, где уже есть основание подозревать проблему (например, `visual-checks` нашёл непереведённый контент на этой странице).
- [ ] hreflang-аннотации в **sitemap** (`<xhtml:link rel="alternate" hreflang="...">` внутри записей `sitemap.xml`/`sitemap_index.xml`) — некоторые сайты декларируют мультиязычность через sitemap вместо (или вместе с) тегов в `<head>`. Проверяй обязательно, не пропускай как необязательное.
- [ ] HTTP-заголовок `Content-Language` — проверь через доступный способ (например, `playwright-cli request <id>`, если показывает заголовки ответа). Обязательный пункт, а не «если удобно» — если технически не можешь посмотреть заголовки конкретно в этом прогоне, так и напиши в отчёте, не пропускай молча.
- **Итог по каждой странице:** явно перечисли, какой метод(ы) присутствует, какой отсутствует (например: «hreflang в `<head>` есть и корректен; hreflang в sitemap отсутствует; `Content-Language` не проверен — заголовки недоступны в этом прогоне»).

### 9. Schema (JSON-LD) / SEO
- [ ] Разметка оформлена как JSON-LD (`<script type="application/ld+json">`), не microdata/RDFa. Извлеки все блоки через `playwright-cli eval`: `JSON.stringify([...document.querySelectorAll('script[type="application/ld+json"]')].map(s => s.textContent))` — распарси и проверь каждый.
- [ ] Тип разметки соответствует типу страницы: LocalBusiness (или LegalService для юридических сайтов) / Organization — HP и сквозная информация о компании; Product — сервисные страницы с отзывами/рейтингом; Article/BlogPosting — блоговые страницы; BreadcrumbList — все страницы кроме HP; ProfilePage — персональные страницы команды; FAQPage — страницы с видимым блоком вопрос-ответ.
- [ ] Один и тот же тип разметки не дублируется на странице (два блока `LocalBusiness` и т.п. — баг).
- [ ] **Обязательные поля по типу** (минимум, без которого Google не примет тип как валидный для rich results):
  - **LocalBusiness/LegalService:** `name`, `address` (полный `PostalAddress`: `streetAddress`, `addressLocality`, `addressRegion`, `postalCode`), `telephone`, `url`. Если бизнес мультилокационный — все локации с телефонами в одной разметке, не в нескольких раздельных блоках.
  - **Organization:** `name`, `url`, `logo`, `sameAs` (соцсети из футера).
  - **Product** (если используется для рейтинга/отзывов): `name` + минимум одно из `aggregateRating`/`review`; если есть `offers` — обязательны `price`, `priceCurrency`, `availability`.
  - **Article/BlogPosting:** `headline`, `image`, `datePublished`; желательно `dateModified`, `author.name`, `publisher.name`+`logo`.
  - **BreadcrumbList:** `itemListElement` — каждый элемент с `position`, `name`, `item` (кроме последнего/текущего уровня).
  - **ProfilePage:** компактно — базовые обязательные поля своего типа + `sameAs` (без лишнего, см. ниже).
  - **FAQPage:** `mainEntity[]`, каждый — `Question.name` + `acceptedAnswer.text`; количество вопросов в разметке должно совпадать с количеством видимых на странице (не больше и не меньше).
- [ ] Данные в разметке релевантны проекту и совпадают с тем, что реально на странице (адрес, телефон, счётчик отзывов/постов) — не хардкод из шаблона или чужого проекта.
- [ ] Разметка компактна: содержит обязательные (+ по возможности рекомендованные Google) поля своего типа, не тянет в себя лишние несвязанные данные (например, ProfilePage/Article не должны включать всё подряд).
- Готового валидатора (Google Rich Results Test) у агента нет — проверка ведётся вручную по списку выше. Если найдены системные проблемы разметки (много типов/страниц затронуто) — не пытайся починить структуру сам, зафиксируй в отчёте с рекомендацией завести отдельный таск на разметку.
- **Асинхронно подгружаемая разметка — не спеши фиксировать «разметки нет/не совпадает» ни для какого типа.** Любой тип JSON-LD (не только `Product` с `aggregateRating`/`review` — так же может касаться `Article`, `FAQPage`, `BreadcrumbList` и любого другого) может генерироваться или обновляться JS уже ПОСЛЕ первичной отрисовки — например, синхронно с виджетом, который подгружается отдельно (лениво/по скроллу/асинхронным запросом: отзывы, счётчики, динамический FAQ и т.п.). Поэтому **извлекай JSON-LD последним шагом технической проверки страницы** — после того как `visual-checks`/`content-checks` уже провзаимодействовали со страницей и прокрутили её (это уже соответствует порядку вызова Skills из Шага 3 в CLAUDE.md, где `technical-checks` идёт последним). Если на странице визуально виден ещё не подгрузившийся блок, от которого разметка может зависеть — подожди его отрисовки и только тогда делай финальное извлечение. Фиксируй баг только если разметка всё ещё отсутствует/не совпадает после того, как связанный контент точно отрисовался.

## Функциональный тест форм и калькуляторов (сабмит)
Полная процедура описана в CLAUDE.md, Шаг 3.1 (карта обязательности полей и поиск противоречий, граничные значения по всем полям, максимум 2–3 сабмита на шаблон, тестовые данные, рекомендация проверить админку/почту после сабмита) — используй её как есть, не дублируй логику здесь.

## Доп. информация
- В агентстве используются свопы номеров (подмена телефона для трекинга звонков) — они встречаются **только на LIVE**, причём как на основном сайте, так и на PPC-лендингах (агентство практикует свопы и там). На **DEV** (и на сайте, и на лендингах) свопов не бывает вовсе — там ожидается один и тот же оригинальный номер клиента (кроме контекстно оправданных исключений, см. раздел 7).
- **Какой конкретно номер должен быть на какой странице, и работает ли сам механизм свопа технически — вне компетенции этого скилла по умолчанию.** Раздел 7 здесь проверяет только отображаемый контент (формат, консистентность). Техническая работоспособность свопа и сверка с оригинальными номерами — отдельный опциональный скилл `callrail-checks`, вызывается только по запросу.
