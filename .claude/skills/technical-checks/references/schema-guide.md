# Гайд по Schema (JSON-LD) — внутренний стандарт агентства

Источник: внутренний гайд агентства (автор — Владислав Конев, QA), с правками по датам. Это эталон для проверки §9 `technical-checks` — точнее моей (агента) более ранней реконструкции по общему знанию Google-требований. При расхождении с §9 SKILL.md — верен этот файл, SKILL.md стоит поправить.

## Общие принципы (применимы ко всем типам)

1. **Ворнинги от Rich-results** — красные и жёлтые нужно фиксить (у нас нет доступа к самому валидатору Google Rich Results Test — см. §9 SKILL.md, работаем по списку полей ниже вручную).
2. **Дублирование типа разметки в валидаторе обычно НЕ означает дублирование в исходном коде** — частая причина: сам валидатор так интерпретирует структуру. Если увидел дубль — зафиксируй как находку как есть, не пытайся сам определить, будет ли это видно после рендера.
3. **Placeholder-URL вида `example.com` в значениях ключей — не баг на этапе Интермед QA** (наш обычный сценарий: DEV-сайт до публичного запуска). Такие URL часто динамически подставляются на реальные при лонче, а до этого момента по ним нельзя пройти и проверить разметку (у поисковых роботов нет доступа к непубличному сайту). Не путай это с реальным багом (случайно оставленным чужим доменом в проекте, который НЕ является служебным placeholder'ом типа `example.com`/`test.com`).
4. **Три фазы проверки разметки в общей практике агентства** — наш агент покрывает только первую:
   - **Интермед QA (наш скоуп)** — разметка проверяется в ОТРЕНДЕРЕННОМ коде (не в исходном!), вручную по списку обязательных/рекомендованных полей ниже — реального валидатора Rich-Results у агента нет.
   - День лонча — по реальному URL в Rich Results (вне скоупа агента, ручной процесс после публикации).
   - Через месяц после лонча — по URL Rich Results + `schema.org` валидатор, ради проверки отсутствия дублей (вне скоупа агента).

## LocalBusiness (он же LegalService, FinancialService и другие подтипы)

**Обязательны только `name` и `address`** (полный `PostalAddress`). Всё остальное — рекомендательного характера, не билось-найдено-баг само по себе, если отсутствует.

Важно: подтип должен отражать род деятельности бизнеса — для юристов обязателен `LegalService`, не голый `LocalBusiness`.

Пример (одна локация):
```json
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "@id": "https://test.com/",
  "url": "https://test.com/",
  "logo": "...",
  "name": "Brackenbox",
  "image": ["..."],
  "address": {
    "@type": "PostalAddress",
    "streetAddress": "2300 W 167th St",
    "addressLocality": "Markham",
    "addressRegion": "IL",
    "postalCode": "60428",
    "addressCountry": "US"
  },
  "telephone": "+17083394100",
  "priceRange": "$",
  "geo": { "@type": "GeoCoordinates", "latitude": "41.589142", "longitude": "-87.6720712" },
  "sameAs": ["https://twitter.com/test", "https://www.linkedin.com/company/...", "https://www.facebook.com/..."],
  "review": [ /* см. раздел Review ниже */ ],
  "aggregateRating": { "@type": "AggregateRating", "ratingValue": 5, "reviewCount": 11 }
}
```

### LocalBusiness with department (мультилокационный бизнес)

Используется, когда у сайта несколько офисов/локаций. Структура: главный `LocalBusiness` (со своими name/url/priceRange/logo/image/telephone/sameAs/address/geo/openingHours/contactPoint) + массив `department`, где каждый элемент — тоже `LocalBusiness` (свой `@id`/name/url/priceRange/logo/image/telephone/sameAs/address/geo/openingHours/contactPoint) для конкретной локации. `review`/`aggregateRating` — на верхнем уровне, не на каждом department отдельно.

**`name`+`address` обязательны у каждого department так же, как у обычного одиночного LocalBusiness** — это не отдельное правило, а то же самое базовое требование, просто применённое к вложенному объекту того же типа. `address` у department обязан быть СВОИМ (разные локации физически не могут иметь один адрес). Само поле `name` обязательно в любом случае — но его конкретное значение (совпадает ли оно с материнской компанией дословно, или уточняется под конкретный офис) ничем не подтверждено сверх единственного примера ниже, где оба уровня называются одинаково («HagEstad Law Group, PLLC») — не утверждай здесь общее правило сверх этого одного наблюдения, просто сверяй `name` конкретного department с тем, что реально написано для этой локации на сайте.

## WebSite

Сообщает название сайта. **Обязательных полей нет формально**, но обычно есть `url`, `name`.

`potentialAction`/`SearchAction` — опционально, только если на сайте реально есть поиск. **Раньше в гайде была рекомендация «всегда добавлять SearchAction ради этого»; проверено — прямо в документации Google такого требования нет, эта рекомендация снята.**

Пример:
```json
{
  "@context": "https://schema.org",
  "@type": "WebSite",
  "url": "https://example.com",
  "name": "...",
  "potentialAction": {
    "@type": "SearchAction",
    "target": "https://example.com/search?q={search_term_string}",
    "query-input": "required name=search_term_string"
  }
}
```

## FAQPage — особый статус (обновлено после консультации с SEO-специалистами агентства, позже чем первая версия этого раздела)

Классический развёрнутый FAQ rich-сниппет Google убрал из поиска (официальный апдейт, "removing FAQ rich result", с 2026-07-01) — это было верно. Но **по консультации с SEO-специалистами агентства разметка всё ещё может влиять на отображение в SERP** (не тот же эффект, что раньше, но не нулевой) — поэтому финальная позиция другая, чем в первой версии этой заметки:

- **Если разметка ЕСТЬ на странице с видимым Q&A-блоком** — оставляем и проверяем как обычно: обязательные поля `mainEntity[].Question.name` + `.acceptedAnswer.text`; правило «один вопрос — один ответ» (иначе нужен тип `QAPage`); число вопросов в разметке = число видимых на странице.
- **Если разметки НЕТ** — это не баг, максимум рекомендация добавить (см. §9 SKILL.md — идёт в «Рекомендации», не в «Баги»).

## Breadcrumbs (`BreadcrumbList`)

Обязательные поля: `itemListElement[]`, каждый — `item`, `name`, `position`. Последний уровень крошек — желательно без ссылки (`item` не указан либо не ведёт на саму себя).

## BlogPosting (для блог-постов)

**Обязательных свойств формально не существует** — добавлять нужно те, что реально соответствуют контенту страницы. Практически важнее всего — `datePublished` и `dateModified`. Не требуется, чтобы эти две даты обязательно отличались друг от друга — но **даты в разметке и в видимом на странице контенте не должны расходиться** (это и есть главный проверяемый факт).

## ProfilePage (для авторов блог-постов)

Если у автора/клиента есть ссылки на соцсети — **обязательно** добавить через `sameAs` (прямая рекомендация Google — связывает деятельность клиента с сайтом). Обязательное поле: `mainEntity.name`.

Пример:
```json
{
  "@context": "https://schema.org",
  "@type": "ProfilePage",
  "mainEntity": { "@id": "#main-author", "@type": "Person", "name": "Marlo Smith" },
  "hasPart": [{
    "@type": "Article",
    "headline": "...",
    "url": "...",
    "datePublished": "...",
    "author": { "@id": "#main-author" }
  }]
}
```

## VideoObject (для видео)

Обязательные поля: `name`, `thumbnailUrl`, `uploadDate`.

## Product (для НЕ коммерческих сайтов — используется ради Review/AggregateRating)

Обязательные поля: `name`, `review`, `aggregateRating`.

**Важно про хардкод отзывов:** в идеале `review`/`aggregateRating` должны подтягиваться динамически (из виджета отзывов), но это часто просаживает производительность сайта — в практике агентства это **осознанно хардкодят**, и значения (например, количество отзывов) время от времени обновляют вручную. **Это не баг сам по себе** — хардкод отзывов ожидаем и допустим.

**Но это не значит, что любой хардкод — ок:** если содержимое хардкода явно относится к ДРУГОМУ проекту/бизнесу (не к тому, что сейчас проверяется — например, имя другой компании, отзыв про другой продукт/локацию, чужой бренд в `name`/`brand`/тексте отзыва) — это баг. Частая причина у нас: разработчики копируют разметку с другого проекта-донора и меняют данные, но что-то забывают заменить.

## Review и AggregateRating — отдельно

Официально по документации Google: если сайт использует виджет отзывов (например Elfsight) для отдельной секции, `Review`/`AggregateRating` **нельзя** размещать в разметке `LocalBusiness`/`Organization` — только в `Product`.

**Уточнено у SEO-специалистов агентства (перекрывает буквальное правило Google выше):** на практике агентства `Review`/`AggregateRating` размещают **в обеих** разметках — `LocalBusiness` и `Product` одновременно.

Отсутствие `Review`/`AggregateRating` в разметке страниц, где нет виджета отзывов (обычно privacy, contact-us, блоговые страницы) — **нормально, не баг**: секции отзывов там обычно и не должно быть по дизайну.

**Review — обязательные поля:** `author`, `itemReviewed` (только если отзыв не вложен в `LocalBusiness`/`Product` — если вложен, берётся `name` родителя), `reviewRating`, `reviewRating.ratingValue`.

**AggregateRating — обязательные поля:** `itemReviewed` (аналогично, если не вложена — иначе `name` родителя), `ratingCount`, `reviewCount`, `ratingValue`.

## Organization

Формируется Google автоматически на основе `LocalBusiness`. **Обязательных полей нет** — важно только убедиться, что она заполнена корректными/релевантными данными (см. общее правило релевантности в §9 SKILL.md).
