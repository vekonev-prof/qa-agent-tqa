# Сравнение с Figma-макетом

## Условие вызова
Только если одновременно: (1) для сайта/страницы передана ссылка на Figma в `Сайты.txt`, и (2) `visual-checks` уже нашёл конкретное подозрение на расхождение. Не вызывай для всех страниц подряд и не вызывай, если Figma-ссылка не передана.

## Входные параметры
- URL страницы, где найдена проблема.
- Ссылка на Figma-макет — конкретный frame/node, если он известен (например, отдельная ссылка на лендинг из блока `Лендинги:`), либо общая ссылка на файл/Homepage для основного сайта — в этом случае нужный узел находится по имени фрейма (см. Алгоритм, шаг 2).

## Алгоритм (сокращённый, только проблемная секция)
1. Извлеки file key (и node-id, если он есть в ссылке) из URL Figma.
2. **Если ссылка НЕ содержит node-id, относящийся именно к шаблону проверяемой страницы** (типичный случай для основного сайта — в `Сайты.txt` передана одна общая ссылка на файл/Homepage, а расхождение найдено, например, на сервисной странице) — найди нужный узел по имени: запроси у Figma MCP список страниц/фреймов файла (лёгкий вызов по метаданным, не по всему файлу с содержимым; если этот список уже запрашивался в этом же прогоне на Шаге 1 CLAUDE.md при определении шаблонов страниц — переиспользуй его, не запрашивай второй раз) и найди среди названий фрейм, соответствующий шаблону проверяемой страницы (агентство обычно называет фреймы осмысленно — «Service Page», «Practice Area Template», «Location Page» и т.п.). Используй node-id найденного фрейма дальше. **Если подходящий по названию фрейм не нашёлся** — зафиксируй в результате «нужный фрейм не опознан по имени в макете», не сравнивай наугад с первым попавшимся узлом.
3. **Сопоставь разрешение.** Расхождение, ради которого вызван этот скилл, найдено `visual-checks` на конкретном разрешении (десктоп/мобилка/планшет) — сравнивай именно с фреймом ЭТОГО разрешения, не с любым попавшимся. Макеты по разным разрешениям для одного шаблона обычно оформлены отдельными фреймами (например «Service Page — Desktop» / «Service Page — Mobile» / «Service Page — Tablet», либо разнесены по отдельным страницам файла «Desktop»/«Mobile»/«Tablet», внутри каждой — те же шаблоны) — используй то же название/список фреймов, чтобы найти версию под нужное разрешение.
   - **Если фрейма для нужного разрешения нет вообще** (частый случай — например, макет нарисован только для Homepage на десктопе и мобилке, а планшет не рисуют вовсе; или для конкретного шаблона есть десктоп, но нет мобилки) — **не придумывай и не экстраполируй недостающий макет**, не сравнивай с фреймом другого разрешения как с эквивалентом. Зафиксируй в результате «макет для [разрешение] не предоставлен» и для этого разрешения ориентируйся на общий внутренний стандарт чек-листа агентства (тот же, что используется, когда Figma вообще не передан — см. Readme.md, «Как агент понимает, что это расхождение», Стадия 1), а не на Figma.
   - Планшет в Figma отсутствует особенно часто (агентство не всегда его рисует) — это нормально, не сигнал проблемы с самим макетом. Открытие и визуальная проверка планшета по внутреннему стандарту (см. CLAUDE.md, Шаг 2) при этом всё равно происходит как обычно — отсутствие Figma-эталона отменяет только возможность эскалации до `figma-compare` на этом разрешении, не саму проверку.
4. Запроси у Figma MCP данные только по нужному узлу/фрейму, не по всему файлу — посмотри в описании доступных инструментов MCP, какой из них принимает node-id и ограничивает выдачу конкретным узлом, и используй его вместо запроса всего файла.
5. Если для сравнения нужен snapshot сайта — используй `playwright-cli snapshot --depth=4`, не полный snapshot.
6. Сравнивай структуру и ключевые визуальные параметры (наличие секции, порядок, число колонок, цвет) — НЕ pixel-perfect, и только для секции с подозрением на баг.
7. Если размеры элемента в CLI отличаются от Figma больше чем на 20% — сделай скриншот только этого элемента (не всей страницы, сохрани в `{домен}/{прогон}/screenshots/`) и передай в Vision вместе с соответствующим фрагментом макета для финального решения.

## Что не делать
- Не загружай Figma-файл целиком.
- Не сравнивай страницы/секции, где `visual-checks` не нашёл проблем.
- Не сравнивай с фреймом не того разрешения и не выдумывай недостающий макет (десктоп/мобилка/планшет) — см. Алгоритм, шаг 3.

## Формат результата
- **Статус:** «Макет загружен, расхождений нет» / «Макет загружен, найдены расхождения» / «Макет не загружен (ошибка)» / «Макет для этого разрешения не предоставлен — сверено по внутреннему стандарту».
- Если есть расхождения — по каждой: страница, разрешение, секция, краткое описание проблемы.

**Пример:**
```
Сравнение с Figma: макет загружен.
Расхождения:
- /about, секция «Преимущества»: в макете 3 колонки, на сайте — 4.
- /contact: цвет CTA-кнопки на сайте красный, в макете — синий.
```
