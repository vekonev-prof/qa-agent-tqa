# Сверка DEV с реальным эталонным сайтом (вместо Figma)

## Когда вызывать
Только если строка сайта в `Сайты.txt` указывает `ORIGINAL:<url>` вместо ссылки на Figma во втором поле. Если указана обычная Figma-ссылка — этот скилл не применим, используй `figma-compare`. Оба варианта взаимоисключающие для каждой строки отдельно — сайта и лендинга (у сайта может быть `ORIGINAL:`, а у его лендинга — Figma, и наоборот; в одной строке — только одно из двух).

**Лендинги (блок `Лендинги:`):** сверка с эталоном по умолчанию НЕ выполняется. Она выполняется только если для конкретного лендинга в `Сайты.txt` через `|` указан эталон `ORIGINAL:<url>` — тогда сверяй только структуру, текст, изображения, NAP и форму; Schema на лендингах не сверяется.

**Кто выполняет:** одиночный агент — сам; при параллельном прогоне — `tqa-page-agent` по своим страницам (суффикс сессий и `{прогон}` — из промпта оркестратора).

## Экономия токенов — три правила, снижающие стоимость вдвое

Сверка с отдельным реальным сайтом по своей природе дороже, чем без неё — по факту это удвоение браузерных сессий на каждую проверяемую страницу (DEV + эталон). Три правила ниже держат эту стоимость под контролем:

1. **Контент/структуру/Schema/телефон сверяй ОДИН раз, на десктопе.** Подавляющее большинство находок про верность переноса (пропавшие секции, изменённый текст, неверный NAP, неверный тип/поля Schema) видны уже на одном разрешении. Не открывай эталонный сайт на мобилке/планшете по умолчанию для этой части.
2. **Эталонный сайт на мобилке/планшете открывай ТОЛЬКО если `visual-checks` уже нашёл конкретное визуальное расхождение на DEV именно на этом разрешении** — то же условие, что у `figma-compare` («только если найдено расхождение»). Так отличаются «регрессия переноса» от «унаследовано с оригинала, воспроизведено 1:1» — но открывать эталон на этом разрешении имеет смысл только когда есть что подтверждать/опровергать, не заранее «на всякий случай».
3. **Не пиксель-в-пиксель.** Сравнивай структуру, порядок секций, ключевые факты (текст, NAP, тип Schema, набор полей формы) через `snapshot --depth=4`/`find` — не через скриншот-диффинг всей страницы. Скриншот — только если решаешь зафиксировать конкретный визуальный баг (см. Шаг 4 CLAUDE.md).

Держи одну именованную сессию на каждое разрешение, на котором открываешь эталон, на весь прогон (`-s=orig-desktop-<суффикс>`, `-s=orig-mobile-<суффикс>`, `-s=orig-tablet-<суффикс>`; суффикс — из промпта оркестратора, для единственного агента `solo`, для оркестратора `orch`; `close` — с тем же именем) и переходи между страницами через `goto` внутри неё — не открывай (`open`) новую сессию на каждую страницу эталона.

## Соответствие страниц

По умолчанию — тот же URL-путь на обоих доменах (например `/services/cabinet-refacing` и там, и там). Если по этому пути на эталоне 404 — не спеши делать вывод о расхождении структуры URL:
1. Сначала попробуй очевидный вариант (добавить/убрать сегмент, например `/blogs/slug` вместо `/slug`, или наоборот).
2. Только если очевидный вариант тоже не сработал — поищи вручную по навигации/sitemap эталонного сайта страницу с тем же заголовком/темой.

Если после этого страница на эталоне не находится вовсе — это не баг DEV, а находка про сам эталонный сайт (например, статья не привязана к общей ленте/навигации там) — фиксируй в «Рекомендации для ручной проверки», не в основной список находок DEV.

## Что сравнивать
- **Структура секций** (порядок, количество, тип блоков) — `snapshot --depth=4` на обеих версиях.
- **Текст — не требуется дословное совпадение** (перенос обычно делают ИИ-агенты, которые пересказывают текст — это ожидаемо, не баг само по себе). Критерий — **сохранность фактов, не слов**:
  - **ОК:** переформулированный текст, другой порядок предложений/абзацев, сокращённые обороты — если все факты/утверждения оригинала при этом присутствуют.
  - **Баг (`[Visual]`, пропавший факт/секция — по умолчанию 🟥 как грубая контентная ошибка):** пропавший факт/утверждение/абзац/секция целиком; изменённое число, дата, название, характеристика услуги, гарантия (например, «работаем с 2010» превратилось в «работаем с 2015» без пометки в `Правки:`); прямое противоречие тому, что было в оригинале.
  - При сомнении — сверяй конкретные факты/цифры/названия построчно между версиями, а не общее «звучит похоже».
- **Изображения** — те же по смыслу картинки на месте (не «тот же файл побайтово» — платформа может переразмещать файлы под новыми именами, это не баг); отсутствующий блок с картинкой или неуместное (не по теме/географии) изображение — баг.
- **NAP (телефон/адрес)** — сверяется по правилам `technical-checks` §7, не дублируй логику здесь; в частности, если сравниваешь конкретные номера, § 7 требует брать номер эталона из сырого HTML (до выполнения JS), а не из отрисованного DOM.
- **Schema (JSON-LD)** — на лендингах из блока `Лендинги:` не сверяется вовсе (как и не проверяется по `technical-checks` §9). На остальных страницах: тип разметки и обязательные поля по `technical-checks` §9; дополнительно сверь, что тип/состав полей на DEV не хуже эталона (потерянный уровень `BreadcrumbList`, пропавший ожидаемый тип схемы — баг; более полная/богатая схема на DEV, чем на эталоне, — не баг сам по себе, а улучшение, не нужно фиксировать как расхождение с оригиналом — **но это не отменяет обычные правила дублей и релевантности данных** из `technical-checks` §9: лишние поля/блоки в DEV всё равно проверяй на дублирование и на релевантность данных странице, как на любой другой странице).
- **Формы** — набор полей и их обязательность относительно эталона (например другая маска, другой список опций в дропдауне, пропавшее поле) — это структурная сверка; сам функциональный сабмит-тест делает `form-submit-checks`, не дублируй его здесь.

## Скриншоты и вручную сохранённые снапшоты
DEV и эталонный сайт — это два РАЗНЫХ сайта, у каждого своя рабочая папка `projects/{домен}/{прогон}/` (см. CLAUDE.md, «Рабочая папка сайта») — не смешивай их файлы в одной папке, даже если сравниваются в рамках одной задачи. Используй одно и то же значение `{прогон}` для обеих папок (DEV и эталона) — это части одного и того же прогона.
- Скриншоты DEV — как обычно, `{домен-DEV}/{прогон}/screenshots/{страница}_bugs/...` (см. Шаг 4 CLAUDE.md).
- **Скриншоты эталонного сайта — в его СОБСТВЕННУЮ рабочую папку**, `projects/{домен-эталона}/{прогон}/screenshots/{страница}_bugs/...`.
- **В имени файла явно помечай версию** — `DEV_` или `ORIGINAL_` первым префиксом; у пар до/после дальше идёт `before_`/`after_`, затем разрешение и проблема (`DEV_before_{разрешение}_{проблема}.png`), например:
  - `{домен-DEV}/{прогон}/screenshots/estimate_bugs/DEV_tablet_h1-clipped.png`
  - `projects/{домен-эталона}/{прогон}/screenshots/estimate_bugs/ORIGINAL_tablet_h1-reference.png`

  Без этой пометки при нескольких скриншотах из разных прогонов сложно на глаз отличить, какой скриншот с какой версии сайта.
- **То же самое — для вручную сохранённых snapshot (`.yml`), если решаешь зафиксировать структуру страницы для дальнейшего сравнения, а не только держать её в контексте диалога.** Не клади оба снапшота плоско в корень проекта и не называй их сокращённо (`dev-...yml`, `orig-...yml`) вместо пути:
  - `{домен-DEV}/{прогон}/snapshots/DEV_estimate_desktop.yml`
  - `projects/{домен-эталона}/{прогон}/snapshots/ORIGINAL_estimate_desktop.yml`

## Отчёт
Сверка с оригиналом идёт в ту же строку формата отчёта (CLAUDE.md) — «Сравнение с Figma / сверка с оригиналом:» — с кратким статусом (сверено по N страницам, расхождений сверх перечисленных в списке находок не найдено / эталонный сайт недоступен — причина). Находки из этой сверки оформляются пунктами общего списка «Что нужно доделать» с тегом типа (`[Form]`/`[Technical]`/`[Visual]`/`[Interactive]`/`[SEO]`/`[Rel/Target]`/`[Schema]`, см. CLAUDE.md, «Формат отчёта») наравне со всем остальным — не создавай для них отдельный раздел.
