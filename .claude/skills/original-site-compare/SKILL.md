# Сверка DEV с реальным эталонным сайтом (вместо Figma)

Цель — найти то, что потерялось или исказилось при переносе сайта (перенос обычно делают ИИ-агенты, которые пересказывают текст): не перенесённые страницы, пропавшие секции и факты, изменённые числа, потерянные SEO-данные, поля формы, разметку. Сверка не про пиксели и не про «как красиво».

## Когда вызывать
Только если строка сайта в `Сайты.txt` указывает `ORIGINAL:<url>` вместо ссылки на Figma во втором поле. Если указана обычная Figma-ссылка — используй `figma-compare`. Варианты взаимоисключающие для каждой строки отдельно — сайта и лендинга (у сайта может быть `ORIGINAL:`, а у его лендинга — Figma, и наоборот; в одной строке — только одно из двух).

**Лендинги (блок `Лендинги:`):** сверка с эталоном по умолчанию НЕ выполняется. Она выполняется только если для конкретного лендинга через `|` указан эталон `ORIGINAL:<url>` — тогда сверяй структуру, текст, изображения, NAP и форму; Schema на лендингах не сверяется, URL-парность (шаг А) для лендинга не делается.

**Кто выполняет:**
- Шаг А (парность страниц, один раз на сайт) — одиночный агент сам, при параллельном прогоне — оркестратор (подагенты `tqa-page-agent` его пропускают, пока оркестратор явно не поручил).
- Шаги Б–Г — одиночный агент сам; при параллельном прогоне — `tqa-page-agent` по своим страницам (суффикс сессий и `{прогон}` — из промпта оркестратора).

## Инструменты (дешёвые; используй их, а не «в уме» и не чтение двух длинных snapshot)
| Инструмент | Что делает |
|---|---|
| `node .claude/tools/compare-urls.js <dev-sitemap> <orig-sitemap> [--dev-user login:pass] [--orig-user login:pass] [--check-dev]` | Без браузера сравнивает списки URL двух sitemap (индексы обходятся): какие пути есть ТОЛЬКО на эталоне, ТОЛЬКО на DEV, сколько общих. `--check-dev` (нужен https-адрес DEV) для путей «только на эталоне» делает HEAD-запрос на DEV: 200 / 301 / 404. |
| `playwright-cli --raw -s=<сессия> run-code --filename=.claude/tools/compare-fingerprint.js` | «Отпечаток» открытой страницы: title, description, H1–H4, секции с числом слов, числа/суммы/годы, телефоны и email, CTA-кнопки, картинки (alt), внутренние и внешние ссылки, трекинг-скрипты, типы и поля JSON-LD, формы (поля, `required`). Запускай после паузы ≥3 с (на LIVE-эталоне для номеров — ≥5–10 с и второе чтение, см. `technical-checks` §7). |
| `node .claude/tools/compare-diff.js <dev.json> <orig.json>` | Разница двух отпечатков: только расхождения, компактный JSON. С флагом `--responsive` сравнивает мобильный отпечаток DEV с десктопным отпечатком того же DEV. |

**Временные файлы.** Отпечатки сохраняй во временной папке ОС, не в `projects/`: `T=$(mktemp -d)`, файлы `$T/dev.json`, `$T/orig.json`, `$T/devm.json`. Сразу после `compare-diff.js` удаляй (`rm -rf "$T"`). На закрытом DEV — `state-load` в каждой новой сессии (см. CLAUDE.md, Шаг 2); для `compare-urls.js` на закрытом DEV передай `--dev-user` (креды только в аргументе, в отчёт не пиши).

Скрипты ничего не оценивают: они показывают, где версии различаются «по форме». Решение «баг / не баг» и серьёзность — за тобой по разделам «Что не является находкой» и «Серьёзность» ниже.

## Экономия токенов
1. **Контент, структуру, Schema и NAP сверяй один раз на десктопе.** Большинство ошибок переноса видно на одном разрешении.
2. **Эталон на мобилке/планшете открывай только по триггеру** (шаг В): либо `visual-checks` уже нашёл конкретное расхождение на DEV именно на этом разрешении, либо отпечаток DEV на мобилке показал, что блоки/слова пропали относительно десктопа того же DEV (`--responsive`). Не «на всякий случай».
3. **Не пиксель-в-пиксель.** Скриншот — только для фиксации найденного визуального бага (Шаг 4 CLAUDE.md). Читать `snapshot` секции обоих сайтов нужно только там, где `compare-diff.js` показал расхождение и для решения не хватает текста.
4. **Одна именованная сессия на разрешение эталона на весь прогон:** `-s=orig-desktop-<суффикс>`, `-s=orig-mobile-<суффикс>`, `-s=orig-tablet-<суффикс>` (суффикс — из промпта оркестратора; единственный агент — `solo`; оркестратор — `orch`; `close` с тем же именем). Между страницами эталона переходи через `goto`, а не новым `open`.

## Шаг А. Полнота переноса: список страниц (один раз на сайт, без браузера)
1. Найди sitemap обоих сайтов (`sitemap.xml`, `sitemap_index.xml`; для DEV — то же, что в Шаге 1 CLAUDE.md). Запусти:
```bash
node .claude/tools/compare-urls.js <https://dev/sitemap.xml> <https://original/sitemap.xml> [--dev-user login:pass] [--check-dev]
```
2. Разбери результат **по спискам путей, а не по числам** — равное число URL на обеих сторонах не значит равный набор страниц.
3. Для каждого пути из `only_on_orig`:
   - Найди парный путь в `only_on_dev` (тот же слаг в другом сегменте: `/blog/x` ↔ `/blogs/x`, добавленный или убранный префикс языка/категории, смена окончания). Пара найдена — страница перенесена, но адрес изменился: **это не «страница отсутствует»**. Сверяй такую пару как обычную страницу, а смену адреса запиши в «Рекомендации для ручной проверки» одной строкой на все такие пары: «адрес изменился (старый → новый), перед запуском убедись, что со старого адреса настроен 301-редирект».
   - Пары нет. С `--check-dev`: `200` — страница на DEV есть, но не в sitemap → `[SEO]` 🟨 «страница есть на DEV, но не входит в sitemap»; `301/302` — редирект настроен, ничего не фиксируй; `404` — страница не перенесена. Без `--check-dev` (DEV не по https или недоступен для запросов) открой путь на DEV в браузере один раз, прежде чем писать вывод.
   - Страница действительно не перенесена → находка `[SEO]` 🟥 «страница эталона отсутствует на DEV». Одна запись на все такие страницы («массово», список путей); в «Доказательство» — путь, HTTP-статус DEV и то, что путь есть в sitemap эталона.
4. Пути из `only_on_dev` (нет на эталоне) находкой не считаются: новые страницы, сделанные при переносе, — норма. Кратко упомяни их количество и примеры в «Технических деталях».
5. Если у эталона нет sitemap — не обходи сайт ссылками (дорого): возьми список страниц из его навигации и футера, а в «Технических деталях» напиши «парность страниц проверена только по навигации, sitemap эталона отсутствует».
6. Мультиязычный sitemap: сравнивай и `/es/…`-пути; отсутствующие языковые версии — та же находка.

## Соответствие страниц для шагов Б–Г
По умолчанию — тот же путь на обоих доменах. Если на эталоне 404 или на DEV 404 — не делай вывод о расхождении структуры: (1) попробуй очевидный вариант пути (добавить/убрать сегмент, `/blogs/slug` вместо `/slug`); (2) для страниц из шага А используй найденные там пары; (3) только потом поищи вручную по навигации/sitemap страницу с тем же заголовком. Если страницы нет на эталоне вовсе — это не баг DEV, а наблюдение про сам эталон (например, статья не привязана к общей ленте на нём): «Рекомендации для ручной проверки».

## Шаг Б. Сверка страницы на десктопе (обязательный шаг для каждой выбранной страницы)
1. Открой DEV и эталон в сессиях `desktop-…` и `orig-desktop-…` на десктопном разрешении (1920×1080, Chrome). Дождись ≥3 с; при `images.lazy > 0` прокрути страницу вниз.
2. Сними отпечатки: `run-code --filename=.claude/tools/compare-fingerprint.js` в каждой сессии → `$T/dev.json`, `$T/orig.json`.
3. `node .claude/tools/compare-diff.js "$T/dev.json" "$T/orig.json"` — прочитай ключи `differences`:

| Ключ diff | Что означает | Что делать |
|---|---|---|
| `head` | различаются `title`, `description`, `ogTitle`, `ogDescription`, `ogImage`, `twitterCard`, наличие `canonical`, `lang`, число `hreflang` | Сравни смысл. Заглушка вместо описательного (`Home`, `Services`), пустое значение или пропавший тег — находка `[SEO]`. Перефразированный, но осмысленный текст и улучшение — нет. `robots` в `info` (noindex на DEV) — норма, не находка. |
| `headings` | H1–H4, которые есть только на одной стороне | Подбери парные заголовки по смыслу; перефразирование не находка. H1 заменён на заглушку или пропал — `[SEO]`; целый заголовок и его блок пропали — см. `sections`. |
| `sections` | `missing_on_dev` — секции эталона без пары по заголовку; `shorter` — секция на DEV короче ≥30% (по числу слов); `hidden_on_…` — секция в DOM, но скрыта; `order` — другой порядок; `only_dev` — лишние секции | `missing_on_dev`: докажи отсутствие (`find` по ключевому слову заголовка и по фрагменту текста, `snapshot --depth=4` того места) — заголовок мог быть переименован, а блок остаться. `shorter`: найди в секции, что именно пропало (шаг Г). |
| `numbers` | числа, суммы, проценты, годы, которые есть только на одной стороне | Самый быстрый признак изменённого или потерянного факта. По каждому найди контекст на обеих версиях: значение заменено или факт исчез. |
| `phones`, `emails` | телефоны (10 цифр) и адреса почты, которых нет на другой стороне | NAP — по `technical-checks` §7 (на LIVE-эталоне учти колл-трекинг: номер эталона бери из сырого HTML через `curl`, а не из отрисованного DOM). |
| `ctas` | тексты кнопок/CTA только на одной стороне | Пропавшая кнопка — находка `[Visual]`; переименованная по смыслу — нет. |
| `images` | число видимых/битых картинок, `alt` только на одной стороне | Сравнивай по смыслу (`alt`), не по файлам. Пропала картинка секции — находка; переименованный файл — нет. Битые AVIF в WebKit — ограничение инструмента (CLAUDE.md, «Обработка ошибок»). |
| `internalLinks`, `externalHosts` | ссылки только на одной стороне | Справка. Пропавшая ссылка на страницу услуги из меню/футера — находка `[Technical]`; смена адреса, найденная в шаге А, — нет. |
| `tracking` | GTM/GA/CallRail/Pixel и т.п. только на одной стороне | Находкой не считается: на DEV трекинг обычно отключён или другой. Только строка в «Рекомендации для ручной проверки». |
| `jsonld` | типы Schema и поля, которых нет на DEV/на эталоне | Потерян тип (`BreadcrumbList`, `FAQPage`, `Service`…) или поля — находка `[Schema]` (серьёзность — «Серьёзность»). На лендингах не сверяется. Более богатая разметка на DEV — не находка, но дубли блоков, чужие данные и нерелевантные поля всё равно проверяются по `technical-checks` §9. |
| `forms` | поля, `required`, тип поля только на одной стороне; форма есть только на одной стороне | Находка `[Form]`. Функциональный сабмит-тест — `form-submit-checks`, не дублируй его здесь. |

## Шаг В. Мобилка и планшет: только по триггеру
1. **Триггер 1 — `visual-checks` нашёл на DEV конкретное расхождение на этом разрешении** (секция сломана, блок пропал, порядок другой).
2. **Триггер 2 — дешёвая проверка «что пропало на мобилке» для каждой сверяемой страницы:** в уже открытой мобильной сессии DEV (после `page-audit.js`) сними отпечаток → `$T/devm.json` и выполни `node .claude/tools/compare-diff.js "$T/devm.json" "$T/dev.json" --responsive` (мобилка против десктопа того же DEV). Если есть `hidden_on_mobile`, `missing_on_mobile` или число слов упало больше чем на 25% — сработал триггер.
3. При срабатывании открой эталон на этом же разрешении (`orig-mobile-…`, тот же язык/путь страницы), сними отпечаток и сравни как в шаге Б (`compare-diff.js "$T/devm.json" "$T/origm.json"`):
   - блок скрыт **и на эталоне, и на DEV** (так и задумано) — не находка;
   - блок виден на эталоне и скрыт/пропал только на DEV — находка `[Visual]`.
4. Если триггеры не сработали — эталон на мобилке/планшете не открывай.

## Шаг Г. Ручное доведение того, что скрипт не решает
`compare-diff.js` показывает, где различается «форма»; смысл проверяешь ты:
- **Текст — не дословное совпадение, а сохранность фактов.** Пересказ, другой порядок предложений, сокращения — норма, если все факты оригинала присутствуют. Для секций из `shorter` и чисел из `numbers` читай оба фрагмента (`find`/`snapshot` только нужной секции) и сверяй факты, цифры, названия, сроки, гарантии построчно.
- **Изображения** — по смыслу (`alt`), а не по файлам; неуместное (не по теме/географии) изображение — баг.
- **NAP** — по правилам `technical-checks` §7; список оригинальных номеров даёт эталон (`ORIGINAL:`) — это допустимая сверка по §7.
- **Schema** — состав полей и типов не хуже эталона; потерянный `BreadcrumbList` при сохранившихся видимых хлебных крошках — баг.
- **Формы** — набор полей и обязательность относительно эталона.

## Что НЕ является находкой
- Переформулированный текст с сохранёнными фактами, другой порядок абзацев, сокращения.
- Те же по смыслу картинки под другими именами файлов; изменённые размеры/формат.
- Более богатая разметка Schema на DEV (лишние `sameAs`, `priceRange` и т.п.) — если нет дублей и чужих данных.
- Страницы, секции и блоки, которых нет на эталоне (новое на DEV).
- `noindex`/`nofollow` в `robots` на DEV; другой или отключённый трекинг; другие номера из-за колл-трекинга на LIVE-эталоне (правила §7).
- Динамический контент: блоги и ленты (списки постов, даты), отзывы из виджетов, счётчики, рекламные баннеры.
- Блок, скрытый на мобилке и на эталоне, и на DEV.
- Стилистические различия (цвета, шрифты, отступы) — эта сверка их не проверяет.
- Страница, которой нет на самом эталоне.

## Серьёзность и тег (значок 🟥/🟨/🟩 и тег — по CLAUDE.md, «Критерии»)
| Что найдено | Тег | Серьёзность |
|---|---|---|
| Страница из sitemap эталона отсутствует на DEV (ни адреса, ни пары, ни редиректа) | `[SEO]` | 🟥 |
| Секция (блок) эталона целиком отсутствует на DEV | `[Visual]` | 🟥 |
| Значение изменено (число, год, цена, срок, гарантия, имя, адрес, ссылка) — на DEV теперь другой факт | `[Visual]` | 🟥 |
| Факт/утверждение/абзац внутри секции пропал, значение не подменено | `[Visual]` | 🟨 |
| Блок скрыт или пропал только на мобилке/планшете DEV | `[Visual]` | 🟨 (🟥, если это форма, CTA-кнопка или телефон) |
| Расхождение NAP | `[Technical]` | 🟥 (`technical-checks` §7) |
| Поле лид-формы пропало или потеряло `required` | `[Form]` | 🟥 (нелид-форма — 🟨) |
| Пропал ожидаемый тип Schema целиком (`BreadcrumbList`, `FAQPage`…) | `[Schema]` | 🟥; пропали отдельные поля — 🟨 |
| `title`/`description`/H1: заглушка, пусто или пропал (`Home`, `Services`, нет `description`) | `[SEO]` | 🟨 (массово по шаблону — 🟥 для отсутствующего `description`) |
| Пропала CTA-кнопка или ссылка меню/футера на страницу | `[Visual]` / `[Technical]` | 🟨 |
| Пропала ключевая картинка секции | `[Visual]` | 🟨 |

**Формат «Доказательства» для сверки с эталоном.** Эталон `ORIGINAL:` — явный эталон, переданный пользователем, поэтому пиши две строки: **Ожидалось (эталон): [значение на эталоне] / Получено (DEV): [значение на DEV]**, плюс URL обеих страниц. Для «страница/секция отсутствует» — путь и статус, либо дословные списки секций обеих версий из `compare-diff.js`.

## Скриншоты и вручную сохранённые снапшоты
DEV и эталонный сайт — два РАЗНЫХ сайта, у каждого своя рабочая папка `projects/{домен}/{прогон}/` (CLAUDE.md, «Рабочая папка сайта»); не смешивай их файлы. Используй одно и то же значение `{прогон}` для обеих папок.
- Скриншоты DEV — как обычно, `projects/{домен-DEV}/{прогон}/screenshots/{страница}_bugs/...` (Шаг 4 CLAUDE.md).
- **Скриншоты эталона — в его СОБСТВЕННУЮ рабочую папку** `projects/{домен-эталона}/{прогон}/screenshots/{страница}_bugs/...`.
- **В имени файла явно помечай версию** — `DEV_` или `ORIGINAL_` первым префиксом; у пар до/после дальше `before_`/`after_`, затем разрешение и проблема, например `projects/{домен-DEV}/{прогон}/screenshots/estimate_bugs/DEV_tablet_h1-clipped.png` и `projects/{домен-эталона}/{прогон}/screenshots/estimate_bugs/ORIGINAL_tablet_h1-reference.png`.
- То же для вручную сохранённых snapshot (`.yml`): `projects/{домен-DEV}/{прогон}/snapshots/DEV_estimate_desktop.yml`, `projects/{домен-эталона}/{прогон}/snapshots/ORIGINAL_estimate_desktop.yml`. Отпечатки `compare-fingerprint.js` в эти папки НЕ сохраняются (временные файлы, шаг «Временные файлы»).

## Расширенный режим (только по явной строке `Сверка с оригиналом: все страницы` в `Сайты.txt`)
Перенос контента ломается постранично, а сэмплирование 1–2 страниц на шаблон ловит системные ошибки, но не одиночные. Если в `Сайты.txt` есть эта строка, после шагов А–Г для страниц выборки пройди **все остальные пары страниц** из `common` шага А (не более 100; если пар больше — возьми по порядку sitemap и напиши в «Технических деталях», сколько не покрыто): для каждой открой DEV и эталон (`goto` в тех же сессиях), сними отпечатки, выполни `compare-diff.js` и оформи находки. Без `snapshot`, без мобилки и планшета, без скриншотов до момента фиксации находки. Одинаковые находки на страницах одного шаблона оформляй одной записью «массово» со списком страниц. Не включай этот режим сам и не спрашивай о нём.

## Отчёт
- В «Технических деталях» строка «Сравнение с Figma / сверка с оригиналом:» — режим (`ORIGINAL`, обычный или расширенный), итог шага А (число URL на DEV / на эталоне / общих; сколько страниц не перенесено, сколько сменило адрес, сколько новых на DEV), а также таблица «что с чем сравнивалось» (по строке на каждую пару и разрешение):

  | Страница DEV | Страница эталона | Разрешение | Статус |
  |---|---|---|---|
  | / | https://original/ | десктоп 1920×1080 | сверено, N расхождений |
  | /blogs/x | /blog/x | десктоп 1920×1080 | сверено, адрес изменился (в рекомендации) |
  | /services/y | — | — | страницы нет на эталоне |

  Если эталон недоступен — «эталон недоступен, причина»; остальные проверки DEV это не блокирует.
- Находки оформляются пунктами общего списка «Что нужно доделать» с тегом типа (`[Form]`/`[Technical]`/`[Visual]`/`[Interactive]`/`[SEO]`/`[Rel/Target]`/`[Schema]`, см. CLAUDE.md, «Формат отчёта») наравне со всем остальным — отдельный раздел не создавай.
- В «Рекомендации для ручной проверки» вынеси: смену адресов страниц (проверить 301-редиректы), различия трекинга, страницы, которых нет на самом эталоне.
