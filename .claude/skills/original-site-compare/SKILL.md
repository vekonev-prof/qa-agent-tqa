# Сверка DEV с реальным эталонным сайтом (вместо Figma)

## Когда вызывать
Только если строка сайта в `Сайты.txt` указывает `ORIGINAL:<url>` вместо ссылки на Figma во втором поле. Если указана обычная Figma-ссылка — этот скилл не применим, используй `figma-compare`. Оба варианта взаимоисключающие для одного сайта.

## Экономия токенов — три правила, снижающие стоимость вдвое

Сверка с отдельным реальным сайтом по своей природе дороже, чем без неё — по факту это удвоение браузерных сессий на каждую проверяемую страницу (DEV + эталон). Три правила ниже держат эту стоимость под контролем:

1. **Контент/структуру/Schema/телефон сверяй ОДИН раз, на десктопе.** Подавляющее большинство находок про верность переноса (пропавшие секции, изменённый текст, неверный NAP, неверный тип/поля Schema) видны уже на одном разрешении. Не открывай эталонный сайт на мобилке/планшете по умолчанию для этой части.
2. **Эталонный сайт на мобилке/планшете открывай ТОЛЬКО если `visual-checks` уже нашёл конкретное визуальное расхождение на DEV именно на этом разрешении** — то же условие, что у `figma-compare` («только если найдено расхождение»). Так отличаются «регрессия переноса» от «унаследовано с оригинала, воспроизведено 1:1» — но открывать эталон на этом разрешении имеет смысл только когда есть что подтверждать/опровергать, не заранее «на всякий случай».
3. **Не пиксель-в-пиксель.** Сравнивай структуру, порядок секций, ключевые факты (текст, NAP, тип Schema, набор полей формы) через `snapshot --depth=4`/`find` — не через скриншот-диффинг всей страницы. Скриншот — только если решаешь зафиксировать конкретный визуальный баг (см. Шаг 4 CLAUDE.md).

Держи одну именованную сессию на сайт на весь прогон (например `-s=orig-desktop`) и переходи между страницами через `goto` внутри неё — не открывай (`open`) новую сессию на каждую страницу эталона.

## Соответствие страниц

По умолчанию — тот же URL-путь на обоих доменах (например `/services/cabinet-refacing` и там, и там). Если по этому пути на эталоне 404 — не спеши делать вывод о расхождении структуры URL:
1. Сначала попробуй очевидный вариант (добавить/убрать сегмент, например `/blogs/slug` вместо `/slug`, или наоборот).
2. Только если очевидный вариант тоже не сработал — поищи вручную по навигации/sitemap эталонного сайта страницу с тем же заголовком/темой.

Если после этого страница на эталоне не находится вовсе — это не баг DEV, а находка про сам эталонный сайт (например, статья не привязана к общей ленте/навигации там) — фиксируй в «Рекомендации для ручной проверки», не в «Баги» DEV.

## Что сравнивать
- **Структура секций** (порядок, количество, тип блоков) — `snapshot --depth=4` на обеих версиях.
- **Текст — не требуется дословное совпадение** (перенос обычно делают ИИ-агенты, которые пересказывают текст — это ожидаемо, не баг само по себе). Критерий — **сохранность фактов, не слов**:
  - **ОК:** переформулированный текст, другой порядок предложений/абзацев, сокращённые обороты — если все факты/утверждения оригинала при этом присутствуют.
  - **Баг:** пропавший факт/утверждение/абзац/секция целиком; изменённое число, дата, название, характеристика услуги, гарантия (например, «работаем с 2010» превратилось в «работаем с 2015» без пометки в `Правки:`); прямое противоречие тому, что было в оригинале.
  - При сомнении — сверяй конкретные факты/цифры/названия построчно между версиями, а не общее «звучит похоже».
- **Изображения** — те же по смыслу картинки на месте (не «тот же файл побайтово» — платформа может переразмещать файлы под новыми именами, это не баг); отсутствующий блок с картинкой или неуместное (не по теме/географии) изображение — баг.
- **NAP (телефон/адрес)** — сверяется по правилам `technical-checks` §7, не дублируй логику здесь; в частности, если сравниваешь конкретные номера, § 7 требует брать номер эталона из сырого HTML (до выполнения JS), а не из отрисованного DOM.
- **Schema (JSON-LD)** — тип разметки и обязательные поля по `technical-checks` §9; дополнительно сверь, что тип/состав полей на DEV не хуже эталона (потерянный уровень `BreadcrumbList`, пропавший ожидаемый тип схемы — баг; более полная/богатая схема на DEV, чем на эталоне, — не баг, а улучшение, не нужно фиксировать как расхождение).
- **Формы** — набор полей и их обязательность относительно эталона (например другая маска, другой список опций в дропдауне, пропавшее поле) — это структурная сверка; сам функциональный сабмит-тест делает `form-submit-checks`, не дублируй его здесь.

## Скриншоты и вручную сохранённые снапшоты
- Скриншоты DEV — как обычно, `screenshots/{домен DEV}/...` (см. Шаг 4 CLAUDE.md).
- **Скриншоты эталонного сайта — в его СОБСТВЕННУЮ доменную подпапку**, `screenshots/{домен эталона}/...` — не смешивай с подпапкой DEV, это разные сайты, даже если сравниваются в рамках одной задачи.
- **В имени файла явно помечай версию** — `_DEV` или `_ORIGINAL` перед разрешением/проблемой, например:
  - `screenshots/{домен-DEV}/estimate_DEV_tablet_h1-clipped.png`
  - `screenshots/{домен-эталона}/estimate_ORIGINAL_tablet_h1-reference.png`

  Без этой пометки при нескольких скриншотах из разных прогонов сложно на глаз отличить, какой скриншот с какой версии сайта.
- **То же самое — для вручную сохранённых snapshot (`.yml`), если решаешь зафиксировать структуру страницы для дальнейшего сравнения, а не только держать её в контексте диалога.** Общее правило Шага 4 CLAUDE.md («любой явно сохранённый файл — в подпапку по домену») здесь распадается на ДВЕ подпапки, по одной на каждую сторону сравнения — не клади оба снапшота плоско в корень проекта и не называй их сокращённо (`dev-...yml`, `orig-...yml`) вместо пути:
  - `.playwright-cli/{домен-DEV}/estimate_DEV_desktop.yml`
  - `.playwright-cli/{домен-эталона}/estimate_ORIGINAL_desktop.yml`

## Отчёт
Сверка с оригиналом заменяет строку «Сравнение с Figma» в формате отчёта (CLAUDE.md) — вместо неё пиши **«Сверка с оригиналом:»** с кратким статусом (сверено по N страницам, расхождений сверх перечисленных в «Багах» не найдено / эталонный сайт недоступен — причина). Находки из этой сверки идут в обычные три чек-листа отчёта (Баги/Правки/Рекомендации) наравне со всем остальным — не создавай для них отдельный раздел.
