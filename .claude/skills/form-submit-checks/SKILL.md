# Функциональный тест форм и калькуляторов (сабмит)

Визуальную часть форм (наличие полей, видимость кнопки отправки, визуальная пометка обязательности) уже проверяет `visual-checks`. Этот скилл добавляет то, что визуальной проверки не ловит: сабмит не проходит, письмо уходит не туда, поле обязательно/необязательно не так, как задумано.

## Когда вызывать — классификация форм

Тестируется реальным сабмитом **любая** форма на проверяемой странице — глубина протокола зависит от того, что делает конкретная форма. «Не сабмитим вообще» — больше не вариант по умолчанию.

**Лид-генерирующие (полный протокол ниже, до 10 попыток):** любая форма/калькулятор, успешный сабмит которой создаёт лид/заявку для отдела продаж клиента — главная контактная форма, форма в hero/quick-quote, функциональные калькуляторы, форма записи на приём/консультацию (booking/appointment), форма заявки на финансирование (financing application), любая другая форма-CTA на странице (в т.ч. mini-CTA на служебных/локационных страницах), если по смыслу она ведёт к заявке.

**Все остальные формы (облегчённая проверка — один сабмит, но не пропускать):** рассылка, поиск по сайту, отзыв/review на сайте, живой чат, отклик на вакансию (job application) и любые другие формы, не попавшие в лид-генерирующие. Для них: **агент сам определяет, что нужно для успешной отправки** (какие поля реально обязательны — через `eval`, а не на глаз; какое значение контекстно уместно для конкретного поля — единого фиксированного набора тестовых данных для этой категории нет), заполняет и делает **одну** тестовую отправку. Без отдельного граничного/невалидного сабмита, без троттлинг-теста, без потолка в 10 попыток — просто один валидный сабмит. Обязательна та же техническая верификация, что и для лид-генерирующих форм (сеть + консоль, см. ниже) — не только визуальный результат. Зафиксируй в отчёте по каждой такой форме: что вводилось, технически подтверждена ли отправка (сетевой запрос/статус/консоль), итоговый вывод.

**Исключение — форма немедленно публикует публичный контент без модерации.** Если успешный сабмит формы **сразу**, без очереди модерации, публикует контент, видимый обычным посетителям сайта (например, виджет отзывов без «на рассмотрении», публичный комментарий) — не сабмить её в рамках этого общего правила. Зафиксируй в отчёте, что такая форма найдена и не протестирована по этой причине, и дождись отдельного явного подтверждения пользователя перед конкретно этим сабмитом — публикация видимого посетителям контента на сайте клиента не покрывается общим согласием на функциональное тестирование форм.

Если неочевидно, лид-генерирующая форма перед тобой или нет — трактуй по последствиям: если баг в ней означает потерянный реальный бизнес-лид — она лид-генерирующая, даже если формально не входит в перечисленные примеры.

## Лимит (лид-генерирующие формы)
Не больше **10 сабмитов на один уникальный шаблон формы** — потолок, не цель: обычно 5 попыток (граничный кейс + валидный кейс только обязательными полями + валидный кейс всеми полями + точечная перепроверка + троттлинг-тест — все пять обязательны для лид-генерирующих форм, см. «Порядок сабмитов» ниже, не «иногда»). Не старайся специально «дотянуть» до 10. Например, если один и тот же contact-form встречается в футере на 10 страницах — тестируй его один раз, а не на каждой странице. Лимит считается **отдельно для каждого шаблона**, а не суммарно на сайт: если на сайте несколько разных лид-генерирующих форм (contact-form, quote-form, калькулятор), у каждой свой потолок 10, и итоговое количество сабмитов за прогон может быть больше 10 суммарно. Для «всех остальных форм» (см. выше) лимита нет — там по протоколу и так всего один сабмит.

## Как определить, что форма — тот же переиспользуемый шаблон (чтобы не сабмитить её повторно зря)
Прежде чем решить «эта форма уже протестирована на другой странице, повторно не сабмитим» — не полагайся только на визуальное сходство заголовка/лейблов. Проверяй в таком порядке приоритета:
1. **Технический ID формы в разметке/сети** — самый надёжный признак. Ищи через `snapshot`/`eval`: скрытое поле или атрибут CMS-конструктора форм (Contact Form 7: скрытый input `_wpcf7` с числовым ID, либо сам endpoint сабмита вида `/wp-json/contact-form-7/v1/contact-forms/<ID>/feedback`; WPForms: класс вида `wpforms-form-<ID>`; Gravity Forms: `gform_<ID>`; HubSpot: `data-form-id`; и т.п. — конкретный маркер зависит от платформы, ищи по аналогии). Совпадение этого ID на двух страницах = точно один и тот же шаблон, повторный сабмит не нужен. Несовпадение ID при похожем визуале = разные шаблоны, у каждого свой лимит на 10 попыток.
2. **Если технического ID нет или не читается** — сравни точный набор имён полей (`name`/`id` атрибутов инпутов через `eval`). Полное совпадение набора полей — весомый, но не стопроцентно надёжный признак (случайное совпадение возможно) — трактуй как «вероятно тот же шаблон» и явно отметь эту неуверенность в отчёте.
3. **Только если 1 и 2 недоступны** — как последний по надёжности признак, используй визуальное сходство (заголовок, лейблы, порядок и количество полей), и явно укажи в отчёте, что идентичность шаблона подтверждена только визуально, не технически.
Если два экземпляра похожей формы дают разный ID/набор полей — это самостоятельный X-site баг (расхождение реализации одной и той же логической формы между страницами), см. п.5 ниже, а не повод пропустить тестирование второго экземпляра.

## Координация между параллельными агентами (общий файл-маркер)
Приоритет из раздела выше работает надёжно только в рамках памяти ОДНОГО агента — если проверка сайта распределена между несколькими параллельными подагентами (разные страницы одного прогона), ни один из них не видит, что другой уже сабмитил тот же переиспользуемый шаблон где-то ещё, даже если это заранее не было предусмотрено в координации на уровне промптов (например, обнаружилось только по ходу проверки, что форма на неожиданной странице — тот же ID). Чтобы не зависеть от того, удалось ли заранее всё предусмотреть, перед сабмитом лид-генерирующей формы:

1. **Проверь маркер.** Определи технический ID шаблона (см. раздел выше), приведи к безопасному имени файла (например `cf7-201`, `wpforms-form-262`) и проверь, существует ли файл `{домен}/{прогон}/.form-submissions/<ID>.json` (`{домен}/{прогон}` — рабочая папка ЭТОГО прогона проверяемого сайта, см. CLAUDE.md, «Рабочая папка сайта» — при параллельных подагентах `{прогон}` должен быть передан оркестратором явно, одинаковый у всех, иначе каждый будет смотреть в свою собственную папку и маркер не сработает).
2. **Если файл уже существует** — прочитай его и **не сабмитй форму повторно**. Допиши текущую страницу в его поле `pages` (см. п.3 ниже), если её там ещё нет — эта форма-шаблон могла впервые встретиться на этой странице другому агенту, даже если сабмит был сделан не на ней. В своём отчёте укажи: технический ID, страницу(ы), на которой шаблон уже был протестирован/встречен, и результат из файла (успех/провал, thank-you URL, время). Это не «пропуск проверки» — это учёт уже полученного результата.
3. **Если файла нет** — пройди протокол как обычно (Шаг 0 → сабмиты → техническая верификация), и **по завершении создай этот файл** (JSON с полями: `template_id`, `pages` — массив URL всех страниц, где эта форма встретилась ТЕБЕ (не только страница сабмита — нужен для итоговой таблицы «Карта форм по сайту» в отчёте, см. CLAUDE.md), `submission_numbers` — массив номеров сабмитов (см. «Сквозная нумерация» ниже), которые ушли в эту форму, `tested_by` — краткое имя/описание своей сессии, `timestamp` (МСК, тот же момент `{прогон}`, что и в имени рабочей папки — см. CLAUDE.md), `result` — краткая сводка: успех/провал каждого сабмита, thank-you URL, найденные баги формы) — чтобы следующий параллельный агент, наткнувшись на тот же ID, увидел готовый результат вместо повторного сабмита и мог дополнить список страниц.
4. **Встретил ту же форму на новой странице, но сама форма технически уже протестирована** (маркер существует) — не сабмитишь повторно, но всё равно допиши эту страницу в `pages` маркера (п.2 выше). Не пропускай этот шаг молча: без него итоговая таблица «Карта форм по сайту» в отчёте останется неполной — покажет только страницы, где реально сабмитили, а не все, где форма встретилась.
5. Небольшой риск гонки (два агента одновременно не находят файл и оба сабмитят, либо оба одновременно дописывают `pages`) — приемлем: он не нарушает лимит в 10 попыток и заметно снижает количество дублирующих сабмитов по сравнению с полным отсутствием координации.

Эта папка (`{домен}/{прогон}/.form-submissions/`) — служебная для одного прогона, не результат проверки для отчёта клиенту; при сборке итогового отчёта можно опираться на неё как на точный список того, какие шаблоны сабмитились и сколько раз, вместо того чтобы собирать это из прозы разных агентов.

## Шаг 0 — карта полей формы (до всякого сабмита)
1. Собери список всех полей формы (`snapshot` + `eval` на атрибут `required`, а также `type`/`pattern`/`inputmode`/`maxlength` каждого поля) и отметь, какие визуально помечены как обязательные (звёздочка, текст "required" и т.п.), а какие нет.
2. Сверь визуальную пометку с реальным поведением и найди противоречия — это самостоятельный баг вне зависимости от результата сабмита:
   - Поле выглядит обязательным, но `required`-атрибута нет / пустое поле не блокирует отправку. **Важно:** если у CMS-формы (Contact Form 7 и подобные) обязательность реализована не через нативный HTML `required`, а через `aria-required="true"` + собственный класс валидации (например `wpcf7-validates-as-required`) — и при этом реальный сабмит с пустым полем действительно блокируется (см. Сабмит №1 ниже) — это НЕ противоречие, а рабочий альтернативный механизм валидации. Проверяй по фактическому поведению при сабмите, а не только по наличию конкретного атрибута `required`.
   - Поле не помечено как обязательное визуально, но фактически блокирует сабмит.
   - Обязательный чекбокс согласия/условий — отдельно проверь, действительно ли он должен быть обязательным (по смыслу формы или по ТЗ в `Сайты.txt`), и совпадает ли это с фактическим поведением.
3. Для каждого поля отметь, какие граничные значения имеет смысл проверить (см. ниже) — телефон, ZIP, email, числовые поля калькулятора, поля с ограничением длины.
4. **Для каждого обязательного поля, не входящего в фиксированный список тестовых данных ниже** (дропдауны, radio, чекбоксы кроме согласия, даты, числовые поля, любые специфичные для проекта поля вроде «Move Size», «Service Type», «How did you hear about us») — **сам подготовь контекстно уместное значение** заранее, до сабмита: для дропдауна/radio выбери любой не-пустой пункт (не заголовок-плейсхолдер вида «Select…»), для даты — ближайшую валидную дату в нужном формате, для чекбокса без явного «согласия» — отметь, если это разумно по смыслу поля. Список из «Тестовые данные» ниже не покрывает все возможные проекты — это ожидаемо, дополняй его на месте под конкретную форму.
5. **Если один и тот же логический тип формы** (по названию/полям/смыслу — например «Contact Us» или «Get a Quote») **встречается на нескольких проверенных страницах — сравни карты полей между экземплярами** (используя приоритет признаков из раздела выше). Расхождение в реализации одной и той же формы (разные атрибуты `required`/`pattern`/`maxlength`, разная маска телефона, разный набор полей) между страницами — самостоятельный баг (X-site несогласованность реализации), даже если каждый экземпляр по отдельности не выглядит сломанным. Явно укажи, на каких страницах какая версия реализации.

## Сквозная нумерация сабмитов
Каждому реальному сабмиту (не граничному/невалидному кейсу — тому, что реально должен дойти) присваивается номер по единому счётчику **на весь прогон**, не на форму и не на страницу: первый сабмит за весь прогон — №1, следующий (даже другая форма на другой странице) — №2, и так далее. Номер вписывается в тестовые данные этого сабмита (см. ниже) — так итоговый отчёт даёт таблицу «№ → страница → форма → thank-you URL/ID», по которой ПМ/клиент сверяет с CRM/почтой и сразу видит, если какой-то номер не дошёл.

**Координация при параллельных подагентах** — тем же способом, что и файл-маркер дедупликации (см. выше): общий счётчик в `{домен}/{прогон}/.form-submissions/_counter.txt` этого прогона. Перед каждым реальным сабмитом прочитай текущее значение, используй `значение+1` как свой номер, запиши новое значение обратно. Небольшой риск гонки (два агента одновременно читают одно и то же значение) — приемлем, тот же принцип, что и у файла-маркера дедупликации: не блокирует работу, и даже при коллизии результат остаётся читаемым (максимум задвоится один номер, не вся нумерация).

## Тестовые данные для валидного сабмита
Для стандартных полей — всегда одинаковые (кроме номера сабмита `N`, который меняется каждый раз), чтобы клиент сразу узнал тест агентства; для остального — см. Шаг 0 п.4, готовь сам под конкретную форму:
- Имя / Фамилия (если поля раздельные): `Vladislav` / `Konev`.
- Email: `vladislav.k@comradeweb.com`.
- Телефон: номер из зарезервированного NANPA-блока для тестового использования — `+1 (555) 555-01XX` (например `+1 (555) 555-0142`), где `XX` — номер сабмита `N` с ведущим нулём (01, 02, 03…), не произвольные цифры. Это официально выделенный под тест/вымышленные номера диапазон в США, не принадлежит реальному абоненту ни при какой area code.
- Адрес (если есть автоподбор адреса, например для relocation-форм с полями «Адрес начальный»/«Адрес конечный»): любой реальный публичный адрес, например `350 5th Ave, New York, NY 10118`.
- Свободный текст / сообщение: `TEST MESSAGE FROM QA TEAM, PLS IGNORE. Submission #N. Submitted from: [URL страницы, с которой отправлен сабмит] | Form: [идентификатор формы]`. Идентификатор формы — это `id`/`name`-атрибут формы (или технический ID из раздела «Как определить...» выше) из разметки, если он есть; если технического ID в разметке нет — короткое описательное имя (например «footer contact form», «hero quick-quote»). Нужно, чтобы в CRM можно было отличить, какая именно форма прислала заявку, если их на бэкенде несколько.

## Граничные значения — проверяй не только телефон, а все применимые поля
**Для полей с визуальной маской/форматированием (телефон, дата и т.п.) — каждое граничное значение проверяй ДВУМЯ реалистичными способами ввода, не одним:** настоящим посимвольным вводом (по одной клавише) И настоящей вставкой (эмулируй реальный paste — не программной подстановкой `.value`/`fill()` в обход событий клавиатуры/вставки). Маскирующий скрипт нередко ведёт собственное внутреннее состояние, синхронизирующееся с DOM по-разному в зависимости от способа ввода — расхождение результата между способами может быть либо реальным багом (тогда фиксируй оба наблюдения — какой способ ломается, какой нет), либо артефактом того, что протестирован только один способ. Если один способ ввода показал подозрительный результат, а другой не проверялся — не фиксируй находку до перепроверки вторым способом (см. `CLAUDE.md`, «Обработка ошибок»).

**Расхождение между способами ввода — ещё не готовый баг, доведи проверку до конца (см. `CLAUDE.md`, «Обработка ошибок»):** проследи механизм пошагово — по нажатию клавиши (`run-code`, логируя `el.value` после каждого символа), а не только сравнивай финальное значение до/после. Отличай тихую порчу данных (значение меняется на другое, отличное от введённого, без видимого пользователю сигнала — баг) от ограничения ввода (поле просто перестаёт принимать нажатия по достижении лимита длины, значение не меняется, пользователь видит это в реальном времени — не баг). И в обоих случаях доведи проверку до реальной попытки сабмита с этим граничным значением — подозрительное значение в поле само по себе не значит, что дефектные данные дойдут до CRM; если форма блокирует отправку и подсвечивает поле как невалидное, защита сработала правильно.
- Телефон (исторически самое проблемное поле): с `+1` и без, со скобками/дефисами и без, с недостаточным/избыточным числом цифр — маска должна нормализовать ввод и не пропускать некорректную длину.
- ZIP: буквы вместо цифр, слишком короткий/длинный.
- Email: без `@`, без домена, странные символы.
- Числовые поля калькулятора: 0, отрицательное значение, очень большое число, дробное там, где ожидаются целые.
- Текстовые поля с `maxlength`: значение на грани лимита и сверх него.
- Обязательные текстовые поля (имя, сообщение и т.п.): значение только из пробелов (например, три пробела без другого текста) — должно блокироваться так же, как пустое поле, а не приниматься как заполненное.
- **Случайный пробел сбоку от иначе полностью валидного значения** (не путать с пунктом выше — здесь само значение корректное, лишний только пробел по краю): например, email со случайным пробелом в начале или конце (`" vladislav.k@comradeweb.com"` или `"vladislav.k@comradeweb.com "`), телефон с пробелом перед/после номера. Это реалистичный кейс — именно так выглядит значение, если пользователь скопировал его откуда-то (письмо, визитка, другая форма) и случайно задел пробел рядом. Проверь на email и на телефон (посимвольным вводом с пробелом в начале/конце — см. правило про способы ввода выше, для телефона это тоже граничное значение маски). Ожидаемое поведение: форма должна либо тихо обрезать пробел по краям (trim) и принять значение как есть, либо явно показать ошибку валидации, если строго связана с наличием пробела. Баг — если пробел молча проходит валидацию AND реально уходит в CRM внутри значения (испорченный email/телефон в базе клиента) без обрезки и без ошибки.
- Дата (если есть поле с датой, отдельно от общего правила про маски выше): недопустимый день месяца (31 число в 30-дневном месяце, 29 февраля не в високосный год), дата в прошлом или неправдоподобно далеко в будущем — если по смыслу поля должны быть ограничения (например, дата переезда не может быть в прошлом), неверный формат ввода.
- Загрузка файла (если есть такое поле, например резюме в форме отклика на вакансию): файл неподходящего типа (если задан `accept`), файл сверх лимита размера (если лимит виден в разметке или тексте рядом с полем), пустой файл — форма должна отклонять некорректный файл с понятным сообщением, а не падать молча/зависать.

## Техническая верификация каждого сабмита (обязательна после любого клика Submit, для каждой попытки — не только когда видно визуальный сбой)
Визуальный результат (появилась confirmation, произошёл редирект/reload, ничего видимо не изменилось) — недостаточное основание для вывода об успехе или неудаче. Подтверждай факт отправки данных технически:
1. Сразу после клика сними список сетевых запросов (`playwright-cli requests`) и найди тот, что соответствует реальной отправке формы — по признакам, а не по названию (оно на каждом сайте своё): метод POST/PUT, тайминг сразу после клика, payload содержит значения только что введённых полей.
2. Проверь статус-код и содержимое ответа этого запроса на признак успеха/неудачи — что бы это ни было конкретно на этом сайте (JSON с `success`/`error`, HTTP-редирект на thank-you URL, специфичный статус-код и т.п.).
3. **Если такого запроса не нашлось вообще** (например, страница просто перезагрузилась без единого нового relevant-запроса) — это самостоятельный технический признак, что сабмит не дошёл, даже без видимой ошибки. Исключение — Сабмит №1 (граничный/невалидный кейс, см. ниже): там отсутствие такого запроса — ожидаемый правильный результат (форма должна была заблокировать отправку на клиенте); если запрос всё же ушёл несмотря на невалидные данные — вот это баг.
4. Проверь консоль (`playwright-cli console`, только уровень `error`) в узком окне вокруг самого клика Submit (непосредственно до/во время/после) — отдельно от разового прохода по консоли всей страницы в `technical-checks` (тот не привязан по времени к моменту сабмита и может его не поймать). JS-исключение внутри обработчика сабмита может тихо сорвать отправку без единого видимого признака для пользователя.

## Порядок сабмитов
До 10 попыток на уникальный шаблон формы (потолок, не цель; к каждой применяй техническую верификацию выше). Если не указано иное — все сабмиты делай на десктопной сессии (Chrome), а не на мобильной/планшетной:
1. **Сабмит №1 (граничный/невалидный кейс), десктоп:** оставь один-два обязательных поля пустыми или впиши граничное невалидное значение (см. выше) — форма должна заблокировать отправку на клиенте (см. п.3 верификации выше) и показать ошибку именно у нужного поля. Если обязательный чекбокс есть — оставь его неотмеченным на этом шаге.
2. **Сабмит №2 (валидный кейс, ТОЛЬКО обязательные поля), десктоп:** заполни валидными данными **только те поля, что реально обязательны по факту** (по карте полей Шага 0 — включая случаи, где обязательность реализована не через `required`, а через `aria-required`/класс валидации), необязательные оставь пустыми. Отметь обязательный чекбокс, если есть. Цель — реалистичный сценарий: многие реальные пользователи заполняют только помеченное звёздочкой и пропускают остальное; форма и бэкенд должны нормально это принимать. Подтверди сабмит технически, как любой другой (см. верификацию выше). **Если сабмит неожиданно заблокирован на поле, которое не было помечено как обязательное ни визуально, ни атрибутом** — это самостоятельный баг (поле фактически обязательно, но нигде не заявлено таким), отдельный от того, что ловит Сабмит №1 (там наоборот — заявленно обязательное поле должно блокировать).
3. **Сабмит №3 (валидный кейс, ВСЕ поля), десктоп:** заполни **все** поля формы — обязательные и по возможности необязательные, чтобы не оставить пустым что-то, что реально требуется. Для стандартных полей — тестовые данные из списка выше; для всего остального — подготовленные на Шаге 0 п.4 значения. Отметь обязательный чекбокс. Только когда ты уверен, что заполнено всё видимое обязательное поле — отправляй. **Прежде чем зафиксировать «сабмит не проходит» или «поле некорректно валидируется» как баг, сначала проверь снапшотом/eval, какое именно поле блокирует отправку.** Если это поле, которое ты сам не заполнил (недосмотр, а не баг сайта) — это не баг: заполни его и продолжай, не трать на это отдельную попытку из потолка. Багом это становится только если поле было заполнено корректно, а форма всё равно не проходит (по критериям технической верификации выше, не только по визуальному сообщению об ошибке).
4. **Защита от дублирования лида (сразу после успешного Сабмита №3, теми же данными — отдельной попытки из потолка 10 не тратит):**
   - **Двойной клик:** если форма отправляется через AJAX (JS перехватывает submit — после отправки страница обновилась на месте без полной навигации/reload, а не как обычный `<form action>` с полной перезагрузкой) — заполни форму валидными данными ещё раз и кликни Submit дважды быстро подряд (второй клик — до завершения первого запроса, пока кнопка ещё выглядит активной). Через сеть (`playwright-cli requests`) убедись, что реальной отправки данных ушла ровно **одна**, а не две. Если кнопка не блокируется на время отправки и ушло два запроса (два лида в CRM от одного клика пользователя) — это баг.
   - **Повторная отправка после «Назад» в браузере:** после успешного Сабмита №3 (редирект/сообщение об успехе) нажми «назад» в браузере, вернувшись на страницу с формой, и проверь, не осталась ли форма заполненной с теми же данными в состоянии, готовом к повторной отправке одним кликом «на автомате» (например, если пользователь машинально жмёт «назад» и снова Submit) — если так, зафиксируй как находку (риск случайного дубля лида), но не как критичный баг, если форма при этом всё же требует осознанного повторного клика.
5. **Сабмит №4 (точечная перепроверка), всегда обязателен — не только когда что-то найдено:** если Шаг 0, Сабмит №1 или Сабмит №2 выявили конкретное противоречие, которое иначе не подтвердить однозначно — целься именно в него, на той сессии (десктоп/мобилка), где оно всплыло. **Если явного противоречия не нашлось — это не повод пропускать сабмит:** проверь дополнительный реалистичный граничный кейс, ещё не покрытый Сабмитом №1 (другое поле с маской/лимитом из списка «Граничные значения» выше, либо тот же граничный сценарий вторым способом ввода — например, Сабмит №1 проверял телефон посимвольным вводом, здесь проверь его же вставкой (paste), см. правило про способы ввода выше). Цель — дополнительная уверенность в форме всегда, а не только в момент, когда уже что-то заподозрено.
6. **Троттлинг-тест (сабмит под искусственно замедленной сетью), всегда обязателен для лид-генерирующих форм (сверх стандартных сабмитов №1–№4, которые идут на десктопе):** выполни ещё один валидный сабмит на мобильном разрешении под искусственным троттлингом сети (аналог Slow 3G) — независимо от того, AJAX это форма или обычный `<form action>` с полной перезагрузкой страницы (раньше проверка ограничивалась только AJAX-формами — теперь выполняется всегда: на AJAX-формах она провоцирует race condition в асинхронной загрузке JS-скриптов, на обычных — вскрывает свои проблемы медленной сети, например таймаут сервера или потерю введённых данных при обрыве соединения). Эта попытка **не входит** в потолок 10 сабмитов на шаблон — тот потолок про количество вариантов тестовых данных (граничный/валидный/точечный), а троттлинг — отдельная узкоспециализированная проверка именно тайминг-зависимых багов, а не ещё один вариант данных. Не повторяй троттлинг-тест больше одного раза на форму — если он ничего не показал, этого достаточно.

   Технически: троттлинг через CDP работает только в Chromium — WebKit его не поддерживает. Поэтому для этой проверки открой отдельную именованную сессию — мобильная эмуляция в Chromium, не буквально WebKit-сессия основных проверок:
   ```bash
   playwright-cli -s=throttle-test open --mobile --browser=chrome <URL>
   playwright-cli -s=throttle-test run-code "async page => { const client = await page.context().newCDPSession(page); await client.send('Network.enable'); await client.send('Network.emulateNetworkConditions', { offline: false, downloadThroughput: 50*1024/8, uploadThroughput: 50*1024/8, latency: 2000 }); }"
   ```
   Дальше заполни форму теми же тестовыми данными, что и в Сабмите №3 (все поля), отправь и примени ту же техническую верификацию (сетевой запрос + консоль). Закрой сессию (`playwright-cli -s=throttle-test close`) по завершении.
7. Для калькуляторов: **ТЗ на формулу расчёта можно передать в `Сайты.txt` (блок `Комментарии:`) — если оно есть, сверь результат с ним точно.** Но по умолчанию считай, что ТЗ передано НЕ будет — это обычный случай, а не исключение. Без ТЗ агент не оценивает точность формулы (не его компетенция без спецификации), а проверяет только устойчивость и правдоподобность по конкретным критериям:
   - Прогони несколько реалистичных сценариев (не только границы 0/отрицательное/пустое поле) — результат не падает, не показывает `NaN`/пустое значение/отрицательное число там, где это не имеет смысла.
   - Монотонность: при увеличении одного вводного значения (например, расстояние, объём, количество комнат) итоговая величина меняется в ожидаемую сторону (обычно растёт), а не наоборот — без явной бизнес-причины для обратной зависимости.
   - Калькулятор реагирует на ввод: разные вводные данные дают разный результат, а не одно и то же число независимо от того, что ввели (нередкий баг — калькулятор фактически ничего не считает).
   - Один и тот же ввод даёт один и тот же результат при повторном расчёте (детерминированность), если не задумана намеренная случайность.
   - **Внутренняя арифметическая согласованность (критический уровень проверки, не требует знания формулы):** если калькулятор показывает разбивку итоговой суммы (например, база + доп. услуги + итог) — сложи показанные компоненты и убедись, что сумма реально равна показанному итогу. Расхождение — баг, причём это не догадка о бизнес-логике, а проверяемый факт, идёт в блок «Формы и калькуляторы» (см. CLAUDE.md, «Формат отчёта»). Если разбивки нет (калькулятор выдаёт только одно число) — глубже без ТЗ не проверяется, это предел.
   Зафиксируй в отчёте «ТЗ на логику калькулятора не предоставлено — сверка с реальной формулой не проводилась, нужно запросить у ПМа», но саму устойчивость, правдоподобность и внутреннюю согласованность результата (по критериям выше) всё равно проверь и опиши — это не освобождает от проверки, а лишь ограничивает её без точной формулы.
8. Держи в памяти, на какой thank-you URL/ID вышел каждый успешный сабмит (и результат технической верификации по нему) — это понадобится для рекомендации проверить админку/почту в итоговом отчёте.

## Возвращаемый результат
- Для каждой лид-генерирующей формы: технический признак, по которому определён шаблон (ID/набор полей/только визуально — см. раздел выше), карта полей (визуал vs `required`, найденные противоречия), результат каждого сабмита (что вводилось → что произошло технически, сеть+консоль → вывод: прошло/не прошло), **номер сабмита (см. «Сквозная нумерация» выше) и thank-you URL/ID** успешного сабмита, результат проверки на дублирование (двойной клик / повторная отправка после «назад»), результат обязательного троттлинг-теста (см. «Порядок сабмитов» п.5 — он больше не опциональный).
- **Полный список всех страниц, где этот шаблон формы встретился за прогон** (не только страница, где сделан сабмит) — нужен для итоговой таблицы «Карта форм по сайту» в отчёте (см. CLAUDE.md); координируется через поле `pages` в файле-маркере (см. «Координация между параллельными агентами»).
- Для каждой «прочей» формы (лёгкий протокол): что вводилось, технический результат сабмита (сеть+консоль), вывод — подтверждена отправка технически или нет, номер сабмита и thank-you URL/ID.
- Если форма (любой категории) определена как уже протестированный где-то ещё переиспользуемый шаблон — явно укажи это и на основании какого признака, без повторного сабмита.
- Если найдена форма, публикующая публичный контент без модерации (см. исключение выше) — укажи её отдельно как непротестированную и требующую явного подтверждения пользователя.
- Если проблем не найдено — «Функциональных проблем в формах не обнаружено».
