# Функциональный тест форм и калькуляторов (сабмит)

Визуальную часть форм (наличие полей, видимость кнопки отправки) уже проверяет `visual-checks`. Этот скилл добавляет то, что визуальной проверки не ловит: сабмит не проходит, письмо уходит не туда, поле обязательно/необязательно не так, как задумано.

## Когда вызывать — классификация форм

Тестируется реальным сабмитом **любая** форма на проверяемой странице — глубина протокола зависит от того, что делает конкретная форма.
**Лид-генерирующие (полный протокол ниже, лимит — см. «Лимит»):** любая форма/калькулятор, успешный сабмит которой создаёт лид/заявку для отдела продаж клиента — главная контактная форма, форма в hero/quick-quote, функциональные калькуляторы, форма записи на приём/консультацию (booking/appointment), форма заявки на финансирование (financing application), любая другая форма-CTA на странице (в т.ч. mini-CTA на служебных/локационных страницах), если по смыслу она ведёт к заявке.

**Все остальные формы (облегчённая проверка — один сабмит, но не пропускать):** рассылка, поиск по сайту, отзыв/review на сайте, живой чат, отклик на вакансию (job application) и любые другие формы, не попавшие в лид-генерирующие. Для них: **агент сам определяет, что нужно для успешной отправки** (какие поля реально обязательны — через `eval`, а не на глаз; какое значение контекстно уместно для конкретного поля — стандартные поля — те же тестовые данные, что в разделе «Тестовые данные», остальное подбирай по контексту поля), заполняет и делает **одну** тестовую отправку. Без отдельного граничного/невалидного сабмита, без троттлинг-теста, без потолка (см. «Лимит») — просто один валидный сабмит на шаблон формы (не на страницу): маркер и дедупликация — те же, что у лидовых форм (см. «Координация между параллельными агентами»), N и тестовые данные — те же (см. «Сквозная нумерация сабмитов» и «Тестовые данные»). Обязательна та же техническая верификация, что и для лид-генерирующих форм (сеть + консоль, см. ниже) — не только визуальный результат. Зафиксируй в отчёте по каждой такой форме: что вводилось, технически подтверждена ли отправка (сетевой запрос/статус/консоль), итоговый вывод.

**Исключение — форма немедленно публикует публичный контент без модерации.** Если успешный сабмит формы **сразу**, без очереди модерации, публикует контент, видимый обычным посетителям сайта (например, виджет отзывов без «на рассмотрении», публичный комментарий) — не сабмить её в рамках этого общего правила и продолжай прогон (остальные проверки не прерываются). Найденную форму вынеси в отчёт: «Технические детали → Не проверено» (с причиной) и «Рекомендации для ручной проверки» — с вопросом пользователю, разрешает ли он сабмит именно этой формы. Публикация видимого посетителям контента на сайте клиента не покрывается общим согласием на функциональное тестирование форм. Признак — явный текст рядом с формой («published immediately», «no moderation» и т.п.) либо публичный список рядом, в который новая запись попадает сразу; если есть сомнение, публикуется ли контент сразу, — сомнение = не сабмить. Маркера у такой формы нет (она не сабмитилась): верни её в тексте (страница, признак/ID, причина) — оркестратор внесёт её в «Карту форм по сайту» с пометкой «не сабмитилась» и причиной.

Если неочевидно, лид-генерирующая форма перед тобой или нет — трактуй по последствиям: если баг в ней означает потерянный реальный бизнес-лид — она лид-генерирующая, даже если формально не входит в перечисленные примеры.

## Лимит (лид-генерирующие формы)
Не больше **10 сабмитов на один уникальный шаблон формы** — потолок, не цель: обычно 2–4 расходуемых сабмита (валидный кейс только обязательными полями и валидный кейс всеми полями — всегда; граничный Сабмит №1 и точечная перепроверка (Сабмит №4) расходуют потолок, только если запрос ушёл на сервер и ответ = успех; все четыре шага обязательны для лид-генерирующих форм, см. «Порядок сабмитов» ниже, не «иногда»). Граничный сабмит, заблокированный клиентом или отклонённый сервером ошибкой валидации (лид не создан), в потолок не входит. Сверх них, вне потолка 10, обязательны «Защита от дублирования лида» (двойной клик — только на AJAX-формах; «Назад» — только там, где применимо, см. её описание) и «Троттлинг-тест». Не старайся специально «дотянуть» до 10. Например, если один и тот же contact-form встречается в футере на 10 страницах — тестируй его один раз, а не на каждой странице. Лимит считается **отдельно для каждого шаблона**, а не суммарно на сайт: если на сайте несколько разных лид-генерирующих форм (contact-form, quote-form, калькулятор), у каждой свой потолок 10, и итоговое количество сабмитов за прогон может быть больше 10 суммарно. Для «всех остальных форм» (см. выше) лимит — 1 сабмит на шаблон формы.

## Как определить, что форма — тот же переиспользуемый шаблон (чтобы не сабмитить её повторно зря)
Прежде чем решить «эта форма уже протестирована на другой странице, повторно не сабмитим» — не полагайся только на визуальное сходство заголовка/лейблов. Проверяй в таком порядке приоритета:
1. **Технический ID формы в разметке/сети** — самый надёжный признак. Ищи в page-audit (ключи `forms.list[].hidden`, `id`, `cls`, `dataFormId`) или, если там нет, через `snapshot`/`eval`: скрытое поле или атрибут CMS-конструктора форм (Contact Form 7: скрытый input `_wpcf7` с числовым ID, либо сам endpoint сабмита вида `/wp-json/contact-form-7/v1/contact-forms/<ID>/feedback`; WPForms: класс вида `wpforms-form-<ID>`; Gravity Forms: `gform_<ID>`; HubSpot: `data-form-id`; и т.п. — конкретный маркер зависит от платформы, ищи по аналогии). Совпадение этого ID на двух страницах = точно один и тот же шаблон, повторный сабмит не нужен. Несовпадение ID при похожем визуале = разные шаблоны, у каждого свой лимит в 10 сабмитов.
2. **Если технического ID нет или не читается** — сравни точный набор имён полей (`forms.list[].fields[].nameAttr` из page-audit — сырой `getAttribute('name')` видимых полей; отдельный `eval` — только если page-audit недоступен). Полное совпадение набора полей — весомый, но не стопроцентно надёжный признак (случайное совпадение возможно) — трактуй как «вероятно тот же шаблон» и явно отметь эту неуверенность в отчёте.
3. **Только если 1 и 2 недоступны** — как последний по надёжности признак, используй визуальное сходство (заголовок, лейблы, порядок и количество полей), и явно укажи в отчёте, что идентичность шаблона подтверждена только визуально, не технически.
Разный технический ID у похожих форм = разные шаблоны (у каждого своё тестирование и свой лимит), это само по себе не баг. Один и тот же ID при разном наборе полей/атрибутов — расхождение реализации: баг, только если по смыслу это одна и та же логическая форма (см. Шаг 0, пункт про сравнение карт полей одной и той же формы на разных страницах).

## Координация между параллельными агентами (общий файл-маркер)
Приоритет из раздела выше работает надёжно только в рамках памяти ОДНОГО агента — если проверка сайта распределена между несколькими параллельными подагентами (разные страницы одного прогона), ни один из них не видит, что другой уже сабмитил тот же переиспользуемый шаблон где-то ещё, даже если это заранее не было предусмотрено в координации на уровне промптов (например, обнаружилось только по ходу проверки, что форма на неожиданной странице — тот же ID). Чтобы не зависеть от того, удалось ли заранее всё предусмотреть, перед сабмитом любой формы (лидовой или облегчённой) — и в параллельном прогоне, и у единственного агента:

1. **Проверь маркер.** Определи технический ID шаблона (см. раздел выше) и преобразуй его в имя файла-маркера по строго детерминированному правилу — два агента, увидевшие один и тот же ID (или один и тот же набор полей), обязаны каждый раз получить БАЙТ-В-БАЙТ одинаковое имя файла, без места для интерпретации:
   - **Если есть технический ID (приоритет 1 из раздела выше):** возьми ID ровно в том виде, в котором он найден в разметке/сети — не переформулируй (если ID доступен из нескольких источников — бери в строгом порядке: 1) скрытое поле конструктора форм (`_wpcf7`, `_form_template` и т.п.); 2) `data-form-id`; 3) `id`/класс формы (для WPForms — класс `wpforms-form-<ID>`); 4) endpoint сети); приведи к нижнему регистру; если ID — голое число (CF7-стиль) — добавь префикс платформы (`cf7-`, `wpforms-`, `gform-`, `hubspot-`, иначе `form-`); если ID уже текстовый (например класс `fluent_form_12`) — используй как есть, без своего префикса; замени любой символ не `a-z0-9` на дефис на своём месте; схлопни повторы дефисов, убери по краям; добавь `.json`. Пример: `fluent_form_12` → `fluent-form-12.json`.
   - **Если технического ID нет, но набор полей чёткий (приоритет 2):** возьми `forms.list[].fields[].nameAttr` (сырой `getAttribute('name')`) видимых `input`/`select`/`textarea` формы, кроме `hidden` и `submit`/`button`; оставь только непустые, без повторов (у radio-группы одно имя); отсортируй побайтово, склей через запятую без пробелов, возьми первые 8 hex-символов SHA-1 от получившейся строки: `printf '%s\n' <имена> | LC_ALL=C sort -u | paste -sd, - | tr -d '\n' | sha1sum | cut -c1-8` → имя файла `custom-<hash>.json`. Поля без `name` в набор не входят. Если полей больше 25 (лимит `fields` в page-audit) или форма многошаговая — набор строй по `snapshot`/`eval` ВСЕХ полей формы (включая поля скрытых шагов; кроме `hidden` и `submit`/`button`), а не только по видимым; если достоверно получить все поля не удалось — считай идентификацию приоритетом 3.
   - **Если только визуальное сходство (приоритет 3, самый слабый):** дедуп между страницами здесь технически недостижим — явно фиксируй в отчёте, что идентификация только визуальная, возможен дубль-сабмит, это документированный предел метода. Имя маркера по умолчанию — `visual-<slug страницы>-<заголовок формы>.json`: slug страницы — путь страницы из URL, санитизированный как в CLAUDE.md, Шаг 4 (слэши → `_`, для главной `home`); заголовок формы (или подпись кнопки, если заголовка нет); обе части приведи к нижнему регистру, каждый символ не `a-z0-9` замени на дефис, схлопни повторы дефисов.

   Проверь, существует ли файл `projects/{домен}/{прогон}/.form-submissions/<полученное-имя>` (расширение `.json` уже входит в имя, добавляется один раз) (`projects/{домен}/{прогон}` — рабочая папка этого прогона, см. CLAUDE.md, «Рабочая папка сайта»; при параллельных подагентах `{прогон}` передаёт оркестратор, он одинаков у всех).
2. **Если файл уже существует** — прочитай его и **не сабмить форму повторно**. Допиши текущую страницу в его поле `pages` (см. «Если файла нет» ниже), если её там ещё нет — эта форма-шаблон могла впервые встретиться на этой странице другому агенту, даже если сабмит был сделан не на ней; не пропускай этот шаг молча — без него итоговая таблица «Карта форм по сайту» в отчёте окажется неполной. В своём отчёте укажи: технический ID, страницу(ы), на которой шаблон уже был протестирован/встречен, и результат из файла (успех/провал, thank-you URL, время). Это не «пропуск проверки» — это учёт уже полученного результата.
3. **Если файла нет** — пройди протокол как обычно (Шаг 0 → сабмиты → техническая верификация), и **по завершении создай этот файл** — всегда, для каждой сабмиченной формы (лидовой и облегчённой), в том числе единственным агентом (формы, которые не сабмитились — без модерации, антибот, калькулятор без отправки лида, — маркера не имеют: верни их в тексте, оркестратор внесёт их в «Карту форм по сайту» с пометкой «не сабмитилась» и причиной); файл служит для дедупликации, поле `pages` — для таблицы «Карта форм по сайту», `submissions[].time` — для сортировки таблицы «Что было отправлено» (JSON с полями: `template_id`, `pages` — массив URL всех страниц, где эта форма встретилась ТЕБЕ (не только страница сабмита — нужен для итоговой таблицы «Карта форм по сайту» в отчёте, см. CLAUDE.md), `submissions` — массив объектов `{"n": номер сабмита (см. «Сквозная нумерация» ниже), "time": реальный момент этого сабмита, UTC+3}` для каждого сабмита, ушедшего в эту форму (по `time` оркестратор сортирует таблицу «Что было отправлено», см. CLAUDE.md), `tested_by` — краткое имя/описание своей сессии, `timestamp` (момент создания самого маркера, UTC+3), `result` — краткая сводка: успех/провал каждого сабмита, статус ответа/thank-you URL, найденные баги формы) — чтобы следующий параллельный агент, наткнувшись на тот же ID, увидел готовый результат вместо повторного сабмита и мог дополнить список страниц. Агент без инструмента `Write` создаёт маркер через Bash: `node -e` с `fs.writeFileSync` (новый файл) либо `JSON.parse` → изменить `pages`/`submissions` → `JSON.stringify` → `fs.writeFileSync` (существующий); `jq` не полагай доступным.
4. Небольшой риск гонки (два агента одновременно не находят файл и оба сабмитят, либо оба одновременно дописывают `pages`) — приемлем: он не нарушает лимит (см. «Лимит») и заметно снижает количество дублирующих сабмитов по сравнению с полным отсутствием координации.

Эта папка (`projects/{домен}/{прогон}/.form-submissions/`) — служебная для одного прогона, не результат проверки для отчёта клиенту; при сборке итогового отчёта можно опираться на неё как на точный список того, какие шаблоны сабмитились и сколько раз, вместо того чтобы собирать это из прозы разных агентов.

## Шаг 0 — карта полей формы (до всякого сабмита)
1. Собери список всех полей формы: атрибуты `required`/`ariaRequired`, `type`/`pattern`/`inputmode`/`maxlength` каждого поля и признак визуальной пометки обязательности `labelStar` — из page-audit (ключ `forms.list[].fields`; отдельные `snapshot`/`eval` — только для того, чего там нет, например для скрытых или динамически добавленных полей, или для перепроверки конкретной находки; функциональные детали (обязательность `required`, маски, `maxlength`) проверяй по этим атрибутам без сабмита — см. «Порядок сабмитов», Сабмит №1; если `forms.inputsOutsideForms` > 0 или форма/калькулятор внутри iframe — карту полей строй через `snapshot`/`eval`) — и отметь, какие визуально помечены как обязательные (звёздочка, текст "required" и т.п.), а какие нет.
2. Сверь визуальную пометку с реальным поведением и найди противоречия — это самостоятельный баг вне зависимости от результата сабмита:
   - Поле выглядит обязательным, но `required`-атрибута нет / пустое поле не блокирует отправку. **Важно:** если у CMS-формы (Contact Form 7 и подобные) обязательность реализована не через нативный HTML `required`, а через `aria-required="true"` + собственный класс валидации (например `wpcf7-validates-as-required`) — и при этом реальный сабмит с пустым полем действительно блокируется (см. Сабмит №1 ниже) — это НЕ противоречие, а рабочий альтернативный механизм валидации. Проверяй по фактическому поведению при сабмите, а не только по наличию конкретного атрибута `required`.
   - Поле не помечено как обязательное визуально, но фактически блокирует сабмит.
   - Обязательный чекбокс согласия/условий — отдельно проверь, действительно ли он должен быть обязательным (по смыслу формы или по ТЗ в `Сайты.txt`), и совпадает ли это с фактическим поведением.
3. Для каждого поля отметь, какие граничные значения имеет смысл проверить (см. ниже) — телефон, ZIP, email, числовые поля калькулятора, поля с ограничением длины.
4. **Для каждого поля (обязательного; необязательного — для Сабмита №3), не входящего в фиксированный список тестовых данных ниже** (дропдауны, radio, чекбоксы кроме согласия, даты, числовые поля, любые специфичные для проекта поля вроде «Move Size», «Service Type», «How did you hear about us») — **сам подготовь контекстно уместное значение** заранее, до сабмита: для дропдауна/radio выбери любой не-пустой пункт (не заголовок-плейсхолдер вида «Select…»), для даты — ближайшую валидную дату в нужном формате, для чекбокса без явного «согласия» — отметь, если это разумно по смыслу поля. Список из «Тестовые данные» ниже не покрывает все возможные проекты — это ожидаемо, дополняй его на месте под конкретную форму.
5. **Если один и тот же логический тип формы** (по названию/полям/смыслу — например «Contact Us» или «Get a Quote») **встречается на нескольких проверенных страницах — сравни карты полей между экземплярами** (используя приоритет признаков из раздела выше). Карту полей экземпляра, который повторно не сабмитится (дедуп по маркеру), бери из page-audit этой страницы (`forms.list[].fields`) — отдельный сабмит для этого не нужен. О форме, которую ты не сабмитил, не утверждай, как она ведёт себя при отправке (шлёт ли запрос, что отвечает): в отчёт идёт только то, что видно в атрибутах, полях и коде страницы. Расхождение в реализации между страницами (разные атрибуты `required`/`pattern`/`maxlength`, разная маска телефона, разный набор полей) — самостоятельный баг (расхождение одного и того же блока/шаблона между страницами), даже если каждый экземпляр по отдельности не выглядит сломанным, но только если это по смыслу одна и та же логическая форма (один технический ID либо явно та же форма — например «Contact Us» в шапке и в футере). Разные технические ID = разные шаблоны, это не баг. Явно укажи, на каких страницах какая версия реализации.

## Сквозная нумерация сабмитов
Каждому реальному сабмиту (тому, что реально должен дойти) присваивается номер `N`. Граничный/невалидный сабмит (Сабмит №1 и граничный вариант Сабмита №4) получает номер `N` и строку в таблице «Что было отправлено» только если запрос реально ушёл на сервер И ответ сервера — успех (лид создан): это баг, в CRM клиента появится лид. Если форма заблокировала отправку на клиенте (запроса не было) либо запрос ушёл, но ответ — ошибка валидации (типично для серверной валидации, например Contact Form 7, `validation_failed`) — лид не создан, номера и строки в таблице нет. `N` для граничных сабмитов не резервируется заранее: подставляй в них `N` следующего реального сабмита; если сабмит заблокирован или отклонён сервером — `N` не расходуется и достаётся следующему сабмиту; если он ушёл и успешен — берёт этот `N`, а следующему сабмиту достаётся `N+1` (так в нумерации нет пропусков, которые ПМ прочёл бы как потерянный лид). Номер `N` — сквозной в рамках одного агента, либо в рамках закреплённого диапазона при параллельных агентах (см. `CLAUDE.md`, «Подагенты»). `N` подставляется в email как основной канал сверки и, если поле есть, в текст сообщения (см. «Тестовые данные» ниже) — так итоговый отчёт даёт таблицу «№ → страница → форма → email → статус ответа и сообщение об успехе / thank-you URL», по которой ПМ/клиент сверяет с CRM/админкой и сразу видит, если какой-то номер не дошёл.

**Координация при параллельных подагентах — закреплённый диапазон, не общий файл-счётчик.** Номер `N` — не просто метка для отчёта, он попадает в реальные данные сабмита (email), поэтому коллизия номеров у двух РЕАЛЬНЫХ сабмитов — не косметика, а два разных лида в CRM клиента с одинаковым email, которые потом нельзя различить. Если оркестратор выделил тебе диапазон номеров в промпте — используй только его, веди `N` в памяти сессии (первый реальный сабмит — начало диапазона, дальше +1); никакого общего файла не требуется. Если диапазон не выделен (прогон не распараллелен, ты единственный агент) — используй сквозной счётчик с 1, тоже в памяти, без файла. Если же ты подагент, а диапазона в промпте нет — не начинай с 1, верни оркестратору вопрос; с 1 начинает только единственный (не параллельный) агент.
(Отдельно от `N` — телефон использует свой локальный счётчик `XX`, см. «Тестовые данные» ниже; не путай эти два счётчика — `XX` не обязан совпадать с `N`.)

## Тестовые данные для валидного сабмита
Для стандартных полей — всегда одинаковые по структуре (кроме номера сабмита `N`, который меняется каждый раз и виден в email), чтобы клиент сразу узнал тест агентства; для остального — см. Шаг 0 (пункт про поля вне фиксированного списка), готовь сам под конкретную форму:
- Имя / Фамилия (если поля раздельные): `Vladislav` / `Konev`. Номер сабмита сюда НЕ добавлять — на некоторых сайтах на этом поле встречается буквенная `pattern`-валидация, непредсказуемая заранее.
- **Email — основной канал номера сабмита:** `{N}vladislav.k@comradeweb.com`, где `N` — номер этого сабмита (см. «Сквозная нумерация сабмитов» выше), номер ставится в НАЧАЛЕ локальной части, без `+` и без иных дополнительных символов. Например, сабмит №142 → `142vladislav.k@comradeweb.com`. Это основной, почти всегда доступный источник номера для сверки с CRM/админкой клиента — доставка письма на реальный ящик агентства не требуется и не гарантируется, важно только что значение попадёт в CRM/админку клиента. **Если в форме нет поля email** (callback: имя + телефон, поиск, чат) — `N` в форму не вписывается: сверка с CRM идёт по времени сабмита (`submissions[].time` в маркере) и по телефону `+1 (555) 555-01XX`; в таблице «Что было отправлено» в колонке Email пиши «нет поля». **Ограничение:** нумерация в каждом прогоне начинается заново (с 1 или с начала выданного диапазона), поэтому email вида `1vladislav…` в разных прогонах совпадают — сверяй с CRM по времени и по тексту сообщения (в нём есть `{прогон}`), а не только по email.
- Телефон: номер из зарезервированного NANPA-блока для тестового использования — `+1 (555) 555-01XX` (например `+1 (555) 555-0101`). `XX` — **не номер сабмита `N`**, а отдельный локальный счётчик текущего агента (свой у каждого агента, начинается с `01`, +1 на каждый реальный сабмит, без координации с другими агентами). Это только визуальный признак «это тест агентства», не ключ для сверки — по всему прогону уникальность `XX` не гарантируется. Это официально выделенный под тест/вымышленные номера диапазон в США, не принадлежит реальному абоненту ни при какой area code.
- Адрес (если есть автоподбор адреса, например для relocation-форм с полями «Адрес начальный»/«Адрес конечный»): любой реальный публичный адрес, например `350 5th Ave, New York, NY 10118`.
- Свободный текст / сообщение (когда поле есть) — дублирующий, более подробный канал: `TEST MESSAGE FROM QA TEAM, PLS IGNORE. Submission #N. Run: {прогон}. Submitted from: [URL страницы, с которой отправлен сабмит] | Form: [идентификатор формы]`. Идентификатор формы — это `id`/`name`-атрибут формы (или технический ID из раздела «Как определить...» выше) из разметки, если он есть; если технического ID в разметке нет — короткое описательное имя (например «footer contact form», «hero quick-quote»). Нужно, чтобы в CRM можно было отличить, какая именно форма прислала заявку, если их на бэкенде несколько.

## Граничные значения — проверяй не только телефон, а все применимые поля
**Для полей с визуальной маской/форматированием (телефон, дата и т.п.) — каждое граничное значение проверяй ДВУМЯ реалистичными способами ввода, не одним:** настоящим посимвольным вводом (по одной клавише) И настоящей вставкой (эмулируй реальный paste — не программной подстановкой `.value`/`fill()` в обход событий клавиатуры/вставки). **Как это делается в `playwright-cli`** (проверено на `eval/fixture-site/index.html`, поле Phone): посимвольный ввод — клик в поле, затем `playwright-cli -s=<сессия> press <клавиша>` по одной клавише либо `playwright-cli -s=<сессия> type "<текст>"` (нажимает клавиши по одной, генерирует `keydown`); вставка — `playwright-cli -s=<сессия> run-code "async page => { await page.click('<селектор>'); await page.keyboard.insertText('<текст>'); }"` (событие `input` без `keydown`, как при вставке из буфера) либо через буфер обмена: `page.context().grantPermissions(['clipboard-read','clipboard-write'])`, `navigator.clipboard.writeText('<текст>')` внутри `page.evaluate`, клик в поле и `page.keyboard.press('Control+V')`. Искусственное `dispatchEvent(new ClipboardEvent('paste'))` значение в поле не вставляет — не используй. Маскирующий скрипт нередко ведёт собственное внутреннее состояние, синхронизирующееся с DOM по-разному в зависимости от способа ввода — расхождение результата между способами может быть либо реальным багом (тогда фиксируй оба наблюдения — какой способ ломается, какой нет), либо артефактом того, что протестирован только один способ. **Расхождение между способами ввода — ещё не готовый баг (общий принцип см. `CLAUDE.md`, «Обработка ошибок»):** если один способ ввода показал подозрительный результат, а другой не проверялся — не фиксируй находку до перепроверки вторым способом; доведи проверку до конца: проследи механизм пошагово — по нажатию клавиши (`run-code`, логируя `el.value` после каждого символа), а не только сравнивай финальное значение до/после. Отличай тихую порчу данных (значение меняется на другое, отличное от введённого, без видимого пользователю сигнала — баг) от ограничения ввода (поле просто перестаёт принимать нажатия по достижении лимита длины, значение не меняется, пользователь видит это в реальном времени — не баг). И в обоих случаях доведи проверку до реального сабмита с этим граничным значением — подозрительное значение в поле само по себе не значит, что дефектные данные дойдут до CRM; если форма блокирует отправку и подсвечивает поле как невалидное, защита сработала правильно.
- Телефон (исторически самое проблемное поле): с `+1` и без, со скобками/дефисами и без, с недостаточным/избыточным числом цифр — маска должна нормализовать ввод и не пропускать некорректную длину.
- ZIP: буквы вместо цифр, слишком короткий/длинный.
- Email: без `@`, без домена, странные символы.
- Числовые поля калькулятора: 0, отрицательное значение, очень большое число, дробное там, где ожидаются целые.
- Текстовые поля с `maxlength`: значение на грани лимита и сверх него.
- Обязательные текстовые поля (имя, сообщение и т.п.): значение только из пробелов (например, три пробела без другого текста) — должно блокироваться так же, как пустое поле, а не приниматься как заполненное.
- **Случайный пробел сбоку от иначе полностью валидного значения** (не путать с пунктом выше — здесь само значение корректное, лишний только пробел по краю): например, email со случайным пробелом в начале или конце (`" vladislav.k@comradeweb.com"` или `"vladislav.k@comradeweb.com "`), телефон с пробелом перед/после номера. Это реалистичный кейс — именно так выглядит значение, если пользователь скопировал его откуда-то (письмо, визитка, другая форма) и случайно задел пробел рядом. Проверь на email и на телефон (посимвольным вводом с пробелом в начале/конце — см. правило про способы ввода выше, для телефона это тоже граничное значение маски). Ожидаемое поведение: форма должна либо тихо обрезать пробел по краям (trim) и принять значение как есть, либо явно показать ошибку валидации, если строго связана с наличием пробела. Баг — если пробел молча проходит валидацию AND реально уходит в теле сетевого запроса внутри значения (испорченный email/телефон в заявке; проверяется через `playwright-cli -s=<сессия> request-body <индекс>`) без обрезки и без ошибки.
- Дата (если есть поле с датой, отдельно от общего правила про маски выше): недопустимый день месяца (31 число в 30-дневном месяце, 29 февраля не в високосный год), дата в прошлом или неправдоподобно далеко в будущем — если по смыслу поля должны быть ограничения (например, дата переезда не может быть в прошлом), неверный формат ввода.
- Загрузка файла (если есть такое поле, например резюме в форме отклика на вакансию): файл неподходящего типа (если задан `accept`), файл сверх лимита размера (если лимит виден в разметке или тексте рядом с полем), пустой файл — форма должна отклонять некорректный файл с понятным сообщением, а не падать молча/зависать. Для нелид-форм (лёгкий протокол) граничные проверки загрузки не выполняются. Для валидного сабмита создай крошечный безобидный файл во временной папке ВНЕ `projects/{домен}/` (`mktemp -d`, в `playwright-cli -s=<сессия> upload` передавай абсолютный путь) и удали его после сабмита. Если `upload` отклонил путь вне рабочей папки — положи файл в `.playwright-cli/upload-tmp/` и удали после сабмита.

## Техническая верификация каждого сабмита (обязательна после любого клика Submit, для каждого сабмита — не только когда видно визуальный сбой)
Визуальный результат (появилась confirmation, произошёл редирект/reload, ничего видимо не изменилось) — недостаточное основание для вывода об успехе или неудаче. Подтверждай факт отправки данных технически:
1. **Перед кликом** очисти списки: `playwright-cli -s=<сессия> requests --clear` и `playwright-cli -s=<сессия> console --clear` (иначе в списках остаются прошлые сабмиты и подсчёт запросов при двойном клике неоднозначен). **Для формы с полной перезагрузкой страницы** POST принадлежит уходящему документу и после навигации в `requests` не появится — до клика перехвати его через `run-code`: `async page => { page.__posts = []; page.on('request', r => { if (r.method() !== 'GET') page.__posts.push(r.method() + ' ' + r.url() + ' ' + (r.postData() || '')); }); }`, а после клика прочитай `JSON.stringify(page.__posts)` следующим `run-code` (проверено на фикстуре; использовать `globalThis` вместо `page.__posts` нельзя — не сохраняется между вызовами). Сразу после клика сними список сетевых запросов (`playwright-cli -s=<сессия> requests`) и найди тот, что соответствует реальной отправке формы — по признакам, а не по названию (оно на каждом сайте своё): метод POST/PUT, тайминг сразу после клика, payload содержит значения только что введённых полей.
2. Проверь статус-код и содержимое ответа этого запроса на признак успеха/неудачи — что бы это ни было конкретно на этом сайте (JSON с `success`/`error`, HTTP-редирект на thank-you URL, специфичный статус-код и т.п.).
3. **Если такого запроса не нашлось вообще** (проверь и `requests`, и перехват `page.__posts`; по одному лишь списку `requests` после навигации вывод «запроса не было» не делай) — это самостоятельный технический признак, что сабмит не дошёл, даже без видимой ошибки. Исключение — граничные/невалидные сабмиты (Сабмит №1 и граничный вариант Сабмита №4, см. ниже): там отсутствие такого запроса — ожидаемый правильный результат (форма должна была заблокировать отправку на клиенте); если запрос всё же ушёл с невалидными данными и ответ сервера — успех (лид создан) — вот это баг; если ответ — ошибка валидации сервера (лид не создан) — это ожидаемая работа серверной валидации, не баг.
4. Проверь консоль (`playwright-cli -s=<сессия> console error`) в узком окне вокруг самого клика Submit (непосредственно до/во время/после) — отдельно от разового прохода по консоли всей страницы в `technical-checks` (тот не привязан по времени к моменту сабмита и может его не поймать). JS-исключение внутри обработчика сабмита может тихо сорвать отправку без единого видимого признака для пользователя.

## Порядок сабмитов
Потолок сабмитов на шаблон — см. «Лимит» выше; к каждому сабмиту применяй техническую верификацию выше. Все сабмиты делай только на десктопной сессии (Chrome): при проходе той же страницы на мобилке/планшете форму не сабмить. Единственное исключение — «Троттлинг-тест», он идёт отдельно на мобильной эмуляции. «Сабмит №1–№4» ниже — это названия шагов протокола, а не сквозной номер `N`: в email, тексте и таблице отчёта используется только `N`. На пункты списка в ссылках ссылайся по именам («Защита от дублирования», «Точечная перепроверка (Сабмит №4)», «Троттлинг-тест»), а не по порядковому номеру пункта: нумерация списка не совпадает с номерами «Сабмит №N».
1. **Сабмит №1 (граничный/невалидный кейс), десктоп:** оставь один-два обязательных поля пустыми или впиши граничное невалидное значение (см. выше) — форма не должна создать лид: заблокировать отправку на клиенте (запроса нет, см. пункт «Если такого запроса не нашлось вообще» верификации выше) либо отклонить её сервером ошибкой валидации, и в обоих случаях показать ошибку именно у нужного поля. Если обязательный чекбокс есть — оставь его неотмеченным на этом шаге. Отклонение пустого значения у КАЖДОГО обязательного поля с нативным `required` проверяй без реального сабмита (`eval`: `checkValidity()`/`validity.valueMissing` или блокировка клиентской валидации). Для полей без нативного `required` (обязательность через `aria-required`/класс валидации, серверная валидация) `checkValidity()` ничего не покажет — проверяй реальным пустым сабмитом: все такие пустые обязательные поля вместе, одним сабмитом (это и есть граничный кейс Сабмита №1). Других реальных сабмитов с пустыми обязательными полями не делай (потолок — см. «Лимит»); Сабмит №2 оставляет пустыми только необязательные поля.
2. **Сабмит №2 (валидный кейс, ТОЛЬКО обязательные поля), десктоп:** заполни валидными данными **только те поля, что реально обязательны по факту** (по карте полей Шага 0 — включая случаи, где обязательность реализована не через `required`, а через `aria-required`/класс валидации), необязательные оставь пустыми. Отметь обязательный чекбокс, если есть. Цель — реалистичный сценарий: многие реальные пользователи заполняют только помеченное звёздочкой и пропускают остальное; форма и бэкенд должны нормально это принимать. Подтверди сабмит технически, как любой другой (см. верификацию выше). **Если сабмит неожиданно заблокирован на поле, которое не было помечено как обязательное ни визуально, ни атрибутом** — это самостоятельный баг (поле фактически обязательно, но нигде не заявлено таким), отдельный от того, что ловит Сабмит №1 (там наоборот — заявленно обязательное поле должно блокировать).
3. **Сабмит №3 (валидный кейс, ВСЕ поля), десктоп:** заполни **все** поля формы — обязательные и по возможности необязательные, чтобы не оставить пустым что-то, что реально требуется. Для стандартных полей — тестовые данные из списка выше; для всего остального — значения, подготовленные на Шаге 0 (пункт про поля вне фиксированного списка тестовых данных). Отметь обязательный чекбокс. Только когда ты уверен, что заполнено всё видимое обязательное поле — отправляй. **Прежде чем зафиксировать «сабмит не проходит» или «поле некорректно валидируется» как баг, сначала проверь снапшотом/eval, какое именно поле блокирует отправку.** Если это поле, которое ты сам не заполнил (недосмотр, а не баг сайта) — это не баг: заполни его и продолжай, не трать на это отдельный сабмит из потолка. Багом это становится только если поле было заполнено корректно, а форма всё равно не проходит (по критериям технической верификации выше, не только по визуальному сообщению об ошибке).
4. **Защита от дублирования лида (сразу после успешного Сабмита №3, данными как в Сабмите №3, но с новым `N` — отдельного сабмита из потолка 10 не тратит):**
   - **Двойной клик:** если форма отправляется через AJAX (JS перехватывает submit — после отправки страница обновилась на месте без полной навигации/reload, а не как обычный `<form action>` с полной перезагрузкой) — заполни форму ещё раз данными как в Сабмите №3 (с новым `N`), перед кликом выполни `requests --clear` и `console --clear` (см. верификацию выше) и кликни Submit дважды быстро подряд (второй клик — до завершения первого запроса, пока кнопка ещё выглядит активной). Через сеть (`playwright-cli -s=<сессия> requests`) убедись, что реальная отправка данных ушла ровно **одна**, а не две. Если кнопка не блокируется на время отправки и ушло два запроса (два лида в CRM от одного клика пользователя) — это баг. В таблице «Что было отправлено» такой сабмит — одна строка, один `N`, пометка «×2 запроса» (два лида в CRM от одного клика).
   - **Повторная отправка после «Назад» в браузере:** после успешного Сабмита №3 вернись «назад» на страницу с формой и проверь, не ушла ли отправка повторно сама (например, если пользователь машинально жмёт «назад»). Если форма после отправки увела на другую страницу (редирект на страницу благодарности) — просто нажми «назад». Если форма AJAX и страница осталась на месте — «Назад» здесь = уйти на любую другую страницу сайта (по ссылке) и нажать «назад», вернувшись на страницу с формой; если вернуться на страницу с формой таким способом нельзя, пункт неприменим — так и запиши. Дефект — только если повторная отправка произошла **без клика по Submit** (автосабмит, восстановление страницы из bfcache с повторной отправкой, повтор POST): зафиксируй находку 🟨 Major (риск случайного дубля лида, сам лид не теряется), не 🟥. Если данные просто остались в полях, а отправка требует явного клика — это не находка. Исключение из общего правила для лид-форм зафиксировано в CLAUDE.md, «Критерии серьёзности».
5. **Точечная перепроверка (Сабмит №4), всегда обязательна — не только когда что-то найдено:** если Шаг 0, Сабмит №1 или Сабмит №2 выявили конкретное противоречие, которое иначе не подтвердить однозначно — целься именно в него, на десктопной сессии. **Если явного противоречия не нашлось — это не повод пропускать сабмит:** проверь дополнительный реалистичный граничный кейс, ещё не покрытый Сабмитом №1 (другое поле с маской/лимитом из списка «Граничные значения» выше, либо тот же граничный сценарий вторым способом ввода — например, Сабмит №1 проверял телефон посимвольным вводом, здесь проверь его же вставкой (paste), см. правило про способы ввода выше). Цель — дополнительная уверенность в форме всегда, а не только в момент, когда уже что-то заподозрено.
6. **Троттлинг-тест (сабмит под искусственно замедленной сетью), всегда обязателен для лид-генерирующих форм (сверх сабмитов №1–№4, которые идут только на десктопе):** выполни ещё один валидный сабмит на мобильном разрешении под искусственным троттлингом сети (намеренно более жёсткий профиль: ~50 кбит/с, задержка 2000 мс) — независимо от того, AJAX это форма или обычный `<form action>` с полной перезагрузкой страницы (на AJAX-формах она провоцирует race condition в асинхронной загрузке JS-скриптов, на обычных — вскрывает проблемы медленной сети, например таймаут сервера или потерю введённых данных при обрыве соединения). Этот сабмит **не входит** в потолок (см. «Лимит»): потолок — про варианты тестовых данных, а троттлинг — отдельная проверка тайминг-зависимых багов. Не повторяй троттлинг-тест больше одного раза на шаблон формы за прогон — если он ничего не показал, этого достаточно.

   Технически: троттлинг через CDP работает только в Chromium — WebKit его не поддерживает. Поэтому для этой проверки открой отдельную именованную сессию — мобильная эмуляция в Chromium, не буквально WebKit-сессия основных проверок:
   ```bash
   playwright-cli -s=throttle-mobile-<суффикс> open --mobile --browser=chrome <URL>
   playwright-cli -s=throttle-mobile-<суффикс> run-code "async page => { const client = await page.context().newCDPSession(page); await client.send('Network.enable'); await client.send('Network.emulateNetworkConditions', { offline: false, downloadThroughput: 50*1024/8, uploadThroughput: 50*1024/8, latency: 2000 }); }"
   ```
   Страница и языковая версия — те же, что в Сабмите №3; если DEV закрыт паролем — сначала `playwright-cli -s=throttle-mobile-<суффикс> state-load .playwright-cli/state-{домен}.json` (файл авторизации, см. CLAUDE.md, Шаг 2; при Basic-окне браузера — открой URL с логином и паролем, там же). Дальше заполни форму теми же полями, что и в Сабмите №3 (все поля), но с НОВЫМ `N` (в email и тексте) и следующим локальным `XX` для телефона, отправь и примени ту же техническую верификацию (сетевой запрос + консоль). Закрой сессию (`playwright-cli -s=throttle-mobile-<суффикс> close`) по завершении. `<суффикс>` — уникальный суффикс подагента из промпта оркестратора (для единственного агента — `solo`).
7. Для калькуляторов: **ТЗ на формулу расчёта можно передать в `Сайты.txt` (блок `Комментарии:`) — если оно есть, сверь результат с ним точно.** Но по умолчанию считай, что ТЗ передано НЕ будет — это обычный случай, а не исключение. Без ТЗ агент не оценивает точность формулы (не его компетенция без спецификации), а проверяет только устойчивость и правдоподобность по конкретным критериям:
   - Прогони несколько реалистичных сценариев (не только границы 0/отрицательное/пустое поле) — результат не падает, не показывает `NaN`/пустое значение/отрицательное число там, где это не имеет смысла.
   - Монотонность: при увеличении одного вводного значения (например, расстояние, объём, количество комнат) итоговая величина меняется в ожидаемую сторону (обычно растёт), а не наоборот — без явной бизнес-причины для обратной зависимости.
   - Калькулятор реагирует на ввод: разные вводные данные дают разный результат, а не одно и то же число независимо от того, что ввели (нередкий баг — калькулятор фактически ничего не считает).
   - Один и тот же ввод даёт один и тот же результат при повторном расчёте (детерминированность), если не задумана намеренная случайность.
   - **Внутренняя арифметическая согласованность (критический уровень проверки, не требует знания формулы):** если калькулятор показывает разбивку итоговой суммы (например, база + доп. услуги + итог) — сложи показанные компоненты и убедись, что сумма реально равна показанному итогу. Расхождение — баг, причём это не догадка о бизнес-логике, а проверяемый факт, фиксируется как находка с тегом `[Form]` (см. CLAUDE.md, «Что реально печатается в отчёт»). Если разбивки нет (калькулятор выдаёт только одно число) — глубже без ТЗ не проверяется, это предел.
   Зафиксируй в отчёте «ТЗ на логику калькулятора не предоставлено — сверка с реальной формулой не проводилась, нужно запросить у ПМа», но саму устойчивость, правдоподобность и внутреннюю согласованность результата (по критериям выше) всё равно проверь и опиши — это не освобождает от проверки, а лишь ограничивает её без точной формулы.

   **Калькулятор без отправки лида** (нет `<form>`/submit с заявкой, результат считается на клиенте; например, только поле расстояния и кнопка «Calculate»): выполняется эта проверка калькулятора (устойчивость, монотонность, реакция на ввод, детерминированность, арифметика разбивки) и граничные числа из «Граничные значения» (0, отрицательное, очень большое, дробное). Не применяются: номер `N`, тестовые данные, маркер, «Защита от дублирования», «Троттлинг-тест». Идентификация — по `id`/заголовку/тексту рядом; маркера у него нет (не сабмитился): верни калькулятор в тексте (страница, `id`/заголовок), оркестратор внесёт его в «Карту форм по сайту» с пометкой «не сабмитился» и причиной. Если калькулятор в итоге отправляет заявку (форма с контактами после расчёта) — эта отправляется по полному протоколу как лид-генерирующая форма.
8. Держи в памяти для колонки «Thank-you (URL либо текст успеха + статус ответа)» таблицы «Что было отправлено» (см. CLAUDE.md, «Что реально печатается в отчёт»): статус ответа + текст inline-сообщения об успехе, либо URL страницы благодарности. Если после успешного ответа сервера нет ни редиректа, ни видимого сообщения (проверь `snapshot`/`eval` после паузы, а не по первому кадру) — в колонке пиши «нет (редиректа и сообщения нет) + статус ответа» и добавь находку `[Form]` «после отправки нет подтверждения для пользователя» (серьёзность — по CLAUDE.md, «Критерии серьёзности → Формы»; доказательство — статус и тело ответа из сети плюс состояние страницы после сабмита). Это относится к каждому успешному сабмиту (и результат технической верификации по нему) — это понадобится для рекомендации проверить админку/почту в итоговом отчёте.

## Возвращаемый результат
- Для каждой лид-генерирующей формы: технический признак, по которому определён шаблон (ID/набор полей/только визуально — см. раздел выше), карта полей (визуал vs `required`, найденные противоречия), результат каждого сабмита (что вводилось → что произошло технически, сеть+консоль → вывод: прошло/не прошло), **номер сабмита (см. «Сквозная нумерация» выше) и «статус ответа + текст сообщения об успехе или URL страницы благодарности»** успешного сабмита, результат проверки на дублирование (двойной клик / повторная отправка после «назад»), результат обязательного «Троттлинг-теста» (см. «Порядок сабмитов»).
- **Полный список всех страниц, где этот шаблон формы встретился за прогон** (не только страница, где сделан сабмит) — нужен для таблицы «Карта форм по сайту» (структура — в CLAUDE.md); для сабмиченных форм координируется через поле `pages` в файле-маркере (см. «Координация между параллельными агентами»), для несабмиченных (без модерации, антибот, калькулятор без отправки лида) — верни страницы в тексте.
- Для каждой «прочей» формы (лёгкий протокол): что вводилось, технический результат сабмита (сеть+консоль), вывод — подтверждена отправка технически или нет, номер сабмита и «статус ответа + текст сообщения об успехе или URL страницы благодарности».
- Если форма (любой категории) определена как уже протестированный где-то ещё переиспользуемый шаблон — явно укажи это и на основании какого признака, без повторного сабмита.
- Если найдена форма, публикующая публичный контент без модерации (см. исключение выше) — укажи её в «Технические детали → Не проверено» (с причиной) и в «Рекомендации для ручной проверки» с вопросом пользователю; прогон при этом не прерывается; маркера у неё нет, в «Карту форм по сайту» её вносит оркестратор с пометкой «не сабмитилась» и причиной.
- Если проблем не найдено — «Функциональных проблем в формах не обнаружено».
