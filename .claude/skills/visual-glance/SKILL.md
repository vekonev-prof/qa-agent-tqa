# Визуальный просмотр

`visual-checks` работает по DOM и геометрии и не «видит» страницу. Здесь ты смотришь на неё глазами — по скриншотам — и ищешь только то, что по DOM определить нельзя. Не запускай здесь DOM-проверки (`page-audit`, `eval` для поиска дефектов) — смотри глазами; пересечения с `visual-checks` §1 и `content-checks` §2 допустимы, дубли снимает оркестратор, в одиночном прогоне — сам агент.

## Входные данные
Список URL шаблонов — по одной странице на каждый шаблон из выборки Шага 1 (каждый лендинг — отдельно), готовая рабочая папка прогона `projects/{домен}/{прогон}/` (её передаёт оркестратор), уникальный суффикс сессий; на мультиязычном сайте — ещё и URL второй языковой версии каждого шаблона и главной. Отдельно — URL главной страницы основного сайта (для раздела «Меню»; если главная не входит в список шаблонов, он всё равно передаётся); URL страницы 404 и страницы «спасибо» после формы, если они известны (для раздела «Служебные страницы»; если не переданы — 404 открывается по несуществующему адресу основного сайта, а страница «спасибо» не просматривается и это отмечается в результате). Объём работы: «страницы» (только кадры шаблонов, интерактив, формы, чат; меню и служебные страницы не делать), «меню и служебные» (только раздел «Меню» и страницы 404 и «спасибо») или не указан (делай всё — типично для одиночного прогона). Признак «планшет включён» (`Визуальный просмотр планшета: да` в `Сайты.txt`) оркестратор передаёт, только если пользователь явно запросил просмотр планшета; без этого признака планшет не снимается вовсе. Если DEV закрыт паролем — ещё и путь файла авторизации (по умолчанию `.playwright-cli/state-{домен}.json`). Нет чего-то из обязательного в промпте — верни вопрос, а не угадывай. Исключение — одиночный агент, выполняющий шаг сам (CLAUDE.md, Шаг 3.3): `solo` — если суффикс не передан в промпте; рабочая папка и страницы у него уже есть.

**Что читать из CLAUDE.md (подагенту `tqa-visual-agent`; номера строк заголовков — `grep -n '^#' .claude/CLAUDE.md`, дальше Read по диапазону):** только «Шаг 2» (диалоги, баннеры, вход на закрытый DEV), «Шаг 4» (пути, санитизация `{страница}`) и «Критерии серьёзности» (серьёзность); остальное не нужно. `page-audit.js` в этом skill не запускается.

## Как снять кадры
Для каждого URL: десктоп (и планшет, если включён) — 3 кадра (верх страницы, середина, футер); мобилка — от 3 до 6 кадров по длине страницы (по одному кадру на экран: мобильный кадр примерно в 4 раза дешевле десктопного, а длинная мобильная страница иначе остаётся почти не просмотренной). Лишних кадров не делай (кадры меню, интерактива страницы, форм и служебных страниц — отдельно, по разделам ниже; в основные они не входят). После открытия сессии и до первого кадра закрой cookie-баннеры и попапы (как в CLAUDE.md, Шаг 2; при диалоге — `playwright-cli -s=<сессия> dialog-dismiss`), иначе они попадут на все кадры. Кадры страницы (верх, середина, футер) снимаются в двух разрешениях из таблицы ниже — десктоп и мобилка; планшет — только если в промпте передан признак «планшет включён» (тогда те же 3 кадра), без него сессию планшета не открывай; альбомный 844×390 снимается только для меню (раздел «Меню»), страница целиком в нём не просматривается. Язык на мультиязычном сайте — по правилу CLAUDE.md, Шаг 2: десктоп и планшет — основная версия, мобилка — вторая (её URL передаёт оркестратор; одиночный агент находит его сам по правилу Шага 2).

| Разрешение | Открытие сессии |
|---|---|
| Десктоп | `PLAYWRIGHT_MCP_VIEWPORT_SIZE=1920,1080 playwright-cli -s=glance-desktop-<суффикс> open <URL> --browser=chrome` |
| Планшет (только если включён) | `PLAYWRIGHT_MCP_VIEWPORT_SIZE=768,1024 playwright-cli -s=glance-tablet-<суффикс> open <URL> --browser=webkit` |
| Мобилка | `PLAYWRIGHT_MCP_VIEWPORT_SIZE=390,844 playwright-cli -s=glance-mobile-<суффикс> open <URL> --browser=webkit` |
| Мобилка, альбомная (только меню) | `PLAYWRIGHT_MCP_VIEWPORT_SIZE=844,390 playwright-cli -s=glance-landscape-<суффикс> open <URL главной> --browser=webkit` |

```bash
# сколько кадров на мобилке: от 3 до 6 по длине страницы (десктоп и планшет — всегда 3)
playwright-cli --raw -s=<сессия> eval "Math.min(6, Math.max(3, Math.ceil(document.documentElement.scrollHeight / innerHeight)))"
# при N кадрах k-й кадр (k = 0 … N-1) — прокрутка на долю k/(N-1) от максимума: 3 кадра — 0, 0.5, 1; 6 кадров — 0, 0.2, 0.4, 0.6, 0.8, 1
# ниже пример для 3 кадров: верх, середина, низ (после каждого скролла подожди ~1 с — догружаются lazy-картинки)
playwright-cli -s=<сессия> eval "window.scrollTo(0, 0)"
playwright-cli -s=<сессия> screenshot --filename=.playwright-cli/glance/{страница}_{разрешение}_1.png
playwright-cli -s=<сессия> eval "window.scrollTo(0, (document.documentElement.scrollHeight - innerHeight) / 2)"
playwright-cli -s=<сессия> screenshot --filename=.playwright-cli/glance/{страница}_{разрешение}_2.png
playwright-cli -s=<сессия> eval "window.scrollTo(0, document.documentElement.scrollHeight)"
playwright-cli -s=<сессия> screenshot --filename=.playwright-cli/glance/{страница}_{разрешение}_3.png
```
**Если DEV под паролем** — сразу после `open` загрузи авторизацию: `playwright-cli -s=<сессия> state-load <путь>` (путь передаёт оркестратор; по умолчанию `.playwright-cli/state-{домен}.json`) и перезагрузи страницу; без этого на кадрах будет окно входа. Если DEV закрыт окном Basic-авторизации браузера — открывай URL с логином и паролем, см. CLAUDE.md, Шаг 2.

Кадры лежат во временной папке `.playwright-cli/glance/` (не в `projects/{домен}/`); номер в имени — порядковый (`_1` — верх страницы и первый экран, последний — футер). **Кадры просматривай пачкой, а не по одному:** сними серию кадров подряд, затем одним сообщением вызови `Read` для всех кадров серии параллельно (каждый шаг заново читает весь накопленный контекст, а картинки остаются в нём до конца работы, поэтому меньше шагов — дешевле). Серии: основные кадры страницы; весь интерактив страницы; меню — фаза 1, затем интерактив меню, затем фаза 2 (по каждому разрешению); служебные страницы. Ход обхода (открылось ли подменю, сработал ли клик, куда ведёт «назад») определяй текстом — `snapshot`, `eval`, `aria-expanded`, — а не по кадру; кадры смотри после серии. Закрой сессию тем же именем в конце.

## Что искать
- [ ] Картинка не загрузилась: пустая рамка, значок битого изображения, видна только подпись `alt`. **Кроме `.avif` на WebKit-кадре (планшет, мобилка) — это ограничение инструмента, не дефект** (см. «AVIF в WebKit» ниже).
- [ ] Картинка искажена: растянута/сплющена (круг выглядит эллипсом, лицо вытянуто), обрезана так, что теряется главное.
- [ ] Текст или кнопка обрезаны (видна только часть надписи), текст выходит за рамку блока.
- [ ] Колонки/карточки выглядят съехавшими: неровные высоты и отступы там, где по логике блоки должны быть в один ряд; лишние огромные пустоты внутри блока (не декоративные разделители).
- [ ] Текст лежит поверх картинки/другого текста и не читается.
- [ ] Sticky/fixed-элемент или чат-виджет перекрывает контент, кнопку звонка или форму (cookie-баннер сюда не входит — он закрыт до кадров). **Перекрытие на одном кадре прокрутки — НЕ находка**: fixed-элемент (плашка рейтинга, кнопка «наверх», кнопка фильтров, чат) по природе лежит поверх контента, а при прокрутке контент выезжает из-под него — кадр фиксирует лишь один момент. Находка — только если перекрытие нельзя убрать прокруткой. Проверяй измерением, а не по кадру: прокрути в самый низ (`window.scrollTo(0, document.documentElement.scrollHeight)`) и для интерактивных элементов и текстов в нижней зоне экрана (последние строки и ссылки футера, кнопка отправки, телефон) сравни `getBoundingClientRect()` с прямоугольником fixed-элемента или проверь `document.elementFromPoint` в центре элемента — возвращает ли он сам элемент, а не fixed-слой; то же для постоянно видимой зоны первого экрана на scrollY = 0, если элемент не может её покинуть. Серьёзность — только если перекрытие воспроизвелось на максимальной прокрутке (или постоянно, независимо от прокрутки): 🟥 — закрыты CTA, форма, телефон или меню; 🟨 — закрыты текст или второстепенная ссылка. Если fixed-элемент закрывается крестиком, у него есть крестик и перекрытие проходит при прокрутке — это не находка. Перекрытие, видимое только в промежуточной позиции прокрутки (в т.ч. заголовок Hero на первом экране, срезанный плашкой в альбомной ориентации), — только в «Рекомендации для ручной проверки» одной строкой с пометкой «пропадает при прокрутке». «Массово» серьёзность не повышает: один и тот же сквозной fixed-элемент — одна запись на сайт.
- [ ] Блок карты не работает как карта: водяной знак «For development purposes only», серый квадрат вместо карты, надпись об ошибке, пустое поле. Это находка `[Visual]` 🟨 (допустимо описать и русские подписи на карте в той же записи), а не «Рекомендация»; сомнение может касаться только того, что показ карты вообще не нужен.
- [ ] Мобилка/планшет: горизонтальный скролл страницы, контент выходит за экран, цели тапа слишком близко друг к другу.
- [ ] Шапка и футер на разных шаблонах выглядят по-разному без причины (другой логотип, порядок пунктов, шрифт).
- [ ] Однотипные элементы оформлены по-разному внутри одного блока: например, одна ссылка футера в цвете браузера по умолчанию (синяя, подчёркнутая), а остальные белые; кнопка без стиля среди оформленных. Это несогласованность стиля, а не контраст: фиксируй `[Visual]` 🟩 (какой элемент и чем он отличается от соседних), даже если на тёмном фоне он плохо читается.

**Не проверяй здесь и не упоминай:** работоспособность виджетов и форм по DOM и клику (раскрывается ли аккордеон, переключается ли таб, валидация и сабмит — это `visual-checks` §8/§9, Шаг 3.2 и `form-submit-checks`; здесь — только то, что видно на кадре), DOM-факты по меню (число `nav` и дубли наборов ссылок, область тапа, `tel:` в шапке — это `visual-checks` §6), ADA, контраст и доступность (это WAVE/axe: числа контраста, WCAG, подписи без `aria-label`), вкусовые оценки дизайна. Исключение — пункт про однотипные элементы выше: цвет, выбивающийся из соседних, фиксируй как несогласованность стиля, не как контраст. Если находка совпадёт с находкой page-агента (DOM/`page-audit`) — просто верни её: дубли снимает оркестратор при сборке отчёта (в одиночном прогоне — сам агент, объединяя с находками `visual-checks`/`content-checks`).

## Первый экран (Hero) — кадр 1
Кадр 1 («верх страницы») одновременно служит кадром первого экрана. Перед ним после `open` подожди ~2 с (дорисовываются фото, видео-фон, первый слайд Hero-слайдера); слайдер Hero не листай — это раздел «Интерактив страницы». Смотри на кадр 1 отдельным списком:
- [ ] Фото или видео-фон Hero отрисованы (не пустая рамка, не сплошной цвет на месте фото; `.avif` на WebKit-кадре — ограничение инструмента, см. «AVIF в WebKit»).
- [ ] Заголовок и подзаголовок различимы на фоне: текст не сливается с фоном (оцениваем глазами, без расчёта контраста).
- [ ] Заголовок не обрезан, не выходит за край экрана, не налезает на лицо или ключевую часть фото.
- [ ] Если в Hero есть CTA-кнопка, телефон или форма — они видны целиком, не обрезаны и не закрыты другим элементом.
- [ ] Hero не выглядит «сломанным»: нет огромной пустоты, наложения блоков, текст не выходит за рамку блока.
Серьёзность — по «Критериям серьёзности» CLAUDE.md (раздел «Визуальные»): дефект Hero на проверяемой странице — 🟨 `[Visual]`; если ту же поломку показал `hero-probe.js` (`visual-checks` §1а) на других страницах шаблона или она видна на кадрах всех проверенных шаблонов, оркестратор объединяет находки и поднимает до 🟥 (Hero сломан во всём шаблоне или на всём сайте). Сомнительное («возможно, так задумано») — только в «Рекомендации».

## Фиксированные элементы — на всех кадрах страницы
На каждом основном кадре страницы (верх, середина, футер и промежуточные кадры мобилки) отметь все фиксированные и липкие элементы: шапку, плашку, чат-кнопку, кнопку «наверх», нижнюю панель «Call now» и т.п. Они не должны закрывать заголовки, текст, CTA, поля формы, телефон, ссылки футера **при любой прокрутке, включая максимальную** (то, что пропадает при прокрутке, находкой не считается; как проверять и какая серьёзность — п. выше про sticky/fixed-элемент в «Что искать»). Дополнительно — чат-виджет (сквозной компонент): раскрывается только при объёме работы «меню и служебные» (или если объём не указан), один раз на разрешение (десктоп, мобилка), на главной; при объёме «страницы» чат не раскрывай и в результате пиши «чат: за агентом меню». Исключение — чат, который есть только на лендинге: на лендинге раскрой его один раз. Если на главной чата нет — «чата на главной нет». Как смотреть: если на странице есть кнопка чата, раскрой её один раз (клик; ничего не вводи, формы чата не заполняй, сообщений не отправляй) и сними кадр открытого окна: окно помещается в экран, у него есть видимый крестик закрытия, закрытие работает (кадр после закрытия), окно не закрывает телефон и CTA без возможности закрыть. Если чат до открытия требует ввода данных или открывается в другой вкладке — кадр и пометка в результате, дальше не иди. Раскрытый чат, закрывающий телефон или CTA, который нельзя закрыть, — 🟥 (чат закрывает CTA, телефон или меню — «Критерии серьёзности», «Визуальные»); окно вылезает за экран или нет крестика, но телефон и CTA остаются доступны, — 🟨 `[Interactive]`. Кадры чата не входят ни в потолок меню, ни в потолок интерактива: не больше 3 кадров чата на разрешение (закрыто, открыто, после закрытия).

## Интерактив страницы (на странице каждого шаблона из выборки)
Здесь ты смотришь, как выглядит страница после действий пользователя. Работает ли виджет (раскрывается ли, переключается ли) по DOM и клику проверяют `visual-checks` §9 и Шаг 3.2 CLAUDE.md — не дублируй их; ты смотришь на кадр результата и фиксируешь дефект, который виден глазами, плюс очевидную неработоспособность (кликнул — на кадре ничего не изменилось). Раздел выполняется на десктопе и мобилке; планшет в этом разделе не снимается даже при включённом просмотре планшета (там — только 3 кадра на шаблон, первый экран, меню и страница 404).

**Когда:** после основных кадров страницы, в той же сессии. Действия меняют состояние страницы, поэтому перед каждой новой группой действий (после модалки, чата, форм) перезагрузи страницу (`playwright-cli -s=<сессия> reload`) и прокрути наверх; после перезагрузки адреса `ref` меняются (префикс, например `f1e22`) — перед кликами сними свежий `snapshot`, а вывод команд проверяй на `### Error`.

**Как найти виджеты** (допустимо использовать `snapshot` и `eval` для поиска элементов; дефекты по DOM здесь не ищем): `playwright-cli -s=<сессия> snapshot --depth=4` и один запрос
```bash
playwright-cli --raw -s=<сессия> eval "[...document.querySelectorAll('[aria-expanded],details,[role=tab],[class*=slider],[class*=swiper],[class*=carousel],[class*=slick],[class*=modal],[class*=popup],[class*=chat],[data-bs-toggle],[data-toggle]')].slice(0,40).map(e=>e.tagName+'.'+String(e.className).slice(0,30)+'|'+(e.textContent||'').trim().slice(0,25)).join(' // ')"
```
Составь список виджетов страницы по типам: аккордеон/FAQ/`<details>`, табы, слайдер/карусель, попап/модалка (кнопка, которая её открывает), переключатель языка, дропдаун-фильтр, тултип, чат. Меню здесь не рассматривай (раздел «Меню»), формы — раздел «Формы: состояния без отправки».

**Что открывать — по представителям каждого типа:**
- Аккордеон/FAQ: первый и последний пункт (кадр каждого открытого пункта; если пунктов меньше трёх — все).
- Табы: каждая вкладка, кроме уже активной, но не более 3 вкладок (вторая, последняя и, если есть, ещё одна; для вкладки, дающей пустую область, зафиксируй кадр).
- Слайдер/карусель: один клик «далее» (кадр), один «назад» (кадр). Если слайдер без кнопок (только точки) — клик по второй точке. **Сначала подготовь слайдер как реальный пользователь:** многие слайдеры (Swiper) создаются лениво — при первом движении мыши или прокрутке к блоку; клик по ref или `eval`-клик сразу после загрузки не инициализирует их и «не срабатывает». Прокрути к блоку, подведи мышь (`mousemove` на слайдер), подожди ~1 с (проверь, что экземпляр создан: `.swiper-initialized` / `el.swiper`) и только потом кликай. «Первый клик не сработал» без такой подготовки — артефакт инструмента, не находка; находка — только если клик не работает и после hover и ожидания инициализации (и при сомнении перепроверь свежей загрузкой). **Если все слайды помещаются в контейнер** (слайдов не больше, чем видно одновременно), листать нечего: скрытие или блокировка стрелок после инициализации (`swiper-button-lock`, `swiper-button-disabled`) — норма, а не «стрелки не работают»; максимум 🟩 за мигание стрелок до инициализации.
- Попап/модалка: открой (кадр открытого окна), закрой крестиком (кадр после закрытия: окно и затемнение исчезли, страница на месте); если крестика нет — закрой клавишей Esc или кликом по подложке, а отсутствие крестика — находка. Затемнение страницы **при открытой модалке** — норма.
- Переключатель языка, дропдаун-фильтр, тултип: кадр открытого состояния (для тултипа — наведение курсора).
Кликай только по раскрывающим элементам. **Не кликай ссылки, уводящие со страницы, кнопки отправки форм и кнопки «Купить»/«Заказать».** Если случайно ушёл со страницы — открой её заново в той же сессии.

**Кадры:** видимая область экрана (не `--full-page` и не кадр элемента: раскрытый контент часто выходит за рамку элемента); перед кадром открытого состояния прокрути элемент в центр экрана (`playwright-cli -s=<сессия> eval "document.querySelector('<селектор>').scrollIntoView({block:'center'})"`, либо `click` — Playwright прокручивает сам) и подожди ~1 с. Имена: `.playwright-cli/glance/{страница}_{разрешение}_ia-{NN}.png`, `NN` — сквозной номер кадра интерактива и форм на этой странице в этом разрешении. **Потолок кадров на страницу: десктоп — не больше 8, мобилка — не больше 12** (в него входят кадры интерактива, чата и форм; десктопный кадр примерно в 4 раза дороже мобильного, поэтому потолки разные); сначала — по одному представителю каждого типа, затем остальные; порядок при нехватке потолка: (1) аккордеон/FAQ, табы, слайдер; (2) формы; (3) чат; (4) модалка/попап; (5) переключатель языка, дропдаун, тултип. Если потолок выбран, остальное перечисли в результате («не просмотрено — лимит кадров»), молча не пропускай. Одинаковые экземпляры одного и того же виджета (например, 15 одинаковых FAQ-аккордеонов) — только по правилу представителей выше; если одна и та же вёрстка виджета уже просмотрена на другой странице этого прогона, не повторяй.

**Что искать на кадрах:**
- [ ] Клик не дал эффекта (кадр после действия выглядит так же, как до).
- [ ] Раскрылась пустая область (аккордеон, вкладка), нет контента.
- [ ] Раскрытый текст выходит за рамку элемента и накладывается на соседний заголовок или текст.
- [ ] Слайдер после клика показывает то же, что раньше, либо два слайда наложены друг на друга.
- [ ] Окно модалки или попапа вылезает за экран, обрезано, нет возможности его закрыть.
- [ ] После закрытия модалки или попапа остались затемнение или кусок окна.
- [ ] Раскрытый блок сломал сетку (соседние колонки съехали).
Серьёзность — по «Критериям серьёзности» CLAUDE.md: виджет не работает (клик без эффекта, пустая область, слайдер не листается, модалку нельзя закрыть) — 🟨 `[Interactive]`; визуальный дефект открытого состояния (наложение, выход за рамку) — 🟨 `[Visual]`; мелкое оформление — 🟩. Для багов «до/после» сохрани пару кадров `before_`/`after_` (CLAUDE.md, Шаг 4).

## Формы: состояния без отправки
Сквозные формы (в `header`, `footer` и закреплённые на экране, одинаковые на всех страницах) снимает только агент с объёмом «меню и служебные», на главной; при объёме «страницы» такие формы пропускай («за агентом меню»), снимай только формы в содержимом страницы. Формы смотрятся здесь только глазами и **без отправки данных**: полноценный сабмит-тест делает `form-submit-checks` на десктопе (в этом разделе формы не заполняются и не отправляются). Раздел выполняется на десктопе и мобилке, на одну форму одного шаблона (признак шаблона — как в `form-submit-checks`: ID формы из атрибутов; если ID нет — набор полей) за прогон; на других страницах тот же шаблон повторно не снимай.
1. **Исходное состояние.** Прокрути форму в центр экрана (`eval "document.querySelector('<селектор>').scrollIntoView({block:'center'})"`), кадр видимой области. Смотри: подписи, плейсхолдеры (не `undefined`/`null`/`lorem`/чужой текст), выравнивание полей, кнопку отправки (видна целиком, не обрезана), кастомные выпадающие списки (клик по списку, кадр открытого, закрыть Esc; нативный `<select>` на кадре не рисуется — его не открывай).
2. **Состояние ошибок валидации.** Только если в форме есть хотя бы одно видимое обязательное поле (`required` или `aria-required="true"`), оно пустое, и это не поле «согласие»: (а) клик в обязательное поле, затем `playwright-cli -s=<сессия> press Tab` (уход из поля) — кадр (часть сайтов показывает ошибку при уходе из поля); (б) клик по кнопке отправки пустой формы — кадр. Данные в поля не вводи. Если форма **без** обязательных полей — кнопку отправки не нажимай (пустая заявка уйдёт клиенту), в результате пометка «ошибки валидации не снимались: обязательных полей нет». Форму, которая публикует контент сразу, без модерации (отзывы, комментарии — признаки см. `form-submit-checks`), и форму чата не нажимай никогда. Клик по кнопке пустой формы, которую валидация остановила, не считается сабмитом шаблона в лимите `form-submit-checks`. Если после клика появилось сообщение об успехе или произошёл переход на другую страницу — форма приняла пустую отправку: это находка `[Form]` 🟨, и в результат обязательно запиши страницу, форму и время (возможно, в CRM клиента появилась пустая заявка); дальше форму не трогай.
3. Нативная подсказка браузера («Заполните это поле») на кадр не попадает — если ни на (а), ни на (б) ничего не изменилось, пометка «ошибки не показаны на кадре (возможна нативная подсказка браузера)» без находки.
Что искать: [ ] подписи, плейсхолдеры и кнопка в порядке (нет `undefined`, обрезки); [ ] тексты ошибок читаемы (не светло-красный на розовом, не мелкий шрифт на сером), стоят рядом с полем и не вылезают за экран; [ ] поля с ошибкой отличимы от обычных; [ ] кнопка отправки видна целиком. Серьёзность по «Критериям»: нечитаемые тексты ошибок валидации, ошибка за краем экрана — 🟨 `[Form]`; плейсхолдер `undefined`/мусор — 🟨 `[Visual]` (плейсхолдер); обрезанная кнопка — 🟨 `[Form]`; оформление — 🟩. Состояние «успех после отправки» здесь не снимается (оно относится к `form-submit-checks`), если нужна страница благодарности — см. раздел «404 и «спасибо»». Кадры форм идут в общий потолок раздела «Интерактив страницы» (десктоп 8, мобилка 12).

## Служебные страницы: 404 и «спасибо»
Один раз на сайт, по одному кадру на каждое разрешение (десктоп и мобилка; планшет — если включён) в сессиях страницы.
- **404.** Открой в сессии разрешения несуществующий адрес основного сайта: `<корень сайта>/qa-404-check-page/` (адрес, которого точно нет). Если URL страницы 404 передан в промпте оркестратора (например, в фикстуре eval, где несуществующий адрес не даёт страницу сайта) — открой его. Смотри кадр: [ ] есть шапка, меню и футер сайта (не «голая» страница веб-сервера с текстом вроде «Not Found» без оформления); [ ] есть ссылка на главную или поиск; [ ] вёрстка не сломана, текст читаем. Страница 404 без шапки и футера, ссылок на главную — 🟨 `[Visual]`; мелкое отклонение оформления — 🟩. Не оценивай HTTP-статус страницы (это `technical-checks`).
- **Страница «спасибо».** Только если её URL передан в промпте оркестратора (отдельно от списка шаблонов; при параллельном прогоне этот URL может быть неизвестен — тогда запиши в результат «страница благодарности не просмотрена — URL не передан»). Открой URL, кадр: [ ] есть шапка и футер; [ ] текст без незаменённых шаблонных меток (`{{name}}`, `%FIRST_NAME%`, `[name]`) и пустых мест на их месте; [ ] есть ссылка на главную или дальнейшее действие. Дефект — 🟨 `[Visual]`.
Кадры: `.playwright-cli/glance/{разрешение}_404.png`, `.playwright-cli/glance/{разрешение}_thanks.png`; на DEV за паролем — после `state-load` или входа по Basic (как выше).

## Меню (один раз на сайт, на главной)
Меню — сквозной компонент (X-site), поэтому смотрим его один раз, на главной странице сайта, а не на каждом шаблоне. Но смотрим тщательно: каждый пункт с вложенным уровнем на любой глубине и весь интерактив меню. Разрешений три: десктоп, мобилка и мобилка в альбомной ориентации (844×390); четвёртое, планшет, — только если включён просмотр планшета. Кадры меню — сверх основных кадров страницы. Здесь агент смотрит на кадры состояний меню (закрыто, открыто, каждый уровень, после «назад», после закрытия); DOM-факты по меню остаются в `visual-checks` §6. Если одну поломку нашли оба, дубль снимает оркестратор (в одиночном прогоне — сам агент).

### Подготовка (в каждом разрешении)
1. Главная открыта в сессии разрешения: десктоп и мобилка (и планшет, если включён) — в тех же сессиях `glance-<разрешение>-<суффикс>`, что и кадры страниц (если главной нет среди шаблонов или шаблонов у тебя нет вовсе — открой её в сессии командой `open` или `goto`); альбомная — отдельная сессия `glance-landscape-<суффикс>` (команда `open` — в таблице выше). Cookie-баннеры и попапы закрыты, на закрытом DEV загружена авторизация (как выше), страница прокручена в самый верх. Язык главной на мультиязычном сайте — как у кадров страницы: десктоп и альбомная (и планшет, если включён) — основная версия, мобилка — вторая.
2. Какое меню в этой сессии — определи по виду, а не по названию разрешения: гамбургер ☰ или десктопное меню с выпадающими списками. Если на планшете или в альбомной ориентации вместо ☰ десктопное меню — иди по сценарию десктопа; если на десктопе гамбургер — по сценарию мобилки.
3. **Разведка (без кадров — только текст).** `playwright-cli -s=<сессия> snapshot --depth=4` — найди кнопку ☰ (если есть) и пункты главного меню. В ☰-вёрстке закрытое меню обычно отсутствует в `snapshot`: сначала тапни ☰ (`click <ref>`) и сними `snapshot` заново — только тогда видны пункты. Определи, какие пункты раскрываются (вложенный список, стрелка, `aria-expanded`). Адреса `ref` в каждой сессии свои — ищи заново в каждом разрешении. Открывай по очереди все раскрывающиеся пункты (клик; на десктопе — наведение, а если подменю так не открывается — клик) и читай `snapshot <ref раскрытого пункта>` без `--depth` — так на любой глубине. После каждого вернись на уровень выше («назад», повторный клик, убери курсор). Результат — карта меню: по уровням, какие пункты имеют вложенный уровень, сколько вложенных пунктов в каждом, на каком уровне самая глубокая ветка. Кадры в разведке не снимай.

### Правила обхода
- Кликай только по раскрывающимся пунктам, кнопкам ☰, ✕, «назад» и крестику Top Bar. **Листовые ссылки (без вложенного уровня) не кликай** — это уведёт со страницы. Если всё же ушёл со страницы — открой главную заново в той же сессии и продолжи. Хабовый пункт, у которого есть и ссылка, и подменю: на десктопе используй наведение, клик по такому пункту может перейти по ссылке.
- Кадр — видимая область экрана (без `--full-page`). После каждого действия подожди ~1 с (анимация меню), затем кадр. Если действие не дало эффекта — перепроверь через свежий `snapshot` и повтори один раз (CLAUDE.md, «Обработка ошибок», AJAX-подгруженный контент); если эффекта так и нет — один кадр этого состояния и находка.
- **Технические правила обхода (по замеру пилота: из-за них агент снял ~13 лишних кадров).** (а) После `reload`, `goto` или перехода адреса `ref` меняются (появляется префикс, например `f1e22` вместо `e22`): перед кликами после перезагрузки сними свежий `snapshot`. (б) Не скрывай вывод команд фильтрами вроде `2>&1 | grep`: сообщение `### Error` (например, «Ref not found») означает, что действие не выполнено — повтори его по свежему `ref`, а кадр до этого не снимай. (в) Десктопный выпадающий список закрывается с небольшой задержкой после ухода курсора: если подменю ещё видно на кадре, подожди ~1 с и сними заново, прежде чем считать это дефектом. (г) Серии действий без решений между ними (открыть уровень → кадр → открыть следующий → кадр) выполняй одной командой Bash — несколько вызовов `playwright-cli` подряд, с известными `ref` из одного `snapshot` и заранее заданными именами кадров; затем читай кадры серии пачкой. Так меньше шагов, а шаги — главная статья расхода.
- Имена кадров: `.playwright-cli/glance/home_{разрешение}_menu-{NN}.png`, где `{разрешение}` — `desktop`/`tablet`/`mobile`/`landscape`, `NN` — сквозной номер кадра меню в этом разрешении (01, 02, …). Одно состояние — один кадр.
- **Потолок кадров меню на разрешение: десктоп — 20, мобилка — 30, мобилка в альбомной ориентации — 10 (лёгкий режим), планшет (если включён) — 24** (десктопный кадр примерно в 4 раза дороже мобильного, поэтому потолки разные). В потолок входят: кадр исходного состояния, кадры интерактива и кадры фазы 2. **Кадры фазы 1 в потолок не входят**, поэтому каждый уровень вложенности будет просмотрен независимо от потолка. Когда потолок выбран, остальные пункты не открывай и перечисли их в отчёте.

### Порядок в каждом разрешении
**Альбомная ориентация (844×390) — лёгкий режим.** Меню там то же, что в портретной мобилке, отличается только расположение по высоте экрана, поэтому: (1) исходное состояние; (2) фаза 1 — только цепочка вниз по уровням и кадр закрытия, без возвратов «назад»; (3) длинный список и недоступные пункты (шаг про прокрутку в интерактиве ниже); (4) фазу 2, Top Bar, sticky и повторное ☰ не повторяй — они проверены в портретной мобилке. Потолок — 10 кадров, кадры фазы 1 в него не входят.

1. **Исходное состояние.** Кадр шапки без действий (в ☰-вёрстке видны ☰, иконка телефона и CTA).
2. **Фаза 1 — глубина (вне потолка).** Возьми по карте ветку, которая доходит до самого глубокого уровня (при нескольких таких — ту, на пути которой больше вложенных пунктов; при равенстве — первую по порядку). Открой цепочку уровень за уровнем, на каждом уровне кадр. Сценарий мобилки: тап ☰ (кадр первого уровня, виден ✕), затем каждый вложенный уровень. Сценарий десктопа: наведение на пункт верхнего уровня, затем на пункт вложенного списка и так до самого глубокого. Затем вернись по одному уровню («назад» на мобилке; на десктопе — убери курсор на один уровень) и на каждом шаге сними кадр: должен показываться именно предыдущий уровень. В конце закрой меню (мобилка: ✕; десктоп: курсор вне меню) и сними кадр: меню закрыто, страница на месте.
3. **Интерактив меню (в потолке).**
   - Top Bar (плашка над основным меню), если есть: кадр; закрой крестиком; кадр после закрытия. Если крестика нет — зафиксируй это в результате, кадр Top Bar снят.
   - Sticky-шапка: `playwright-cli -s=<сессия> eval "window.scrollTo(0, innerHeight)"` — кадр (шапка на месте, не дублируется, не съехала; допустимо, что она скрывается при скролле вниз — главное, что она появляется снова); вернись наверх `window.scrollTo(0, 0)` — кадр, если шапка скрывалась.
   - Мобилка, планшет с ☰, альбомная — длинный список и прокрутка страницы за меню: открой меню на уровне с самым большим числом пунктов; замерь `playwright-cli --raw -s=<сессия> eval "window.scrollY"`; наведи курсор на середину открытого уровня (`playwright-cli -s=<сессия> mousemove <x> <y>`) и прокрути колесом несколько раз (`playwright-cli -s=<сессия> mousewheel 0 700`, 4 раза с паузой ~0.5 с между ними: это реальный ввод, как у пользователя; программная прокрутка `scrollTo`/`scrollTop` не годится — она не воспроизводит передачу прокрутки странице); кадр; замерь `window.scrollY` ещё раз: если число изменилось, страница за открытым меню прокручивается (находка). Если пункты уровня помещаются на экране целиком, шаг пропусти; при этом, если в альбомной ориентации или на другом разрешении часть пунктов верхнего уровня (включая телефон и CTA в конце списка) оказалась ниже экрана и до них нельзя прокрутить колесом — это находка (недоступные пункты). Затем закрой меню.
   - ☰ повторно: после закрытия открой меню ещё раз, кадр (состояние ☰/✕ снова меняется, кадр «открыто» выглядит так же, как первый). Закрой.
4. **Фаза 2 — ширина (в потолке).** Остальные пункты с вложенным уровнем, не вошедшие в цепочку фазы 1, — по порядку: сначала все родители первого уровня (в порядке меню), затем второго, затем глубже; для каждого — открыть, кадр, вернуться на уровень выше. Если подменю на десктопе не открылось наведением — клик, кадр. Останавливайся, когда выбран потолок.

### Что искать на кадрах меню
- [ ] Меню не открылось (после клика/тапа на кадре прежнее состояние), открылось пустым или не закрылось после ✕ / «назад».
- [ ] После «назад» показан не предыдущий уровень (пустой экран, осталась вёрстка уровня глубже, меню закрылось целиком).
- [ ] Пункты меню или подменю обрезаны, налезают друг на друга, выходят за край экрана; нужный пункт недоступен для тапа или клика (перекрыт, оказался за границей экрана).
- [ ] Подменю или выпадающий список выходит за пределы экрана или перекрывает пункты, по которым нужно кликать.
- [ ] Открытое меню закрыто другим элементом (чат-виджет, плашка, Top Bar) или само закрывает логотип, телефон или CTA без причины.
- [ ] Текст пункта не читается (сливается с фоном, лежит поверх картинки).
- [ ] В закрытом состоянии ☰-вёрстки нет иконки телефона или CTA, либо они обрезаны.
- [ ] После закрытия меню остались затемнённая подложка или кусок меню, страница сдвинута.
- [ ] Страница за открытым гамбургер-меню прокручивается (`window.scrollY` изменился после прокрутки колесом над меню).
- [ ] Top Bar не закрывается по крестику или крестика нет; sticky-шапка дублируется, съехала или не возвращается.
- [ ] Меню выглядит по-разному на кадрах разных уровней без причины (другой шрифт, пункты разного размера на одном уровне).

Декоративные детали (тень, анимация, пустое место между пунктами) — не баг. Логотип или картинка в `.avif` на WebKit-кадре меню (планшет, мобилка, альбомная) — ограничение инструмента, см. «AVIF в WebKit».

### Серьёзность находок по меню
По «Критериям серьёзности» CLAUDE.md:
- 🟥 `[Interactive]` — меню не открывается, не закрывается, нет возврата на предыдущий уровень, пункт недоступен для тапа или клика на любом разрешении.
- 🟥 `[Visual]` — меню визуально сломано так, что путь по навигации закрыт: пункты обрезаны или недоступны, подменю за экраном, открытое меню перекрыто чатом или плашкой.
- 🟨 `[Visual]` — заметный дефект без блокировки (нечитаемый текст, нет иконки телефона или CTA в закрытом состоянии, остаток подложки).
- 🟨 `[Interactive]` — Top Bar не закрывается, sticky-поведение сломано, страница за открытым меню прокручивается.
- 🟩 `[Visual]` — оформление (разные шрифты или размеры пунктов одного уровня).

Для багов «до/после» (меню не закрывается, «назад» ведёт не туда) сохрани пару кадров `before_`/`after_` (CLAUDE.md, Шаг 4). Сомнительное («возможно, так задумано») — только в «Рекомендации для ручной проверки».

## AVIF в WebKit (ограничение инструмента)
Планшет, мобилка и альбомная ориентация снимаются в WebKit, который в `playwright-cli` не декодирует AVIF: на таких кадрах фото Hero, логотипы, карточки в `.avif` выглядят пустыми рамками или значком «?». Это не дефект сайта. После `open` на планшете и мобилке выполни один раз:
```bash
playwright-cli --raw -s=<сессия> eval "[...document.images].filter(i => i.complete && i.naturalWidth === 0 && /\.avif(\?|$)/i.test(i.currentSrc || i.src)).length"
```
Если результат > 0 — сними один дополнительный верхний кадр той же страницы в Chromium на том же вьюпорте (сессия `glance-<разрешение>-chromium-<суффикс>`, `--browser=chrome`, `PLAYWRIGHT_MCP_VIEWPORT_SIZE` планшета/мобилки) — он сверх основных кадров, один на разрешение и шаблон; Hero и картинки оценивай по нему, а не по WebKit-кадру. Картинку, которая пуста в WebKit, но нарисована в Chromium, не заноси в находки; одной строкой в «Рекомендации» (формулировка — CLAUDE.md, «Обработка ошибок», «AVIF в WebKit»). Картинку, пустую и в Chromium, — в находки как обычную ([Visual] 🟥).

## Правило уверенности
- Явный дефект, который виден на кадре без интерпретации, — в основной список с тегом `[Visual]`, серьёзность по «Критериям серьёзности» CLAUDE.md (раздел «Визуальные»): 🟥 — sticky-элемент, чат или плашка закрывает CTA, форму, телефон или меню и перекрытие не уходит при прокрутке (в т.ч. на максимальной прокрутке); контент нечитаем; горизонтальный скролл, скрывающий кнопку действия; 🟨 — не загрузившаяся или искажённая картинка (не Hero и не CTA), обрезанный текст, съехавшая сетка, текст поверх фото, различия шапки/футера между шаблонами; 🟩 — оформление (несогласованный цвет однотипных элементов, мелкий шрифт). Находки визуального просмотра с Figma-макетом не сверяются (`figma-compare` для них не вызывается) — только по отдельной просьбе пользователя.
- Если возможно, подтверди подозрение через `eval` (например, `naturalWidth === 0` у картинки, `scrollWidth > clientWidth` у обрезанного элемента) — так находка станет доказуемой.
- Сомнительное («похоже на задумку дизайна», декоративные пустые полосы) — только в «Рекомендации для ручной проверки». Не хеджируй в основном списке.
- Декоративное пустое место (разделитель, отступ между секциями, `aria-hidden`-блок) — не баг.
