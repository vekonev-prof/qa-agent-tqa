# QA Agent for TQA Checks

AI-агент на базе Claude Code CLI и Playwright CLI для автоматической TQA-проверки сайтов (визуал, контент, техника, формы/калькуляторы, Figma) перед презентацией dev-сайта клиенту — и для повторных проверок уже запущенных (LIVE) сайтов.

## Какую задачу решает

TQA-инженер вручную прогоняет один и тот же чек-лист на каждом новом сайте: визуальный QA, контент, техника/SEO, сверка с Figma, тест форм и калькуляторов (ADA — отдельно, через WAVE/axe, вне агента). Это долго и легко что-то пропустить. Агент берёт список сайтов из `Сайты.txt`, сам открывает нужные страницы в трёх разрешениях (десктоп и мобилка — полный чек-лист за вычетом нескольких вьюпорт-независимых пунктов, которые проверяются один раз на десктопе; планшет — только визуальные проверки), прогоняет по ним чек-лист и отдаёт готовый отчёт: резюме простыми словами наверху, затем список находок по важности (что чинить в первую очередь — где это встречается, что происходит, как это увидеть самому, что проверить разработчику), статус ранее переданных правок и рекомендации для ручной проверки. Рассчитан на то, что его прочитает и разработчик, и ПМ, и сам клиент — без блоков по типу дефекта и без технического жаргона в основном тексте.

## Что именно проверяет

### Визуал (`visual-checks`)
Десктоп (1920×1080) и мобилка (390×844) — полный список ниже; планшет (768×1024) — только пункты, отмеченные как «+ планшет».

- UI/UX: элементы не наезжают друг на друга, сетка/колонки не съезжают между разрешениями, размер шрифта (считается через computed font-size — основной текст ≥14px, второстепенный ≥12px), sticky-хедер/чат-виджет не перекрывает контент. *(+ планшет)*
- Favicon (PNG, не SVG, ≥32×32) и Apple touch icon (PNG, ≥180×180) — консистентны на всех проверенных страницах; на одной странице не должно быть нескольких разных favicon одновременно (например, старый не убрали при добавлении нового) — сравнение сначала текстовое (по именам файлов), а если по именам неочевидно (хэшированные пути без общего паттерна) — эскалация до визуального сравнения скриншотов самих иконок.
- `<title>`: присутствует, не дефолтный, отражает содержание страницы.
- H1: ровно один, не пустой, не дублируется дословно между страницами одного типа. Если H1 отсутствует на странице, где контент рендерится через iframe стороннего виджета (например Termly для политик конфиденциальности) — это по практике агентства часто осознанное решение, не автоматический баг, но факт фиксируется в отчёте, а не замалчивается.
- Иерархия заголовков H1→H2→H3 без пропусков.
- Главное меню: клик/тап-навигация, вложенные пункты, sticky-поведение, отсутствие дублей в DOM, область тапа на мобилке/планшете ≥14px и не аномально большая; Top Bar (скрытие при скролле вниз/появление при скролле вверх, крестик закрытия); телефон в шапке показан полностью и кликабелен — на десктопе и на планшете; гамбургер (два состояния), иконка телефона + CTA, кнопка «назад» во вложенных уровнях, скролл внутри меню — на мобилке **и на планшете** (на большинстве проектов на 768px рендерится тот же мобильный гамбургер-паттерн, а не десктопное меню); на планшете дополнительно — меню не попадает в «мёртвую зону» между десктопной и мобильной вёрсткой. Отдельно, один раз на весь сайт (компонент переиспользуется X-site) — мобилка в альбомной ориентации (844×390): меню адекватно и работоспособно после поворота.
- Breadcrumbs: логичная последовательность, кликабельны все звенья кроме текущего уровня, отсутствуют на главной.
- Формы — визуально: форма присутствует/отсутствует там, где нужно по дизайну; First/Last name раздельными полями (для HubSpot); раздельные поля адреса для relocation-проектов; визуальная подсветка валидации при потере фокуса. *(+ планшет — только визуальная целостность, без проверки атрибутов и без сабмита)*
- Раскрывающиеся элементы (аккордеоны/FAQ/табы): открываются с первого клика, ведут себя по дизайну (закрывают ли друг друга при открытии).
- Google Maps блок — два раздельных правила: **карты нет на странице вообще** (статичная схема + внешние ссылки вместо встроенной карты) — это осознанная стратегия многих сайтов агентства, не находка сама по себе; **карта вставлена (iframe/embed есть), но не прогружается или сломана** — это **баг** независимо от первого правила. Если карта есть и грузится — маркер локации виден, работают зум и полноэкранный режим, default zoom показывает зону обслуживания клиента на карте штата/региона (не приближение до конкретного здания и не весь материк).

*(Атрибуты полей формы и реальный сабмит — отдельная процедура, см. «Формы и калькуляторы» ниже.)*

### Контент (`content-checks`)
- Тексты: отсутствие lorem ipsum/заглушек, кириллицы (на англоязычном сайте), «славянизированных» стоковых фото; на второй языковой версии — контент/меню/футер переведены полностью.
- Картинки: современный формат (AVIF/WebP предпочтительно), вес (~150 Кб ориентир, от ~300 Кб — уже баг), отображаемое разрешение соответствует контейнеру, alt-теги описательны, нет карточек с отсутствующей картинкой.
- US-форматы: дата — месяц раньше дня, цифрами или словом (`03/05/2026`/`March 5, 2026`), не наоборот и не ISO в видимом тексте; телефон в видимом тексте — `(XXX) XXX-XXXX` без `+1` (сам `+1` ожидается только в `tel:`-href, см. «Техника» ниже); адрес — двухбуквенный код штата перед ZIP (`Город, XX 12345`), не полное название штата; валюта — символ `$`; единицы измерения — мили/футы/дюймы, не км/метры.
- Meta-теги: title/description уникальны и в пределах длины (~50–60 / ~150–160 символов), не пустые и не дефолтные, description без телефонного номера. *(Проверяется один раз, на десктопе — данные из `<head>`, не зависят от вьюпорта; в отчёте — в блоке «SEO».)*
- Виджеты отзывов/социального доказательства (если есть на странице — Google reviews карусель, Elfsight, Trustpilot и подобные): реально показывают контент, а не пустой контейнер/заглушку — проверяется после полной прогрузки страницы, такие виджеты часто асинхронные.
- Open Graph и Twitter Card: `og:title/description/image/url`, `twitter:card/title/description/image`. *(Тоже один раз, на десктопе; в отчёте — в блоке «SEO».)*

### Техника (`technical-checks`)
- Консоль: только уровень `error`; фоновый шум сторонней телеметрии (например, аналитика чужих плагинов) не попадает в отчёт.
- Сеть: запросы со статусом 404.
- HTTP-статусы страниц: отсутствие 3xx-редиректов и 4xx.
- Ссылки: пустые/битые `href`, формат `tel:`-ссылок, карточки ведут на существующие страницы (сверка по sitemap/навигации), ссылка ведёт на правильный конкретный объект (эвристика по тексту/href); ToC (оглавление) в блоговых статьях — каждый пункт ведёт в свою секцию, а не в чужую из-за переставленных заголовков (только если на странице есть ToC — на сервисных страницах его обычно нет).
- Атрибуты `rel`/`target` — две независимые оси, три категории ссылок: **внутренние** (тот же домен) — без `target="_blank"` вообще, кроме файлов на скачивание (там `noopener`/`noreferrer` не нужен — тот же домен); **свои ресурсы клиента** (его соцсети, и **любая** ссылка на Google Maps, включая GBP-листинг — признак простой, без сверки конкретного Place ID) — `target="_blank"`, но **без** `noopener`/`noreferrer`; **прочие внешние** (госресурсы, профессиональные директории, редакционные ссылки в блоге, Google-ссылки кроме Maps) — `target="_blank"` строго с `rel="noopener noreferrer"`. По той же логике «чей это ресурс» — **dofollow только для своих ресурсов клиента** (те же соцсети и Maps), **nofollow для всех остальных внешних**, чтобы не распылять ссылочный вес сайта. *(В отчёте эти находки идут в общем списке находок с обоснованием по своей теме — риск для безопасности ссылок/передачи ссылочного веса, не общая серьёзность бага, см. «Что именно проверяет» → формат отчёта ниже.)*
- Sitemap и индексация: наличие `sitemap.xml` — единый факт на весь сайт, устанавливается один раз на Шаге 1 (там же подсчёт URL) и просто переносится в отчёт, а не перепроверяется на каждой странице; если sitemap мультиязычный (записи с `hreflang`-аннотациями) — считаются оба числа, общее количество записей и отдельно число уникальных страниц (без учёта языковых дублей), чтобы не задвоить масштаб сайта в отчёте; `noindex` на служебных/пагинационных страницах и на лендингах — это уже per-page факт, проверяется один раз на десктопе (не зависит от вьюпорта, не дублируется на мобилке). *(В отчёте — в блоке «SEO».)*
- Телефонные номера — консистентность отображаемого номера: сравниваются только сами цифры (нормализованный вид) — `(213) 223-5593`, `213-223-5593`, `+1 213 223 5593` это один и тот же номер, разное форматирование само по себе не баг; отдельно номер должен быть валиден и реально работать по клику (`tel:`-ссылка с корректным числом цифр). На DEV один номер везде по цифрам (кроме персональных номеров сотрудников на их страницах), на LIVE ожидается динамический своп (в т.ч. на лендингах — это тоже обычная практика), причём `href`/`aria-label`/видимый текст должны указывать на один номер по цифрам (сравнение делается только после того, как номер стабилизировался — своп нередко подставляет его асинхронно).
- Отработка свопа номера (только на LIVE, на DEV не проверяется — там свопов не бывает): применимо к любой системе колл-трекинга (CallRail, Invoca, WhatConverts и подобные) — скрипт свопа не выдаёт JS-ошибок, связанный сетевой запрос не возвращает 4xx/5xx. Сверка исходного кода страницы с оригинальными (не свопнутыми) номерами — только если пользователь явно передал их список в `Сайты.txt`; бизнес-логику самого свопа (какой номер для какого источника трафика) и GTM/GA4/рекламные пиксели агент не проверяет — не его зона.
- Мультиязычность (`hreflang-checks`, вызывается только если у сайта есть больше одной языковой версии): метод декларации — `<html lang>`, hreflang в `<head>`, hreflang-аннотации в sitemap, заголовок `Content-Language`. Все четыре метода проверяются на проверяемых страницах, в отчёте прямо указывается, какие из них реализованы, а какие нет.
- Schema-разметка в формате JSON-LD (LocalBusiness/LegalService, WebSite, WebPage, Product, BlogPosting, BreadcrumbList, ProfilePage, VideoObject, FAQPage, Organization) — по внутреннему стандарту агентства, сверенному с реальной документацией Google (не по общей памяти/реконструкции). Для большинства типов это комбинация Google-минимума и SEO-стратегии агентства сверх него; для `WebPage` источник — исключительно сам Google/schema.org, отдельной позиции агентства там нет. Проверяются дубли, релевантность данных странице, раздутость, асинхронная подгрузка (виджеты отзывов) и мультиязычная адаптация на мультиязычных сайтах — полные критерии и точные цитаты по каждому типу в `references/schema-guide.md`, здесь не дублируются. *(В отчёте — отдельный блок «Schema (JSON-LD)» со своей приоритетностью; не проверяется на лендингах; тип/обязательные поля — один раз, на десктопе.)*
- ADA-доступность агентом не проверяется — для этого используется отдельный специализированный инструмент (WAVE/axe и т.п.).

### Формы и калькуляторы (сабмит — полная процедура в `.claude/skills/form-submit-checks/SKILL.md`)
Вызывается условно — только если на проверяемой странице реально есть хотя бы одна форма/калькулятор; на остальных страницах этот skill вообще не подгружается в контекст. Сабмитятся все формы на странице, глубина протокола зависит от типа:
- **Лид-генерирующие** (главная контактная форма, hero/quick-quote, функциональные калькуляторы, booking/appointment, financing и любой другой CTA, ведущий к заявке) — полный протокол, потолок 10 попыток на уникальный шаблон формы; фактически используется обычно 2–4.
- **Все остальные** (рассылка, поиск, отзыв на сайте, живой чат, отклик на вакансию и т.п.) — облегчённый протокол: агент сам определяет нужные данные и делает одну тестовую отправку с той же технической верификацией, без потолка попыток. Исключение — форма, которая публикует публичный контент немедленно, без модерации: она не сабмитится автоматически, нужно отдельное явное подтверждение пользователя.
- Перед сабмитом строится карта полей: визуальная пометка обязательности сверяется с `required`-атрибутом (либо с `aria-required`/классом валидации, если CMS не использует нативный `required`); для нестандартных полей (дропдауны/даты/специфика проекта) агент готовит данные сам.
- Граничные значения проверяются не только для телефона, а для всех применимых полей: ZIP, email, числовые поля калькулятора, поля с `maxlength`, обязательные текстовые поля со значением из одних пробелов, дата (недопустимый день/месяц, дата в прошлом/далёком будущем), загрузка файла (неверный тип/размер), случайный пробел по краю иначе валидного значения (типичный след копипаста). Для полей с визуальной маской/форматированием (телефон, дата) — каждое граничное значение проверяется ДВУМЯ реалистичными способами ввода (настоящий посимвольный ввод И настоящая вставка), а не только одним — маскирующий скрипт может по-разному синхронизировать своё внутреннее состояние с DOM в зависимости от способа, и находка, воспроизведённая только программной подстановкой значения (`fill()`), не фиксируется как баг без перепроверки настоящим вводом.
- **Определение «та же переиспользуемая форма или нет»** — не на глаз: сначала ищется технический признак (ID формы в разметке — например скрытый `_wpcf7` у Contact Form 7, класс `wpforms-form-<ID>` у WPForms, `data-form-id` у HubSpot — либо ID в самом endpoint сабмита), затем, если ID недоступен — точный набор имён полей, и только как последний по надёжности вариант — визуальное сходство заголовка/лейблов. Если у двух похожих форм на разных страницах ID/набор полей расходятся — это разные шаблоны (свой потолок в 10 попыток у каждого) и самостоятельный X-site баг несогласованной реализации.
- **Координация между параллельными агентами** — перед сабмитом лид-генерирующей формы агент проверяет файл-маркер `{домен}/{прогон}/.form-submissions/<технический-ID>.json` в папке ЭТОГО прогона (`{прогон}` — дата и время старта, одинаковое у всех подагентов прогона); если он уже создан другим параллельным агентом в этом же прогоне, форма повторно не сабмитится (результат берётся из файла), иначе агент проходит протокол и сам создаёт файл для остальных. Файл нужен только на время одного прогона — агент сам убирает его в конце (см. «Уборка после прогона» ниже), никаких персональных данных клиента там нет — только техническая связка ID шаблона/страницы/результата.
- Последовательность попыток: (1) граничный/невалидный кейс, на десктопе — форма должна заблокировать отправку; (2) валидный кейс, на десктопе — форма должна пройти; (3) защита от дублирования лида — двойной клик по Submit (реальный сетевой запрос должен уйти ровно один, не два) и проверка повторной отправки после кнопки «назад» в браузере, на тех же данных, что и (2) — в лимит 10 попыток не входит; (4) точечная проверка (опционально, на том разрешении, где найдено противоречие); (5) троттлинг-тест (опционально, только для форм с AJAX-отправкой) — отдельная мобильная Chromium-сессия под искусственным замедлением сети, ловит тайминг-зависимые «тихие» сбои.
- Каждая попытка проверяется технически, не только по визуальному результату: сетевой запрос отправки формы ищется по признакам (метод, тайминг, содержимое payload), проверяется статус и содержимое ответа; отсутствие такого запроса — самостоятельный признак провала (кроме граничного кейса, где это ожидаемо); дополнительно проверяется консоль на `error` в узком окне вокруг клика Submit.
- Тестовые данные — согласованный набор, одинаковый для всех прогонов (см. `form-submit-checks`); в текстовое поле сообщения формы записываются URL страницы и идентификатор формы. Каждому реальному сабмиту присваивается сквозной номер на весь прогон (не свой для каждой формы) — номер зашивается в тестовые данные (суффикс в фамилии, последние 2 цифры телефона), а в отчёте появляется таблица «Что было отправлено в тестовых формах» — по ней удобно сверяться с CRM/почтой, что все заявки дошли.
- Калькуляторы: если в `Сайты.txt` (`Комментарии:`) передано ТЗ на формулу — сверка точная. Без ТЗ (обычный случай) проверяются устойчивость, монотонность, реакция на разный ввод, детерминированность результата и внутренняя арифметическая согласованность видимой разбивки (без знания самой формулы).

### Figma (`figma-compare`) или сверка с оригиналом (`original-site-compare`)
Взаимоисключающие варианты — какой из двух используется, определяется вторым полем строки сайта в `Сайты.txt` (см. ниже).
- **Figma:** точечная сверка конкретной секции с макетом — только если по ней уже найдено визуальное расхождение и для страницы передан макет. Для лендингов — только если для конкретного лендинга явно указана своя Figma-ссылка. Если передана общая ссылка на файл (не на конкретный узел) — агент сам находит нужный фрейм по названию шаблона среди страниц/фреймов файла; этот же список фреймов используется ещё раньше, при выборе страниц для сэмплинга (см. «Выбор страниц» в таблице «Как это работает» ниже) — обычно в макете отрисован каждый шаблон сайта, но бывает исключение (нарисован только Homepage). Сравнение всегда идёт с макетом ТОГО ЖЕ разрешения (десктоп/мобилка/планшет), где найдено расхождение; если макета для этого конкретного разрешения нет (частый случай — планшет часто не рисуют вовсе) — агент не выдумывает недостающий дизайн, а сверяется с внутренним стандартом чек-листа вместо Figma именно для этого разрешения.
- **Сверка с оригиналом (`ORIGINAL:<url>` вместо Figma-ссылки):** используется, когда макета нет, а перенос сверяется напрямую с реальным сайтом клиента (например, контент перенесён ИИ-агентами на новую платформу). Структура/NAP/Schema/формы сверяются на каждой проверяемой странице; **текст — не дословно, а по сохранности фактов** (переформулировка/другой порядок предложений — норма для ИИ-переноса, не баг; пропавший факт, изменённое число/дата/гарантия, противоречие оригиналу — баг). Дополнительное открытие эталона на мобилке/планшете — только если на DEV уже найдено визуальное расхождение на этом разрешении. Соответствие страниц — тот же URL-путь на обоих доменах по умолчанию, с фолбэком на поиск по навигации эталона. Скриншоты эталона — в его собственную рабочую папку `{домен-эталона}/screenshots/` (не в папку DEV-сайта), с пометкой `_DEV`/`_ORIGINAL` в имени файла.

### Мультиязычные сайты — как распределены проверки по разрешениям
Если у сайта есть вторая языковая версия — десктоп проверяется на основном языке, мобилка на второй языковой версии той же страницы, планшет — на основном языке (там проверяется только визуал, контент на планшете не сверяется). Из-за этого Schema-разметка проверяется не только один раз на десктопе (как обычно) — адаптация под язык (сохранение типов, перевод текста, `inLanguage`, переведённые URL) сверяется на обеих открытых языковых версиях, см. «Техника» выше.

## Из чего состоит агент

- **Главный промпт — [`.claude/CLAUDE.md`](.claude/CLAUDE.md).** Это системная инструкция, которую Claude Code загружает автоматически при каждом запуске из этой папки. Она не проверяет ничего сама — это оркестратор: описывает формат `Сайты.txt`, алгоритм по шагам (выбор страниц → открытие → вызов Skills → сабмит форм → скриншоты → Figma → правки на перепроверку), правило сабмита форм/калькуляторов (какие тестовые данные использовать, что можно, а что нет), формат итогового отчёта и что делать при ошибках.
- **Skills — `.claude/skills/*/SKILL.md`.** Каждый skill — это отдельный «модуль» чек-листа, который агент вызывает по ходу работы; Claude Code подгружает его содержимое только когда он реально нужен (экономия токенов):
  - `visual-checks`, `content-checks`, `technical-checks` — три группы проверок выше.
  - `form-submit-checks` — реальный сабмит-тест форм/калькуляторов, вызывается только если на странице есть хотя бы одна форма: полный протокол (до 10 попыток) для лид-генерирующих форм (контакт, quote/estimate, callback, booking, financing), облегчённый однократный сабмит для всех остальных (рассылка, поиск, отзыв, живой чат, отклик на вакансию).
  - `hreflang-checks` — метод декларирования мультиязычности (html lang, hreflang в `<head>`/sitemap, `Content-Language`), вызывается только на мультиязычных сайтах.
  - `figma-compare` — сверка с макетом, вызывается только при подозрении на расхождение.
  - `original-site-compare` — сверка с реальным сайтом вместо макета, вызывается только если в `Сайты.txt` вместо Figma-ссылки указан `ORIGINAL:<url>`.
  - `eval-regression` — регресс-тест промпта на тестовой фикстуре, вызывается только по явной просьбе («прогони eval» и т.п.), не часть проверки сайта клиента — см. «Регресс-тестирование промпта» ниже.
  - `playwright-cli` — техническая справка по командам браузерной автоматизации (открытие страниц, snapshot, click, eval и т.п.), сгенерированная самим Playwright CLI — ей пользуются остальные skills, чтобы управлять браузером.
- **Подагенты — `.claude/agents/*.md`.** Опционально: если проверка распределяется между несколькими параллельными агентами (Agent tool), диспетчеризуйте `subagent_type: tqa-page-agent` вместо `general-purpose` — это тот же чек-лист, но с настроенным под задачу `reasoning_effort: 40` (подобран сравнением на eval-фикстуре, см. `eval/README.md`). Не обязательно для небольших сайтов — один агент, последовательно проходящий чек-лист, работает так же.

Ничего кроме этих файлов агенту для работы не нужно — весь чек-лист и вся логика живут в `.claude/`.

## Что передавать в `Сайты.txt`

**Этот файл не входит в репозиторий** (добавлен в `.gitignore`) — в нём реальные данные клиента (URL, номера телефонов, комментарии ПМа), их не нужно и не должно коммитить в git. Создайте `Сайты.txt` в корне проекта (рядом с `Readme.md`) самостоятельно перед первым запуском — просто новый текстовый файл с таким именем, пустой репозиторий его не содержит.

Один основной сайт клиента на строку:

```
URL | ссылка_на_Figma | DEV
```

- **URL** — обязателен.
- **Ссылка на Figma** — опциональна. Если макета нет, но перенос сверяется напрямую с реальным сайтом клиента — вместо неё укажите `ORIGINAL:<url эталонного сайта>` (например `URL | ORIGINAL:https://real-site.com | DEV`) — это включает `original-site-compare` вместо `figma-compare`. Два варианта взаимоисключающие.
- **Окружение `DEV`/`LIVE`** — опционально, но желательно указывать: на `LIVE` номер телефона может быть легитимно подменён (своп для колл-трекинга) и отличаться от Figma/DEV; на `DEV` такого быть не должно. Без этой пометки агент не сможет отличить легитимный своп от реальной ошибки в номере. **На возможность сабмитить формы окружение не влияет.**

Если у клиента несколько независимых основных сайтов (разные бренды/домены) — отдельная строка на каждый.

Плюс до трёх опциональных блоков в конце файла:

```
Лендинги:
- [URL рекламной посадочной страницы] | [свой Figma-фрейм, необязательно]

Правки:
- [что перепроверить, что было исправлено]

Комментарии:
- [пожелания клиента/ПМа: специфика проекта, ТЗ на логику калькулятора, тип бизнеса и т.п.]
```

**`Лендинги:` — важно.** Это единственный способ сказать агенту «эта страница — рекламный лендинг, а не обычная страница сайта». Без явного перечисления здесь агент не станет применять к странице лендинг-специфичное правило (обязательный `noindex`) — даже если URL похож на рекламный (`/ppc-...`, с `utm_*` и т.п.). Каждый URL из этого списка проверяется целиком (весь чек-лист, оба разрешения) как конкретная страница, а не сэмплируется по типам, как основной сайт. Телефонные номера на лендингах ведут себя так же, как на основном сайте — свопы для трекинга звонков являются обычной практикой агентства.

**Про Figma для лендингов:** сравнение с макетом для лендинга выполняется только если для него указана своя Figma-ссылка (дизайн лендингов обычно отличается от основного сайта). Указывайте ссылку там, где сверка реально нужна.

Пример полного файла:
```
https://client-site.com | https://figma.com/file/xxxx/Main | DEV

Лендинги:
- https://client-site.com/ppc-landing-1/
- https://client-site.com/ppc-landing-2/

Правки:
- [contact form] сабмит не работал — перепроверить

Комментарии:
- Проект — moving company, проверить поля адреса и автоподбор
- ТЗ на калькулятор: cost = base_rate + distance_miles * per_mile_rate
```

### Рекомендуемая структура блока `Комментарии:` для больших/нестандартных задач

Для простых прогонов пары строк достаточно (см. пример выше). Если задача крупная (много страниц, есть правки от ПМа/клиента, нужно что-то сверить по таблице, или вы разово меняете стандартное поведение агента) — удобнее разбить `Комментарии:` на именованные подсекции, а не писать одним сплошным текстом:

```
Комментарии:

ПРОЕКТ: [тип бизнеса / особенности, которые влияют на обычные проверки]

ПРАВКИ ОТ ПМ/КЛИЕНТА/ЧАТ-БОТА (проверить дополнительно):
1. [конкретная формулировка правки/вопроса — можно вставлять цитатой как есть]
2. ...

СПРАВОЧНЫЕ ДАННЫЕ (если нужно что-то сверить по таблице — номера, ID, коды):
- ...

СПЕЦИФИКА ТОЛЬКО ЭТОЙ ЗАДАЧИ (разовое отступление от стандартного поведения агента — явно пометьте, что это не постоянное правило):
- ...

ФОРМАТ ОТЧЁТА: [встроенный / уточнить, если нужно что-то другое]
```

Так агент не путает «это правило для этого прогона» с «это стандартное поведение навсегда», и ничего не теряется среди сплошного текста.

Шаги ниже можно пройти вручную (как описано) или попросить агента в Claude Desktop выполнить их за вас, указав ему на этот раздел — команды одни и те же, разница только в том, кто их вводит. Исключение — вход в аккаунт Claude (и в Figma, если он нужен): это всегда делаете лично вы через открывшийся браузер, ни один интерфейс агента не может пройти авторизацию за вас.

### 9. Запустите агента

Есть два равнозначных способа получить входные данные — независимо от того, через терминал или через Claude Desktop вы запускаете агента (см. ниже):

- **Файловый режим** — вы заранее заполнили `Сайты.txt` (см. раздел выше) и просите прогнать проверку по нему.
- **Режим чата** — вы просто описываете сайт прямо в сообщении (URL, окружение, что перепроверить), не создавая файл заранее. Агент сам разберёт сообщение в формат `Сайты.txt`, при нехватке важных деталей (например, не указано окружение DEV/LIVE, или неясно, что из перечисленного — лендинги) задаст короткий уточняющий вопрос, сохранит получившиеся данные в `Сайты.txt` и дальше проверяет как обычно. Удобно для разовых/небольших задач, когда заводить файл вручную не хочется — но сам файл всё равно появится на диске, так что при следующем запуске можно будет просто сказать «прогони ещё раз по Сайты.txt».

Ниже — два равнозначных способа вызвать агента (интерфейс), они работают одинаково с обоими режимами выше.

Агент сам сохраняет готовый отчёт в `{домен}/{прогон}/report.txt` (через `Write`) как обязательный последний шаг — независимо от способа запуска, поэтому оба способа ниже равнозначны и в плане получения файла на диске. `{прогон}` — подпапка с датой и временем старта прогона **по московскому времени (МСК, UTC+3 — всегда, независимо от часового пояса машины, где физически работает агент)**, например `2026-09-21_14-30`: каждый прогон одного и того же сайта получает свою собственную подпапку, ничего не перезаписывает и не смешивается с прошлыми прогонами. То же время — в поле «Дата и время» самого отчёта: если оно не совпадает с вашим локальным временем, это ожидаемо, не баг.

**Способ 1 — через терминал (Git Bash):**
```bash
claude -p "Проверь сайты из файла Сайты.txt" --output-format text | tee report.txt
```
`| tee report.txt` здесь уже необязателен (агент сам создаст `{домен}/{прогон}/report.txt`) — оставлен как удобство, если хотите сразу увидеть вывод в терминале и/или держать копию отчёта в корне проекта.

**Способ 2 — через приложение Claude Desktop (вкладка Code):**
Откройте приложение Claude Desktop → вкладка Code → откройте эту папку проекта (там, где `Readme.md` и `.claude/`) как рабочую директорию — и просто напишите в чат:
> Проверь сайты из файла Сайты.txt

Результат придёт прямо в переписке, и агент сам сохранит его в `{домен}/{прогон}/report.txt` на диске — просить об этом отдельно не нужно.

Всё, что агент создаёт по ходу проверки конкретного сайта — отчёт, скриншоты, вручную сохранённые снапшоты, служебные маркеры сабмита форм — лежит в папке ЭТОГО прогона `{домен}/{прогон}/` (хост сайта без протокола и слэшей, например `bestcaliforniamovers.com`, плюс подпапка с датой и временем старта): `{домен}/{прогон}/report.txt`, `{домен}/{прогон}/screenshots/`, `{домен}/{прогон}/snapshots/`, `{домен}/{прогон}/.form-submissions/`. Следующий прогон того же сайта получит новую подпапку `{прогон}` — старые результаты не трогает и не перезаписывает. Автослужебный кэш, который playwright-cli создаёт сам без явного имени файла, остаётся в отдельном `.playwright-cli/` в корне проекта — агент убирает его в конце прогона (см. «Уборка после прогона» ниже), папку сайта при этом не трогает.

### 10. Посмотрите отчёт
Откройте `{домен}/{прогон}/report.txt` (свежая подпапка — самая новая по дате в имени). Отчёт — это не блоки по типу дефекта, а один список находок по важности: так сразу понятно, что чинить в первую очередь, без необходимости самому сопоставлять важность между разными техническими категориями. Разделы отчёта:

1. **Если коротко** — 3–5 предложений простым языком, без терминов: что вообще происходит и на что смотреть в первую очередь.
2. **Что нужно доделать (по важности)** — один пункт = один баг (если баг массовый — одна запись с пометкой «встречается на: …», без дублирования). Для каждого: **Где** он встречается, **Что происходит** (простыми словами — что видит посетитель или чем это грозит бизнесу), **Как воспроизвести** (короткая пронумерованная инструкция — только для непростых багов, где неочевидно с первого взгляда), **Рекомендация для DEV** (отдельно — что конкретно проверить/поправить, техническая гипотеза о причине).
3. **Ранее переданные правки — статус** — таблица со статусом каждого пункта из `Правки:` (исправлено / частично / не исправлено / не проверялось).
4. **Что было отправлено в тестовых формах** — таблица номеров сабмитов (см. «Формы и калькуляторы» выше) со страницей/формой/thank-you URL — по ней сверяетесь с CRM/почтой.
5. **Рекомендации для ручной проверки** — всё, в чём агент не уверен на 100% или не может подтвердить сам техническими средствами (нужен специалист по трекингу/аналитике, бизнес-логика калькулятора без ТЗ и т.п.).
6. **Технические детали** — для интересующихся: сколько URL в sitemap, список проверенных страниц, окружение, статус сравнения с Figma/оригиналом.

Значки 🟥 Critical / 🟨 Major / 🟩 Minor у каждого пункта — это то, насколько срочно его чинить; критерий, по которому агент выбирает значок, у разных тем разный (общая серьёзность дефекта для форм/техники/визуала/интерактива, риск для индексации у SEO-находок, риск для безопасности ссылок у rel/target, риск переспама у Schema) — это внутренняя логика агента при сортировке списка, в самом отчёте она не расписывается.

## 🧠 Как это работает

| Что делает агент | Подробнее |
|---|---|
| Уборка после прогона | Каждый прогон пишет в свою подпапку `{домен}/{прогон}/` — прошлые прогоны того же сайта новый прогон не трогает и не перезаписывает, они просто лежат рядом, в своих подпапках с другой датой/временем. После завершения прогона агент сам удаляет то, что было нужно только во время работы: маркеры сабмита форм `{домен}/{прогон}/.form-submissions/` и автослужебный кэш `.playwright-cli/` в корне проекта — вручную убирать ничего не нужно. Отчёт и скриншоты (`report.txt`, `screenshots/`) при этом не трогает — это и есть результат, который вы смотрите |
| Выбор страниц | Проверяет только 1–2 страницы каждого шаблона (переиспользуемый CMS-паттерн — например, одна сервисная страница спроектирована один раз и тиражирована через CMS-коллекцию на десятки услуг/локаций) – не ходит по всему сайту. Шаблоны определяются по сигналам в порядке приоритета: навигация/футер → URL-префикс, если есть → форма слага по образцу (для сайтов без чёткого префикса, например юридических с URL вида `услуга-lawyer-город-штат`) → список фреймов Figma-макета, если он передан (обычно рисуется на каждый шаблон сайта). Финальный шаг — сверка со ВСЕМ списком sitemap: любой необъяснённый найденными шаблонами URL — сигнал пропущенного шаблона |
| Интерактивные элементы | На каждой странице сначала составляется полный инвентарь всех интерактивных виджетов, не покрытых отдельными пунктами других проверок (меню/формы/breadcrumbs/Google Maps — у них своя процедура): аккордеоны, табы, попапы, карусели, дропдаун-фильтры и т.п. — через `snapshot`, не «что попалось по пути». Каждый РАЗНЫЙ тип виджета доводится до конца хотя бы один раз; несколько экземпляров одного и того же виджета — 1–2 представителя достаточно |
| Разрешения | Десктоп (1920×1080, Chrome) и мобилка (390×844, WebKit) — полный чек-лист на одном и том же наборе страниц из выборки, за вычетом нескольких вьюпорт-независимых пунктов (см. «Проверки» ниже); планшет (768×1024, WebKit) — те же страницы, визуальные проверки (`visual-checks`) плюс интерактив меню (как на мобилке — гамбургер, кнопка «назад», скролл), без content-checks/technical-checks/сабмита форм |
| Проверки | Три группы Skills: `visual-checks`, `content-checks`, `technical-checks` — вызываются на каждой отобранной странице (на планшете — только `visual-checks`). Meta-теги, Open Graph/Twitter Card, `noindex` и Schema (JSON-LD) — данные из `<head>`/технической разметки, не зависят от вьюпорта — проверяются один раз, на десктопе, и не повторяются на мобилке (кроме мультиязычной адаптации Schema — см. «Мультиязычные сайты» выше, там десктоп/мобилка это разные языковые версии, а не просто разные вьюпорты); существование самого `sitemap.xml` — вообще не per-page факт, устанавливается один раз на Шаге 1 |
| Формы и калькуляторы | Отдельный skill `form-submit-checks`, вызывается условно — только если на странице есть хотя бы одна форма (не грузится в контекст на остальных страницах). Полный протокол для лид-генерирующих, облегчённый однократный сабмит для остальных — детали см. раздел «Формы и калькуляторы» выше. При параллельном запуске нескольких агентов координация «кто какой шаблон тестирует» закрепляется заранее в промпте каждого агента |
| Мультиязычность | Отдельный skill `hreflang-checks`, вызывается условно — только если у сайта больше одной языковой версии |
| Figma / сверка с оригиналом | Сравнивает с макетом только при найденных расхождениях (экономия токенов); либо, если макета нет и вместо него в `Сайты.txt` указан `ORIGINAL:<url>`, сверяет DEV с реальным сайтом клиента (`original-site-compare`) — структуру/NAP/Schema на каждой странице, мобилку/планшет эталона — только при найденном расхождении на DEV |
| Своп номеров | На LIVE по умолчанию (`technical-checks`): консистентность номера + техническая отработка свопа (скрипт/сеть). На DEV не проверяется — там свопов не бывает |
| Сверка с оригинальными номерами | Только в двух случаях: список от пользователя в `Сайты.txt`, либо задача явно описана как прямая сверка DEV с реальным LIVE-сайтом вместо Figma-макета — тогда эталоном служит номер из сырого HTML LIVE-сайта (до выполнения JS, не через браузер/eval после отрисовки) |
| Скриншоты | Делает только при обнаружении проблем, сохраняет в `{домен}/{прогон}/screenshots/` (своя подпапка на каждый прогон) – не тратит токены на успешные шаги |
| Оптимизация токенов | `snapshot --depth=4` и `find` вместо полного accessibility tree, группировка массовых багов в одну строку отчёта — подробнее см. «Экономия токенов» ниже |
| Отчёт | Один список находок по важности вместо блоков по типу дефекта — резюме простыми словами, потом каждый пункт: где / что происходит / как воспроизвести (для непростых) / рекомендация для DEV. Плюс отдельные компактные разделы: статус ранее переданных правок, таблица тестовых сабмитов (со сквозной нумерацией), рекомендации для ручной проверки, технические детали (sitemap, страницы, Figma). Значки 🟥/🟨/🟩 расставляются по разным критериям в зависимости от темы находки (общая серьёзность бага / риск для индексации / безопасность ссылок / переспам Schema) — это внутренняя логика агента, не расписывается в самом отчёте. Всё, в чём агент не уверен на 100%, попадает только в рекомендации, не в основной список |

## Экономия токенов: как устроена и почему

**Два термина, которые здесь легко перепутать:** `snapshot` — это текстовый дамп accessibility-дерева страницы (роли элементов, текст, вложенность структуры, без картинки) — обрабатывается моделью как обычный текст, дёшево. `screenshot` — это PNG-картинка реального визуального рендера, для неё нужен Vision — токены на изображение считаются иначе и обычно дороже эквивалентного объёма текста. Отсюда и вся логика ниже: снапшоты — рабочая лошадка на каждом шаге, скриншоты — редкая и точечная операция.

Экономия работает на нескольких уровнях сразу — от того, что вообще проверяется, до того, какой конкретно вызов делается на конкретной странице.

**Уровень 1 — что вообще проверяется.**
- Не весь сайт, а 1–2 страницы каждого типа (шаблона) — см. «Выбор страниц» выше. Это самая крупная экономия: она задаёт объём работы ещё до того, как открыт хоть один браузер.
- Skills подгружаются в контекст только по условию, не все разом: `form-submit-checks` — только если на странице реально есть форма, `hreflang-checks` — только на мультиязычных сайтах, `figma-compare`/`original-site-compare` — только по своим триггерам (см. таблицу Skills выше). Промпт не тяжелеет от логики, которая в конкретном прогоне не нужна.
- Часть пунктов `content-checks`/`technical-checks` — meta-теги, Open Graph/Twitter Card, `noindex`, Schema (JSON-LD) — данные из `<head>`/технической разметки, не зависят от вьюпорта, поэтому проверяются один раз на десктопе и не дублируются на мобилке (кроме проверки языковой адаптации Schema на мультиязычных сайтах — см. «Мультиязычные сайты» выше).
- Существование самого `sitemap.xml` экономится ещё сильнее: это не per-page факт вообще, а один файл на весь домен — устанавливается один раз на Шаге 1 (там же подсчёт URL через `curl`) и просто переносится в отчёт, без повторной проверки на каждой странице выборки.

**Уровень 2 — дешёвые операции вместо дорогих, на каждой странице.**
- `find` (точечный текстовый/regex-поиск по DOM) — когда вопрос просто «этот элемент вообще есть?» (CTA, телефон в US-формате, email). Возвращает пару строк вместо целого дерева страницы.
- `snapshot --depth=4` — только когда `find` не подтвердил элемент, или когда важны порядок/структура (число колонок, вложенность секций) — не полный accessibility tree.
- Правило эскалации простое и всегда одно и то же: сначала `find` → если не хватило, `snapshot --depth=4` → полный snapshot не используется вообще нигде в чек-листе.
- `curl` вместо браузера — там, где нужен только сырой HTML, а не рендеринг: подсчёт URL в sitemap (Шаг 1) и чтение оригинального телефона с LIVE-сайта до выполнения JS (`technical-checks` §7).
- Консоль и сеть, уже один раз собранные на обычном проходе по странице (`technical-checks` §1/§2), переиспользуются и для проверки технической отработки свопа номера на LIVE (§7) — вместо повторного вызова тех же команд на той же уже открытой странице.

**Уровень 3 — отчёт.** Один и тот же баг на многих страницах — одна строка «массово, см. страницы: …», а не описание на каждую страницу отдельно.

**Уровень 4 — скриншоты.** Самая дорогая операция по токенам (и единственная, что уходит в Vision) — когда именно она случается, отдельно ниже.

Экономия токенов на уровне промпта работает вместе с калибровкой модели и reasoning effort подагента, который эти страницы обходит, — см. «Модель и reasoning effort для подагентов» ниже, это отдельная, но дополняющая оптимизация.

## Как агент понимает, что это расхождение — и когда делает скриншоты

**Стадия 1 — `visual-checks`, без Figma вообще.** На этой стадии нет никакого «сравнения с макетом» — есть сверка с внутренним стандартом чек-листа агентства: на странице должен быть CTA, телефон в US-формате, email, ровно один H1, favicon без 404 и т.п. — независимо от того, передан ли для страницы макет. `find`/`snapshot` проверяют присутствие и структуру относительно этого стандарта, а не относительно дизайна конкретного клиента.

«Подозрение на расхождение», которое запускает переход к Figma, — это то, что сам `visual-checks` уже видит без всякого макета: явную структурную/визуальную аномалию (элементы наезжают друг на друга, число колонок в `snapshot` не совпадает с ожидаемым, сетка «съехала» между разрешениями). Обнаруживается через чтение структуры дерева/снапшота — не через diff с Figma, потому что сравнивать пока не с чем.

**Стадия 2 — `figma-compare`, только если оба условия выполнены сразу:** для страницы передан макет, И стадия 1 уже нашла конкретное подозрение. Тогда:
- у Figma MCP запрашивается только нужный узел/фрейм, не весь файл;
- на сайте берётся `snapshot --depth=4` только той секции, где подозрение;
- сравнение идёт текст-против-текста / число-против-числа (есть ли секция, порядок, число колонок, цвет) — никакой картинки на этом шаге.

Здесь Figma выступает эталоном для подтверждения уже найденного подозрения, а не источником его обнаружения — обнаружение всегда происходит на стадии 1, без макета.

**Когда доходит до скриншота.** Только если по итогам текстового сравнения размер элемента разошёлся с Figma больше чем на 20% — тогда скриншот делается точечно (сам элемент, не вся страница) и уходит в Vision вместе с фрагментом макета для финального решения. Это частный случай общего правила (Шаг 4 CLAUDE.md): скриншот вообще делается только в трёх случаях — найден визуальный дефект, страница загрузилась с ошибкой, нужна дополнительная визуальная фиксация конкретного бага — никогда для успешных шагов.

## Регресс-тестирование промпта (для поддержки агента)

Перед правкой `.claude/CLAUDE.md` или любого skill — прогоните тестовую фикстуру из папки `eval/`, чтобы убедиться, что правка не сломала уже работающую проверку, без необходимости перечитывать всё вручную.

Ничего заполнять или готовить не нужно — тестовый сайт и список для проверки уже полностью готовы, свой рабочий `Сайты.txt` при этом никак не трогается. Достаточно попросить агента в чате «прогони eval» (или «проверь регресс» и т.п.) — за это отвечает отдельный skill `eval-regression`, который сам читает `eval/README.md` и знает актуальный список фикстур, даже если он вырастет. Подробности процесса — там же, в [`eval/README.md`](eval/README.md).

Та же фикстура используется и для калибровки модели/эффорта подагентов — см. следующий раздел.

## Модель и reasoning effort для подагентов

Подагент, который проверяет страницы при распараллеливании (`tqa-page-agent`, см. «Из чего состоит агент» выше), сконфигурирован с `model: sonnet` и `reasoning_effort: 40` — оба значения подобраны прямым измерением на eval-фикстуре, а не выбраны произвольно.

**Модель — Sonnet 5.** Основной объём работы (открытие страниц, снапшоты, сеть, консоль, сабмиты форм) механический и подробно специфицирован в CLAUDE.md/skills — область, где Sonnet справляется наравне с более дорогими моделями. Opus не даёт заметного выигрыша в качестве за кратно большую цену за токен для этой задачи. Haiku не подходит — часть проверок требует настоящего суждения (например, отличить легитимное исключение от бага), а не только механическую классификацию/экстракцию, а на таких задачах более дешёвые модели чаще ошибаются.

**Reasoning effort — 40**, по результатам прямого сравнения трёх уровней на eval-фикстуре (2026-09-16, 17 применимых пунктов `ground-truth.md`):

| Эффорт | Покрытие ground-truth | Взвешенные эффективные токены* |
|---|---|---|
| 20 | 15.5/17 — пропустил базовую проверку (lorem ipsum) | 1 223 790 |
| **40** | **~17/17** | **1 124 243** |
| 80 | 17/17 | 2 061 898 |

\* `input×1 + output×5 + cache_creation×2 + cache_read×0.1` — считается по JSONL-транскрипту подагента, не по сырым токенам.

Эффорт 40 — не компромисс, а строго лучший вариант из трёх: дешевле и быстрее эффорта 20, и при этом не пропустил ничего (в отличие от 20); даёт то же покрытие чек-листа, что эффорт 80, примерно за половину его стоимости.

**Калибровка привязана к конкретной модели.** `model: sonnet` в `tqa-page-agent.md` — алиас поколения, который сам обновится на следующий Sonnet без правки файла. Число `40` получено на поведении именно Sonnet 5 — если/когда `sonnet` станет резолвиться в другую модель, сравнение стоит прогнать заново (инструменты для этого — `.claude/agents/qa-eval-low-effort.md`/`qa-eval-mid-effort.md`/`qa-eval-high-effort.md` — уже в репозитории), а не полагаться на цифры выше как на постоянную истину. Подробности — в `eval/README.md`.

## 📌 Важно
- **Уборка после прогона** (полное описание — см. «Как это работает» выше, строка «Уборка после прогона»): каждый прогон пишет в свою подпапку `{домен}/{прогон}/`, прошлые прогоны не трогает; агент сам удаляет служебные файлы своего прогона (маркеры сабмита форм, кэш playwright-cli) после завершения — вручную ничего убирать не нужно, отчёт и скриншоты остаются.
- Сабмит форм (протокол, лимит попыток, техническая верификация, троттлинг-тест) — см. раздел «Формы и калькуляторы» выше; исключение без подтверждения пользователя — форма, немедленно публикующая публичный контент без модерации.
- Планшет — третье разрешение по умолчанию: визуальные проверки плюс интерактив меню (как на мобилке — гамбургер, кнопка «назад», скролл), без content-checks/technical-checks/сабмита форм (см. таблицу «Как это работает», строка «Разрешения»).
- Агент не входит в админку/CMS и не может сам проверить, дошло ли письмо с формы — это всегда остаётся ручной проверкой в отчёте.
- Прежде чем занести находку в отчёт как баг, агент обязан довести проверку до конца тем же путём, которым идёт реальный пользователь (например, реально проскроллить горизонтально-скроллируемый блок, а не судить по одной лишь геометрии; довести граничное значение маскированного поля до реальной попытки сабмита) — технический сигнал сам по себе ещё не подтверждённый баг (см. `.claude/CLAUDE.md`, «Обработка ошибок»).
- Для работы с Figma нужен Pro-аккаунт (или токен доступа).
- Устойчив к типовым сбоям: сайт под паролем без доступа, антибот-защита/капча (в т.ч. при попытке сабмита формы), недоступный Figma MCP или упавшая браузерная сессия не останавливают весь прогон — фиксируются в отчёте и проверка идёт дальше (полный список — `.claude/CLAUDE.md`, раздел «Обработка ошибок»).
- **ADA-доступность не входит в проверку агента** (см. «Техника» выше) — используйте отдельный инструмент (WAVE/axe и т.п.).
