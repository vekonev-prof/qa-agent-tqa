# QA Agent for TQA Checks

AI-агент на базе Claude Code CLI и Playwright CLI для автоматической TQA-проверки сайтов (визуал, контент, техника, формы/калькуляторы, Figma) перед презентацией dev-сайта клиенту — и для повторных проверок уже запущенных (LIVE) сайтов.

## Какую задачу решает

TQA-инженер вручную прогоняет один и тот же чек-лист на каждом новом сайте: визуальный QA, контент, техника/SEO, сверка с Figma, тест форм и калькуляторов (ADA — отдельно, через WAVE/axe, вне агента). Это долго и легко что-то пропустить. Агент берёт список сайтов из `Сайты.txt`, сам открывает нужные страницы в трёх разрешениях (десктоп и мобилка — полный чек-лист, планшет — только визуальные проверки), прогоняет по ним чек-лист и отдаёт готовый структурированный отчёт с багами — с приоритетом «блокирует презентацию клиенту / нет», а не абстрактным «критично/некритично».

## Что именно проверяет

### Визуал (`visual-checks`)
Десктоп (1920×1080) и мобилка (390×844) — полный список ниже; планшет (768×1024) — только пункты, отмеченные как «+ планшет».

- UI/UX: элементы не наезжают друг на друга, сетка/колонки не съезжают между разрешениями, размер шрифта (считается через computed font-size — основной текст ≥14px, второстепенный ≥12px), sticky-хедер/чат-виджет не перекрывает контent. *(+ планшет)*
- Favicon (PNG, не SVG, ≥32×32) и Apple touch icon (PNG, ≥180×180) — консистентны на всех проверенных страницах.
- `<title>`: присутствует, не дефолтный, отражает содержание страницы.
- H1: ровно один, не пустой, не дублируется дословно между страницами одного типа.
- Иерархия заголовков H1→H2→H3 без пропусков.
- Главное меню: клик/тап-навигация, вложенные пункты, sticky-поведение, отсутствие дублей в DOM, область тапа на мобилке ≥14px; Top Bar (скрытие при скролле вниз/появление при скролле вверх, крестик закрытия); на десктопе — телефон в шапке кликабелен; на мобилке — гамбургер (два состояния), иконка телефона + CTA, кнопка «назад» во вложенных уровнях, скролл внутри меню; на планшете — меню не попадает в «мёртвую зону» между десктопной и мобильной вёрсткой. *(+ планшет — только пункт про «мёртвую зону»)*
- Breadcrumbs: логичная последовательность, кликабельны все звенья кроме текущего уровня, отсутствуют на главной.
- Формы — визуально: форма присутствует/отсутствует там, где нужно по дизайну; First/Last name раздельными полями (для HubSpot); раздельные поля адреса для relocation-проектов; визуальная подсветка валидации при потере фокуса. *(+ планшет — только визуальная целостность, без проверки атрибутов и без сабмита)*
- Раскрывающиеся элементы (аккордеоны/FAQ/табы): открываются с первого клика, ведут себя по дизайну (закрывают ли друг друга при открытии).
- Google Maps блок: карта загружается, работают зум и полноэкранный режим, default zoom ≈ 50 м.

*(Атрибуты полей формы и реальный сабмит — отдельная процедура, см. «Формы и калькуляторы» ниже.)*

### Контент (`content-checks`)
- Тексты: отсутствие lorem ipsum/заглушек, кириллицы (на англоязычном сайте), «славянизированных» стоковых фото; на второй языковой версии — контент/меню/футер переведены полностью.
- Картинки: современный формат (AVIF/WebP предпочтительно), вес (~150 Кб ориентир, от ~300 Кб — уже баг), отображаемое разрешение соответствует контейнеру, alt-теги описательны, нет карточек с отсутствующей картинкой.
- US-форматы: дата (MM/DD/YYYY), телефон (+1 (XXX) XXX-XXXX), адрес, валюта ($), единицы измерения (мили/футы).
- Meta-теги: title/description уникальны и в пределах длины (~50–60 / ~150–160 символов), не пустые и не дефолтные, description без телефонного номера.
- Open Graph и Twitter Card: `og:title/description/image/url`, `twitter:card/title/description/image`.

### Техника (`technical-checks`)
- Консоль: только уровень `error`; фоновый шум сторонней телеметрии (например, аналитика чужих плагинов) не попадает в отчёт.
- Сеть: запросы со статусом 404.
- HTTP-статусы страниц: отсутствие 3xx-редиректов и 4xx.
- Ссылки: пустые/битые `href`, формат `tel:`-ссылок, карточки ведут на существующие страницы (сверка по sitemap/навигации), ссылка ведёт на правильный конкретный объект (эвристика по тексту/href).
- Атрибуты `rel`/`target`: внешние ссылки — `target="_blank"` + `rel="noopener noreferrer"`; внутренние — без `target="_blank"` (кроме файлов на скачивание); `nofollow`/`sponsored` — только для партнёрских/рекламных/платных ссылок.
- Sitemap и индексация: наличие `sitemap.xml`, `noindex` на служебных/пагинационных страницах и на лендингах.
- Телефонные номера — консистентность отображаемого номера: на DEV один номер везде (кроме персональных номеров сотрудников на их страницах), на LIVE ожидается динамический своп (в т.ч. на лендингах — это тоже обычная практика), причём `href`/`aria-label`/видимый текст должны совпадать друг с другом (сравнение делается только после того, как номер стабилизировался — своп нередко подставляет его асинхронно).
- Отработка свопа номера (только на LIVE, на DEV не проверяется — там свопов не бывает): применимо к любой системе колл-трекинга (CallRail, Invoca, WhatConverts и подобные) — скрипт свопа не выдаёт JS-ошибок, связанный сетевой запрос не возвращает 4xx/5xx. Сверка исходного кода страницы с оригинальными (не свопнутыми) номерами — только если пользователь явно передал их список в `Сайты.txt`; бизнес-логику самого свопа (какой номер для какого источника трафика) и GTM/GA4/рекламные пиксели агент не проверяет — не его зона.
- Мультиязычность (`hreflang-checks`, вызывается только если у сайта есть больше одной языковой версии): метод декларации — `<html lang>`, hreflang в `<head>`, hreflang-аннотации в sitemap, заголовок `Content-Language`. Все четыре метода проверяются на проверяемых страницах, в отчёте прямо указывается, какие из них реализованы, а какие нет.
- Schema-разметка в формате JSON-LD (LocalBusiness/LegalService, Organization, Product, Article/BlogPosting, BreadcrumbList, ProfilePage, FAQPage): тип соответствует типу страницы, нет дублей, обязательные для Google поля по каждому типу присутствуют, данные релевантны странице, разметка компактна. Учитывается, что разметка может подгружаться асинхронно — извлекается последним шагом на странице.
- ADA-доступность агентом не проверяется — для этого используется отдельный специализированный инструмент (WAVE/axe и т.п.).

### Формы и калькуляторы (сабмит — полная процедура в `.claude/skills/form-submit-checks/SKILL.md`)
Вызывается условно — только если на проверяемой странице реально есть хотя бы одна форма/калькулятор; на остальных страницах этот skill вообще не подгружается в контекст. Сабмитятся все формы на странице, глубина протокола зависит от типа:
- **Лид-генерирующие** (главная контактная форма, hero/quick-quote, функциональные калькуляторы, booking/appointment, financing и любой другой CTA, ведущий к заявке) — полный протокол, потолок 10 попыток на уникальный шаблон формы; фактически используется обычно 2–4.
- **Все остальные** (рассылка, поиск, отзыв на сайте, живой чат, отклик на вакансию и т.п.) — облегчённый протокол: агент сам определяет нужные данные и делает одну тестовую отправку с той же технической верификацией, без потолка попыток. Исключение — форма, которая публикует публичный контент немедленно, без модерации: она не сабмитится автоматически, нужно отдельное явное подтверждение пользователя.
- Перед сабмитом строится карта полей: визуальная пометка обязательности сверяется с `required`-атрибутом (либо с `aria-required`/классом валидации, если CMS не использует нативный `required`); для нестандартных полей (дропдауны/даты/специфика проекта) агент готовит данные сам.
- **Определение «та же переиспользуемая форма или нет»** — не на глаз: сначала ищется технический признак (ID формы в разметке — например скрытый `_wpcf7` у Contact Form 7, класс `wpforms-form-<ID>` у WPForms, `data-form-id` у HubSpot — либо ID в самом endpoint сабмита), затем, если ID недоступен — точный набор имён полей, и только как последний по надёжности вариант — визуальное сходство заголовка/лейблов. Если у двух похожих форм на разных страницах ID/набор полей расходятся — это разные шаблоны (свой потолок в 10 попыток у каждого) и самостоятельный X-site баг несогласованной реализации.
- **Координация между параллельными агентами** — перед сабмитом лид-генерирующей формы агент проверяет файл-маркер `.form-submissions/<технический-ID>.json` в рабочей директории; если он уже создан другим параллельным агентом в этом же прогоне, форма повторно не сабмитится (результат берётся из файла), иначе агент проходит протокол и сам создаёт файл для остальных.
- Последовательность попыток: (1) граничный/невалидный кейс, на десктопе — форма должна заблокировать отправку; (2) валидный кейс, на десктопе — форма должна пройти; (3) точечная проверка (опционально, на том разрешении, где найдено противоречие); (4) троттлинг-тест (опционально, только для форм с AJAX-отправкой) — отдельная мобильная Chromium-сессия под искусственным замедлением сети, ловит тайминг-зависимые «тихие» сбои.
- Каждая попытка проверяется технически, не только по визуальному результату: сетевой запрос отправки формы ищется по признакам (метод, тайминг, содержимое payload), проверяется статус и содержимое ответа; отсутствие такого запроса — самостоятельный признак провала (кроме граничного кейса, где это ожидаемо); дополнительно проверяется консоль на `error` в узком окне вокруг клика Submit.
- Тестовые данные — согласованный набор, одинаковый для всех прогонов (см. `form-submit-checks`); в текстовое поле сообщения формы записываются URL страницы и идентификатор формы.
- Калькуляторы: если в `Сайты.txt` (`Комментарии:`) передано ТЗ на формулу — сверка точная. Без ТЗ (обычный случай) проверяются устойчивость, монотонность, реакция на разный ввод, детерминированность результата и внутренняя арифметическая согласованность видимой разбивки (без знания самой формулы).

### Figma (`figma-compare`) или сверка с оригиналом (`original-site-compare`)
Взаимоисключающие варианты — какой из двух используется, определяется вторым полем строки сайта в `Сайты.txt` (см. ниже).
- **Figma:** точечная сверка конкретной секции с макетом — только если по ней уже найдено визуальное расхождение и для страницы передан макет. Для лендингов — только если для конкретного лендинга явно указана своя Figma-ссылка.
- **Сверка с оригиналом (`ORIGINAL:<url>` вместо Figma-ссылки):** используется, когда макета нет, а перенос сверяется напрямую с реальным сайтом клиента (например, контент перенесён ИИ-агентами на новую платформу). Структура/текст/NAP/Schema/формы сверяются на каждой проверяемой странице; дополнительное открытие эталона на мобилке/планшете — только если на DEV уже найдено визуальное расхождение на этом разрешении. Соответствие страниц — тот же URL-путь на обоих доменах по умолчанию, с фолбэком на поиск по навигации эталона. Скриншоты эталона — в его собственную доменную подпапку, с пометкой `_DEV`/`_ORIGINAL` в имени файла.

### Мультиязычные сайты — как распределены проверки по разрешениям
Если у сайта есть вторая языковая версия — десктоп проверяется на основном языке, мобилка на второй языковой версии той же страницы, планшет — на основном языке (там проверяется только визуал, контент на планшете не сверяется).

## Из чего состоит агент

- **Главный промпт — [`.claude/CLAUDE.md`](.claude/CLAUDE.md).** Это системная инструкция, которую Claude Code загружает автоматически при каждом запуске из этой папки. Она не проверяет ничего сама — это оркестратор: описывает формат `Сайты.txt`, алгоритм по шагам (выбор страниц → открытие → вызов Skills → сабмит форм → скриншоты → Figma → правки на перепроверку), правило сабмита форм/калькуляторов (какие тестовые данные использовать, что можно, а что нет), формат итогового отчёта и что делать при ошибках.
- **Skills — `.claude/skills/*/SKILL.md`.** Каждый skill — это отдельный «модуль» чек-листа, который агент вызывает по ходу работы; Claude Code подгружает его содержимое только когда он реально нужен (экономия токенов):
  - `visual-checks`, `content-checks`, `technical-checks` — три группы проверок выше.
  - `form-submit-checks` — реальный сабмит-тест форм/калькуляторов, вызывается только если на странице есть хотя бы одна форма: полный протокол (до 10 попыток) для лид-генерирующих форм (контакт, quote/estimate, callback, booking, financing), облегчённый однократный сабмит для всех остальных (рассылка, поиск, отзыв, живой чат, отклик на вакансию).
  - `hreflang-checks` — метод декларирования мультиязычности (html lang, hreflang в `<head>`/sitemap, `Content-Language`), вызывается только на мультиязычных сайтах.
  - `figma-compare` — сверка с макетом, вызывается только при подозрении на расхождение.
  - `original-site-compare` — сверка с реальным сайтом вместо макета, вызывается только если в `Сайты.txt` вместо Figma-ссылки указан `ORIGINAL:<url>`.
  - `eval-regression` — регресс-тест промпта на тестовой фикстуре, вызывается только по явной просьбе («прогони eval» и т.п.), не часть проверки сайта клиента — см. «Регресс-тестирование промпта» ниже.
  - `playwright-cli` — техническая справка по командам браузерной автоматизации (открытие страниц, snapshot, click, eval и т.п.), сгенерированная самим Playwright CLI — ей пользуются остальные skills, чтобы управлять браузером.

Ничего кроме этих файлов агенту для работы не нужно — весь чек-лист и вся логика живут в `.claude/`.

## Что передавать в `Сайты.txt`

**Этот файл не входит в репозиторий** (добавлен в `.gitignore`) — в нём реальные данные клиента (URL, номера телефонов, комментарии ПМа), их не нужно и не должно коммитить в git. Создайте `Сайты.txt` в корне проекта (рядом с `Readme.md`) самостоятельно перед первым запуском — просто новый текстовый файл с таким именем, пустой репозиторий его не содержит.

Один основной сайт клиента на строку:

```
URL | ссылка_на_Figma | DEV
```

- **URL** — обязателен.
- **Ссылка на Figma** — опциональна. Если макета нет, но перенос сверяется напрямую с реальным сайтом клиента — вместо неё укажите `ORIGINAL:<url эталонного сайта>` (например `URL | ORIGINAL:https://real-site.com | DEV`) — это включает `original-site-compare` вместо `figma-compare`. Два варианта взаимоисключающие.
- **Окружение `DEV`/`LIVE`** — опционально, но желательно указывать: на `LIVE` номер телефона может быть легитимно подменён (своп для колл-трекинга) и отличаться от Figma/DEV; на `DEV` такого быть не должно. Без этой пометки агент не сможет отличить легитимный своп от реальной ошибки в номере. **На возможность сабмитить формы окружение не влияет.**

Если у клиента несколько независимых основных сайтов (разные бренды/домены) — отдельная строка на каждый.

Плюс до трёх опциональных блоков в конце файла:

```
Лендинги:
- [URL рекламной посадочной страницы] | [свой Figma-фрейм, необязательно]

Правки:
- [что перепроверить, что было исправлено]

Комментарии:
- [пожелания клиента/ПМа: специфика проекта, ТЗ на логику калькулятора, тип бизнеса и т.п.]
```

**`Лендинги:` — важно.** Это единственный способ сказать агенту «эта страница — рекламный лендинг, а не обычная страница сайта». Без явного перечисления здесь агент не станет применять к странице лендинг-специфичное правило (обязательный `noindex`) — даже если URL похож на рекламный (`/ppc-...`, с `utm_*` и т.п.). Каждый URL из этого списка проверяется целиком (весь чек-лист, оба разрешения) как конкретная страница, а не сэмплируется по типам, как основной сайт. Телефонные номера на лендингах ведут себя так же, как на основном сайте — свопы для трекинга звонков являются обычной практикой агентства.

**Про Figma для лендингов:** сравнение с макетом для лендинга выполняется только если для него указана своя Figma-ссылка (дизайн лендингов обычно отличается от основного сайта). Указывайте ссылку там, где сверка реально нужна.

Пример полного файла:
```
https://client-site.com | https://figma.com/file/xxxx/Main | DEV

Лендинги:
- https://client-site.com/ppc-landing-1/
- https://client-site.com/ppc-landing-2/

Правки:
- [contact form] сабмит не работал — перепроверить

Комментарии:
- Проект — moving company, проверить поля адреса и автоподбор
- ТЗ на калькулятор: cost = base_rate + distance_miles * per_mile_rate
```

### Рекомендуемая структура блока `Комментарии:` для больших/нестандартных задач

Для простых прогонов пары строк достаточно (см. пример выше). Если задача крупная (много страниц, есть правки от ПМа/клиента, нужно что-то сверить по таблице, или вы разово меняете стандартное поведение агента) — удобнее разбить `Комментарии:` на именованные подсекции, а не писать одним сплошным текстом:

```
Комментарии:

ПРОЕКТ: [тип бизнеса / особенности, которые влияют на обычные проверки]

ПРАВКИ ОТ ПМ/КЛИЕНТА/ЧАТ-БОТА (проверить дополнительно):
1. [конкретная формулировка правки/вопроса — можно вставлять цитатой как есть]
2. ...

СПРАВОЧНЫЕ ДАННЫЕ (если нужно что-то сверить по таблице — номера, ID, коды):
- ...

СПЕЦИФИКА ТОЛЬКО ЭТОЙ ЗАДАЧИ (разовое отступление от стандартного поведения агента — явно пометьте, что это не постоянное правило):
- ...

ФОРМАТ ОТЧЁТА: [встроенный / уточнить, если нужно что-то другое]
```

Так агент не путает «это правило для этого прогона» с «это стандартное поведение навсегда», и ничего не теряется среди сплошного текста.

Шаги ниже можно пройти вручную (как описано) или попросить агента в Claude Desktop выполнить их за вас, указав ему на этот раздел — команды одни и те же, разница только в том, кто их вводит. Исключение — вход в аккаунт Claude (и в Figma, если он нужен): это всегда делаете лично вы через открывшийся браузер, ни один интерфейс агента не может пройти авторизацию за вас.

### 1. Установите необходимое ПО
- **Node.js 18+** – [скачать](https://nodejs.org/)
- **Git Bash** (для Windows) – [скачать](https://git-scm.com/downloads/win)
- **Аккаунт Claude** – [зарегистрироваться](https://claude.ai/)
- **Аккаунт Figma** (опционально, если нужна сверка с макетами)

### 2. Установите Claude Code CLI
```bash
npm install -g @anthropic-ai/claude-code
```
Проверьте установку:
```bash
claude --version
```

### 3. Установите Playwright CLI и браузеры
```bash
npm install -g @playwright/cli@latest
playwright-cli install-browser
```

### 4. Авторизуйтесь в Claude Code
```bash
claude
```
Следуйте инструкциям в терминале: откроется браузер, где нужно войти в аккаунт Claude.

### 5. Клонируйте репозиторий
```bash
git clone https://github.com/vekonev-prof/qa-agent-tqa.git
cd qa-agent-tqa
```

### 6. Установите Skill для Playwright CLI (обязательно!)
```bash
playwright-cli install --skills
```
Эта команда создаст файл `.claude/skills/playwright-cli/SKILL.md` для интеграции Playwright CLI с Claude Code.

### 7. Настройте Figma MCP (опционально)
Если планируете сверять с макетами:
```bash
claude mcp add --transport http figma https://mcp.figma.com/mcp
```
При первом запуске `claude` откроется браузер для авторизации в Figma.

### 8. Подготовьте `Сайты.txt`
Создайте файл `Сайты.txt` **в корне агента** (в этой же папке, где `Readme.md` и `.claude/`) — в репозитории этого файла нет (он в `.gitignore`, так как в нём реальные данные клиентов), поэтому его нужно создавать каждый раз самостоятельно. Формат — в разделе «Что передавать в `Сайты.txt`» выше.

### 9. Запустите агента

Есть два равнозначных способа — агент один и тот же (тот же `CLAUDE.md` и те же Skills), разница только в интерфейсе.

**Способ 1 — через терминал (Git Bash):**
```bash
claude -p "Проверь сайты из файла Сайты.txt" --output-format text | tee report.txt
```
Вывод будет показан в терминале и одновременно сохранён в файл `report.txt`. Удобно, когда нужен готовый файл на диске сразу после запуска.

**Способ 2 — через приложение Claude Desktop (вкладка Code):**
Откройте приложение Claude Desktop → вкладка Code → откройте эту папку проекта (там, где `Readme.md` и `.claude/`) как рабочую директорию — и просто напишите в чат:
> Проверь сайты из файла Сайты.txt

Результат придёт прямо в переписке. Если нужен файл `report.txt` на диске — попросите об этом явно в том же сообщении («…и сохрани отчёт в `report.txt`»). Этот способ удобен для разовых проверок и не требует Git Bash.

Скриншоты багов сохраняются в папку `screenshots/{домен}/` (отдельная подпапка на каждый проверенный сайт — так файлы разных клиентов/сайтов не перемешиваются), служебные снапшоты страниц (yml) — в `.playwright-cli/`.

### 10. Посмотрите отчёт
Откройте `report.txt` — отчёт состоит из трёх чек-листов, каждая находка — только в одном из них:
1. **Баги** — подтверждённые дефекты, с приоритетом «блокирует презентацию клиенту / не блокирует».
2. **Правки на перепроверку** — статус ранее переданных в `Правки:` пунктов.
3. **Рекомендации для ручной проверки** — всё, в чём агент не уверен на 100% или не может подтвердить сам (например, что тестовые сабмиты форм дошли в CRM/почту — с указанием, какая форма и на какой thank-you URL).

## 🧠 Как это работает

| Что делает агент | Подробнее |
|---|---|
| Выбор страниц | Проверяет только 1–2 страницы из каждого типа (шаблона) – не ходит по всему сайту |
| Разрешения | Десктоп (1920×1080, Chrome) и мобилка (390×844, WebKit) — полный чек-лист на одном и том же наборе страниц из выборки; планшет (768×1024, WebKit) — те же страницы, но только визуальные проверки (`visual-checks`) |
| Проверки | Три группы Skills: `visual-checks`, `content-checks`, `technical-checks` — вызываются на каждой отобранной странице (на планшете — только `visual-checks`) |
| Формы и калькуляторы | Отдельный skill `form-submit-checks`, вызывается условно — только если на странице есть хотя бы одна форма (не грузится в контекст на остальных страницах). Полный протокол для лид-генерирующих, облегчённый однократный сабмит для остальных — детали см. раздел «Формы и калькуляторы» выше. При параллельном запуске нескольких агентов координация «кто какой шаблон тестирует» закрепляется заранее в промпте каждого агента |
| Мультиязычность | Отдельный skill `hreflang-checks`, вызывается условно — только если у сайта больше одной языковой версии |
| Figma / сверка с оригиналом | Сравнивает с макетом только при найденных расхождениях (экономия токенов); либо, если макета нет и вместо него в `Сайты.txt` указан `ORIGINAL:<url>`, сверяет DEV с реальным сайтом клиента (`original-site-compare`) — структуру/NAP/Schema на каждой странице, мобилку/планшет эталона — только при найденном расхождении на DEV |
| Своп номеров | На LIVE по умолчанию (`technical-checks`): консистентность номера + техническая отработка свопа (скрипт/сеть). На DEV не проверяется — там свопов не бывает |
| Сверка с оригинальными номерами | Только в двух случаях: список от пользователя в `Сайты.txt`, либо задача явно описана как прямая сверка DEV с реальным LIVE-сайтом вместо Figma-макета — тогда эталоном служит номер из сырого HTML LIVE-сайта (до выполнения JS, не через браузер/eval после отрисовки) |
| Скриншоты | Делает только при обнаружении проблем, сохраняет в `screenshots/{домен}/` (папка на каждый сайт) – не тратит токены на успешные шаги |
| Оптимизация токенов | `snapshot --depth=4` и `find` вместо полного accessibility tree, группировка массовых багов в одну строку отчёта |
| Отчёт | Три отдельных чек-листа без пересечений: Баги (блокирует презентацию клиенту / MAJOR / MINOR) → Правки на перепроверку → Рекомендации для ручной проверки. Всё, в чём агент не уверен на 100%, попадает только в рекомендации, не в баг-лист |

## Регресс-тестирование промпта (для поддержки агента)

Перед правкой `.claude/CLAUDE.md` или любого skill — прогоните тестовую фикстуру из папки `eval/`, чтобы убедиться, что правка не сломала уже работающую проверку, без необходимости перечитывать всё вручную.

Ничего заполнять или готовить не нужно — тестовый сайт и список для проверки уже полностью готовы, свой рабочий `Сайты.txt` при этом никак не трогается. Достаточно попросить агента в чате «прогони eval» (или «проверь регресс» и т.п.) — за это отвечает отдельный skill `eval-regression`, который сам читает `eval/README.md` и знает актуальный список фикстур, даже если он вырастет. Подробности процесса — там же, в [`eval/README.md`](eval/README.md).

## 📌 Важно
- Агент сабмитит все формы/калькуляторы на проверяемых страницах, безопасными тестовыми данными (см. `.claude/skills/form-submit-checks/SKILL.md`): лид-генерирующие — по полному протоколу (потолок 10 попыток на уникальный шаблон, обычно нужно намного меньше), остальные (рассылка, поиск, отзыв, чат, вакансии) — облегчённо, одна отправка. Исключение — форма, немедленно публикующая публичный контент без модерации: без отдельного явного подтверждения пользователя не сабмитится.
- Каждый сабмит проверяется технически (по сетевому запросу и консоли), а не только по визуальному результату; отсутствие сетевого запроса — сам по себе признак провала (кроме ожидаемо заблокированного граничного кейса).
- Для AJAX-форм дополнительно прогоняется троттлинг-тест на искусственно замедленной сети (Chromium-only, отдельная именованная сессия) — ловит тайминг-зависимые сбои, незаметные на обычной скорости соединения.
- Планшет (768×1024, WebKit) открывается по умолчанию как третье разрешение, но проверяется только визуально (`visual-checks`) — контент и техника там повторно не сверяются.
- Агент не входит в админку/CMS и не может сам проверить, дошло ли письмо с формы — это всегда остаётся ручной проверкой в отчёте.
- Агент не ходит по всему сайту – выбирает 1–2 страницы из каждого типа (экономия токенов).
- Для работы с Figma нужен Pro-аккаунт (или токен доступа).
- Устойчив к типовым сбоям: сайт под паролем без доступа, антибот-защита/капча (в т.ч. при попытке сабмита формы), недоступный Figma MCP или упавшая браузерная сессия не останавливают весь прогон — фиксируются в отчёте и проверка идёт дальше (полный список — `.claude/CLAUDE.md`, раздел «Обработка ошибок»).
- **ADA-доступность не входит в проверку агента** — используйте отдельный специализированный инструмент (WAVE/axe и т.п.).
