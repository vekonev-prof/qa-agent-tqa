# Eval — регресс-тест промпта и Skills

Назначение: проверить, что правка `.claude/CLAUDE.md`, любого `.claude/skills/*/SKILL.md`, `.claude/agents/*.md` или `.claude/tools/page-audit.js` не сломала уже работающую проверку — без необходимости перечитывать всё вручную.

## Что здесь

- `fixture-site/` — маленький статический тестовый сайт (не реальный клиент, можно коммитить) с сознательно "зашитыми" находками.
- `ground-truth.md` — точный список того, что агент обязан найти и НЕ обязан найти.
- `Сайты.eval.txt` — готовый входной файл для основного прогона (окружение DEV), в том же формате, что и `Сайты.txt`, но не гитигнорится (тут нет реальных данных клиента) и не заменяет собой ваш рабочий `Сайты.txt` — агента просто явно просят прочитать этот файл вместо него (см. «Как прогнать» ниже).
- `fixture-site/visual.html` — страница только для визуального просмотра (Шаг 3.3, `visual-glance`; пункты 43–47 в `ground-truth.md`); в sitemap и меню не входит, упомянута в `Комментарии:` файла `Сайты.eval.txt`.
- `Сайты.eval-live.txt` — отдельный входной файл для дополнительной проверки: логика свопа телефонных номеров (`technical-checks` §7) применяется только на LIVE, поэтому её нельзя проверить основной DEV-фикстурой — нужен отдельный прогон с этим файлом.

## Как прогнать

Тестовый сайт и список для проверки уже лежат в этой папке; копировать или переименовывать ничего не нужно, нужно только один раз поправить путь (шаг 0).

0. **Перед первым запуском** замените префикс `file:///C:/Users/Dev/Desktop/qa-agent-by-vlad/` на путь вашей копии проекта (папка, где лежит `eval/`) в `eval/Сайты.eval.txt`, `eval/Сайты.eval-live.txt` и `eval/fixture-site/sitemap.xml` (в sitemap — во всех 5 записях `<loc>`). Без этого `file://`-ссылки будут битыми.
1. Откройте проект в приложении Claude Desktop (вкладка Code) — так же, как для обычной работы с агентом, только не трогайте свой рабочий `Сайты.txt`.
2. Напишите в чат:
   > Прочитай файл `eval/Сайты.eval.txt` и проверь сайты из него как обычно. Это тестовая фикстура для eval, не реальный клиент.
3. Сверьте ответ агента с `eval/ground-truth.md` — по каждому применимому DEV-пункту (все, кроме 18–19 — это LIVE-пункты, см. шаг 4): нашёл/не нашёл то, что должен(на) был(а). Агент сохраняет отчёт в `projects/fixture-site/{прогон}/report.md` (объяснение — в конце файла).
4. Повторите шаги 2–3, но со ссылкой на `eval/Сайты.eval-live.txt` — это отдельная LIVE-фикстура для проверки свопа номеров (пункты 18–19 в `ground-truth.md`).


Если удобнее через терминал, а не через чат — тот же смысл одной командой (для каждого из двух файлов отдельно):
```bash
claude -p "Прочитай файл eval/Сайты.eval.txt и проверь сайты из него как обычно. Это тестовая фикстура для eval, не реальный клиент." --output-format text | tee eval/last-run-report.txt
claude -p "Прочитай файл eval/Сайты.eval-live.txt и проверь сайты из него как обычно. Это тестовая фикстура для eval, не реальный клиент." --output-format text | tee eval/last-run-report-live.txt
```
`eval/last-run-report*.txt` не коммитьте — не для репозитория, полезны только вам локально.

## Когда прогонять

- После любой правки в `.claude/CLAUDE.md`, `.claude/skills/*/SKILL.md`, `.claude/agents/*.md` или `.claude/tools/page-audit.js` — перед тем, как гонять агента на реальном клиенте.
- Не нужно прогонять на каждый мелкий чат-вопрос — только когда реально отредактирован промпт/skill.

## Сколько находок "достаточно" в фикстуре

Не старайтесь покрыть здесь весь чек-лист целиком — это отдельная, гораздо более дорогая по объёму задача с падающей отдачей (одна проверка на 5 строк текста не окупает время на её поддержку). Сфокусируйтесь на:
1. Проверках со сложной условной логикой (исключения, "если А, то Б, иначе В") — там регрессия проще всего проскальзывает незаметно.
2. Проверках, которые уже реально меняли/чинили в истории проекта (в этом репо — `git log --oneline` показывает, какие правки уже случались).
3. 1-2 базовых sanity-проверках (типа lorem ipsum, дубль H1) — просто чтобы убедиться, что общий чек-лист не сломан целиком.

47 пунктов в `ground-truth.md` (45 в основной DEV-фикстуре + 2 в LIVE-фикстуре свопа) — это стартовый набор, покрывающий самые регресс-опасные места на сегодня. Это не финальное число.

## Как расширять со временем

Правило роста: **фикстура растёт от реальных промахов, а не заранее.** Как только в реальном прогоне на клиенте вы поймаете ситуацию "агент должен был это найти/не найти, но повёл себя иначе" (то есть баг в самом промпте, а не в сайте клиента) — добавьте в `fixture-site/` минимальный кусок, который воспроизводит именно эту ситуацию, и добавьте соответствующий пункт в `ground-truth.md` с пометкой, откуда он взялся (дата/клиент можно не указывать, а вот саму механику — обязательно). Так фикстура со временем накапливает именно те кейсы, которые реально кусались, а не гипотетические.

Если фикстура станет слишком большой и прогонять её станет дорого (много токенов на один регресс-тест) — можно разбить на несколько мелких тестовых сайтов по темам (например, отдельно "формы/калькуляторы", отдельно "мультиязычность/hreflang") и прогонять только тот, что относится к изменённому skill, а не всю фикстуру целиком на каждую правку.

## Подбор effort для подагентов

Эта же фикстура используется не только для регресс-теста промпта, но и для подбора `effort` подагента, который проверяет страницы (`.claude/agents/tqa-page-agent.md`). Три вспомогательных агента (`qa-eval-low-effort` / `qa-eval-mid-effort` / `qa-eval-high-effort`, `effort: low` / `medium` / `high`) существуют для этого.

**Как повторить сравнение:**
1. Запустите агентов параллельно (каждому — своя именованная сессия playwright-cli, свой `{прогон}` и свой диапазон номеров сабмитов): на `Сайты.eval.txt` и на `Сайты.eval-live.txt`.
2. Сверьте отчёты с `ground-truth.md`.
3. Токены считайте по JSONL-транскриптам подагентов (`~/.claude/projects/<проект>/<сессия>/subagents/`): для каждого уникального ответа модели `input×1 + output×5 + cache_creation×2 + cache_read×0.1`. Поле `model` в тех же записях показывает, на какой модели реально шёл агент.
4. Агенты `qa-eval-*` работают как одиночные: Шаг 3.3 (визуальный просмотр, в `Сайты.eval.txt` включён строкой `Визуальный просмотр: да`) выполняет сам агент, суффикс сессий (вместо `solo`), `{прогон}` и диапазон номеров он берёт из промпта.
5. Пункты 43–47 (`visual.html`, Шаг 3.3) при сравнении effort считайте отдельно от пунктов 1–42 — таблица в `Readme.md` снята без них.
6. Новые или изменённые файлы агентов подхватываются только после перезапуска сессии.

**Результаты сравнения и выбор `effort`** — в `Readme.md`, раздел «Модель и effort для подагентов». Калибровка привязана к модели (`model: sonnet` — алиас поколения, всегда указывает на последний Sonnet): перепрогоняйте сравнение после смены поколения модели или значительной правки skills.

**Про пункт №14 (дедупликация формы по техническому ID) при перепрогоне:** каждый прогон получает свою папку `projects/fixture-site/{прогон}/` в `projects/` (не `eval/fixture-site/`), поэтому маркер `.form-submissions/` прошлого прогона на пункт 14 не влияет и ручная очистка не нужна. (`fixture-site` — это `{домен}` для этой фикстуры: `Сайты.eval.txt` использует `file://`-URL без хоста, поэтому рабочая папка называется по последнему сегменту пути.)
