# Eval — регресс-тест промпта и Skills

Назначение: проверить, что правка `.claude/CLAUDE.md` или любого `.claude/skills/*/SKILL.md` не сломала уже работающую проверку — без необходимости перечитывать всё вручную.

## Что здесь

- `fixture-site/` — маленький статический тестовый сайт (не реальный клиент, можно коммитить) с сознательно "зашитыми" находками.
- `ground-truth.md` — точный список того, что агент обязан найти и НЕ обязан найти.
- `Сайты.eval.txt` — готовый входной файл для основного прогона (окружение DEV), в том же формате, что и `Сайты.txt`, но не гитигнорится (тут нет реальных данных клиента) и не заменяет собой ваш рабочий `Сайты.txt` — агента просто явно просят прочитать этот файл вместо него (см. «Как прогнать» ниже). **Ничего в нём заполнять/дописывать не нужно — он уже полностью готов к использованию.**
- `Сайты.eval-live.txt` — отдельный входной файл для дополнительной проверки: логика свопа телефонных номеров (`technical-checks` §7) применяется только на LIVE, поэтому её нельзя проверить основной DEV-фикстурой — нужен отдельный прогон с этим файлом.

## Как прогнать

Ничего заполнять, копировать или переименовывать не нужно — весь тестовый сайт и список для проверки уже готовы в этой папке.

1. Откройте проект в приложении Claude Desktop (вкладка Code) — так же, как для обычной работы с агентом, только не трогайте свой рабочий `Сайты.txt`.
2. Напишите в чат:
   > Прочитай файл `eval/Сайты.eval.txt` и проверь сайты из него как обычно. Это тестовая фикстура для eval, не реальный клиент.
3. Сверьте ответ агента с `eval/ground-truth.md` — по каждому из пунктов 1–12: нашёл/не нашёл то, что должен(на) был(а).
4. Повторите шаги 2–3, но со ссылкой на `eval/Сайты.eval-live.txt` — это отдельная LIVE-фикстура для проверки свопа номеров (пункты 13–14 в `ground-truth.md`).

Реальный `Сайты.txt` при этом вообще не участвует — подменять и возвращать нечего, перепутать с боевой проверкой негде.

Если удобнее через терминал, а не через чат — тот же смысл одной командой (для каждого из двух файлов отдельно):
```bash
claude -p "Прочитай файл eval/Сайты.eval.txt и проверь сайты из него как обычно. Это тестовая фикстура для eval, не реальный клиент." --output-format text | tee eval/last-run-report.txt
claude -p "Прочитай файл eval/Сайты.eval-live.txt и проверь сайты из него как обычно. Это тестовая фикстура для eval, не реальный клиент." --output-format text | tee eval/last-run-report-live.txt
```
`eval/last-run-report*.txt` не коммитьте — не для репозитория, полезны только вам локально.

## Когда прогонять

- После любой правки в `.claude/CLAUDE.md` или `.claude/skills/*/SKILL.md` — перед тем, как гонять агента на реальном клиенте.
- Не нужно прогонять на каждый мелкий чат-вопрос — только когда реально отредактирован промпт/skill.

## Сколько находок "достаточно" в фикстуре

Не старайтесь покрыть здесь весь чек-лист целиком — это отдельная, гораздо более дорогая по объёму задача с падающей отдачей (одна проверка на 5 строк текста не окупает время на её поддержку). Сфокусируйтесь на:
1. Проверках со сложной условной логикой (исключения, "если А, то Б, иначе В") — там регрессия проще всего проскальзывает незаметно.
2. Проверках, которые уже реально меняли/чинили в истории проекта (в этом репо — `git log --oneline` показывает, какие правки уже случались).
3. 1-2 базовых sanity-проверках (типа lorem ipsum, дубль H1) — просто чтобы убедиться, что общий чек-лист не сломан целиком.

31 пункт в `ground-truth.md` (29 в основной DEV-фикстуре + 2 в LIVE-фикстуре свопа) — это стартовый набор, покрывающий самые регресс-опасные места на сегодня. Это не финальное число.

## Как расширять со временем

Правило роста: **фикстура растёт от реальных промахов, а не заранее.** Как только в реальном прогоне на клиенте вы поймаете ситуацию "агент должен был это найти/не найти, но повёл себя иначе" (то есть баг в самом промпте, а не в сайте клиента) — добавьте в `fixture-site/` минимальный кусок, который воспроизводит именно эту ситуацию, и добавьте соответствующий пункт в `ground-truth.md` с пометкой, откуда он взялся (дата/клиент можно не указывать, а вот саму механику — обязательно). Так фикстура со временем накапливает именно те кейсы, которые реально кусались, а не гипотетические.

Если фикстура станет слишком большой и прогонять её станет дорого (много токенов на один регресс-тест) — можно разбить на несколько мелких тестовых сайтов по темам (например, отдельно "формы/калькуляторы", отдельно "мультиязычность/hreflang") и прогонять только тот, что относится к изменённому skill, а не всю фикстуру целиком на каждую правку.

## Подбор reasoning effort для подагентов

Эта же фикстура используется не только для регресс-теста промпта, но и для калибровки `reasoning_effort` подагента, который проверяет страницы (`.claude/agents/tqa-page-agent.md`). Три вспомогательных типа агента (`qa-eval-low-effort` / `qa-eval-mid-effort` / `qa-eval-high-effort`, эффорт 20/40/80 соответственно) существуют для этого — прогоните все три на `Сайты.eval.txt`, сверьте с `ground-truth.md` и сравните расход токенов.

**Результат последнего сравнения (2026-09-16, 17 применимых пунктов ground-truth из основной DEV-фикстуры):**

| Эффорт | Покрытие ground-truth | Взвешенные эффективные токены* |
|---|---|---|
| 20 | 15.5/17 — пропустил lorem ipsum (базовый sanity-пункт №9) | 1 223 790 |
| **40** | **~17/17** | **1 124 243** |
| 80 | 17/17 | 2 061 898 |

\* `input×1 + output×5 + cache_creation×2 + cache_read×0.1` — считается по JSONL-транскрипту подагента, не по сырым токенам.

**Выбран эффорт 40** для `tqa-page-agent` — он не «компромисс», а строго доминирует над 20 (дешевле и не пропустил ничего) и даёт то же покрытие, что 80, за ~55% его стоимости.

**Эта калибровка привязана к конкретной модели — Sonnet 5** (`model: sonnet` в `tqa-page-agent.md` — алиас поколения, а не точный ID; он сам обновится на следующее поколение без правки файла). Число `40` получено на поведении именно Sonnet 5 и не гарантированно останется оптимальным, когда `sonnet` начнёт резолвиться в другую модель. Перепрогоняйте это сравнение заново после смены поколения модели (или значительной правки skills) — не полагайтесь на устаревшие цифры выше как на постоянную истину.

**Про пункт №14 (дедупликация формы по техническому ID) при перепрогоне:** с введением подпапки `{прогон}/` (дата и время старта, см. CLAUDE.md, «Рабочая папка сайта») это больше не требует ручной очистки — каждый новый прогон получает свою собственную папку `fixture-site/{прогон}/.form-submissions/`, поэтому маркер от предыдущего прогона физически не может повлиять на новый. (`fixture-site` — это `{домен}` для этой фикстуры: `Сайты.eval.txt` использует `file://`-URL без хоста, поэтому рабочая папка называется по последнему сегменту пути.)
