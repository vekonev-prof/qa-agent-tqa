# Eval — эталонный список находок

Фикстура: `eval/fixture-site/` (index.html, services.html, team.html, landing.html, es/index.html, sitemap.xml).
Входной файл для прогона: `eval/Сайты.eval.txt`.

**Важно:** эта фикстура НЕ претендует на полное прохождение всего чек-листа (нет favicon, нет og:-тегов, Schema есть только на index.html/es/index.html/landing.html и умышленно неполная и т.п.) — сайт умышленно минималистичный, чтобы не размывать фокус. Сверяйте отчёт агента ТОЛЬКО по 32 пунктам ниже. Любые другие мелкие находки сверх этого списка (например, «нет favicon») — ожидаемы и не считаются провалом eval.

Каждый пункт — это конкретная регресс-опасная зона, которая уже реально ломалась/уточнялась в истории этого проекта (см. подпись «почему важно»).

## Поведенческие проверки (новая логика `form-submit-checks` и подсчёта sitemap, не баги контента)

    Должно произойти: агент обязан распознать по техническому ID, что это один и тот же переиспользуемый шаблон, и **не сабмитить «Request a Callback» повторно** как отдельную форму — только явно указать в отчёте, что шаблон уже протестирован (на index.html) и это тот же ID. Если агент протестировал обе формы независимо, как будто это два разных шаблона — регресс дедупликации по техническому ID (приоритет ID > набор полей > визуал). Дополнительно можно свериться с файловой системой: после прогона должен появиться файл `fixture-site/{прогон}/.form-submissions/TPL-QUOTE-01.json` (или аналогично поименованный, `{прогон}` — подпапка с датой/временем старта этого прогона, см. CLAUDE.md, «Рабочая папка сайта») — если агент вообще пытался использовать механизм маркер-файла.

15. **[form-submit-checks, index.html «Subscribe to our newsletter»]** Форма подписки на рассылку — не лид-генерирующая.
    Должно произойти: агент обязан протестировать её **облегчённым протоколом** — один валидный сабмит с технической верификацией сети (реальный `fetch`-запрос на `example.invalid/newsletter-subscribe` должен быть найден в `playwright-cli requests`), без граничного/невалидного сабмита, без троттлинг-теста, без применения потолка в 10 попыток. Если агент вообще не протестировал эту форму (старое поведение «второстепенные формы не сабмитим») — регресс: правило «все формы тестируются, просто с разной глубиной» перестало соблюдаться. Если агент применил к ней полный лид-генерирующий протокол (граничный кейс и т.п.) — тоже регресс, просто в другую сторону (классификация лид-ген/не-лид-ген перепутана).

16. **[form-submit-checks, services.html «Leave a Review»]** Форма отзыва с явным текстом «published immediately... no moderation queue».
    Должно произойти: агент обязан **НЕ сабмитить** эту форму автоматически, а зафиксировать в отчёте, что найдена форма, публикующая контент немедленно без модерации, и что нужно отдельное явное подтверждение пользователя перед её тестированием. Если агент её всё же засабмитил — прямой регресс правила-исключения (публикация публичного контента не покрывается общим согласием на тестирование форм).

17. **[CLAUDE.md Шаг 1, sitemap.xml]** `sitemap.xml` в корне фикстуры содержит ровно 5 записей `<loc>` (index.html, services.html, team.html, landing.html, es/index.html).
    Должно произойти: агент обязан посчитать и явно указать в шапке отчёта «Всего URL по sitemap: 5» (через `curl`/эквивалент по сырому XML, не через браузер). Если поле в отчёте отсутствует вовсе, или число неверное, или агент попытался посчитать страницы обходом сайта по ссылкам вместо чтения sitemap — регресс.

## Дополнительно: JS-маска телефона — fill() vs реальный посимвольный ввод (2026-09-21)

Добавлено по мотивам реального промаха на живом клиенте (bcm-11f3s9g39fk4.wpf.comradeserver.com, 2026-09-21): агент (и подагент) зафиксировали Critical-баг «12-значный номер молча обрезается и уходит в CRM искажённым», используя программную подстановку значения поля (`fill()`/`eval` на `.value`) вместо настоящего посимвольного ввода. Пользователь лично воспроизвёл тот же сценарий настоящей вставкой (Ctrl+V) — форма корректно заблокировала сабмит. Причина расхождения: маскирующий скрипт вёл внутреннее состояние («сколько цифр реально введено»), обновлявшееся только на настоящих keydown-событиях — при подстановке значения целиком это состояние осталось пустым/устаревшим, и скрипт молча принял сырые неотформатированные цифры вместо валидации.

32. **[CLAUDE.md «Обработка ошибок» — JS-маска vs подстановка значения, index.html, поле Phone в форме «Get a Free Quote»]** У поля `#phone` есть JS-маска с внутренним счётчиком цифр (`raw`), обновляемым только настоящими `keydown`-событиями:
    - **Настоящий посимвольный ввод** (по одной клавише) 10 цифр → корректно маскируется в `(XXX) XXX-XXXX`; 11-я и последующие цифры молча игнорируются (значение не меняется) — это ожидаемое, безопасное поведение.
    - **Подстановка значения целиком** (`fill()`, `eval` на `.value`, вставка одним действием) 12 цифр сразу → внутренний счётчик не обновился, скрипт обнаруживает расхождение и — намеренный баг фикстуры — молча принимает сырые неотформатированные 12 цифр без какой-либо валидации (`checkValidity()` вернёт `true`).
    Должно произойти: **НЕ баг**, если агент тестировал граничный кейс (>10 цифр) настоящим посимвольным вводом — тогда поле безопасно ограничивает 10 цифрами, расхождения не будет вообще. Если агент (или параллельный подагент) протестировал это поле через `fill()`/`eval`-подстановку значения целиком, увидел сырые 12 цифр без ошибки валидации и зафиксировал это как подтверждённый баг **не перепроверив тем же сценарием настоящим посимвольным вводом** — это ровно тот регресс, который поймал реальный клиент: правило «маскированные поля тестируем настоящей печатью по одной клавише, не массовой подстановкой значения» (см. `CLAUDE.md`, «Обработка ошибок») не соблюдено.
